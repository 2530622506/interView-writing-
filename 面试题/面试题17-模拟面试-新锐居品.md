### Q2：localStorage、sessionStorage、Cookie 的区别？

## 第二部分：JavaScript 基础

### Q4：var、let、const 的区别？

**参考答案：**

| 特性 | var | let | const |
|------|-----|-----|-------|
| 作用域 | 函数作用域 | 块级作用域 | 块级作用域 |
| 变量提升 | ✅ 提升并初始化为 undefined | ✅ 提升但不初始化（TDZ） | ✅ 提升但不初始化（TDZ） |
| 重复声明 | ✅ | ❌ | ❌ |
| 挂载 window | ✅ | ❌ | ❌ |
| 重新赋值 | ✅ | ✅ | ❌ |

**⚠️ 重点：TDZ（暂时性死区）**

```js
console.log(a);  // undefined（var 提升并初始化）
console.log(b);  // ReferenceError: Cannot access 'b' before initialization
var a = 1;
let b = 2;
```

- `let`/`const` 也有提升，但不会初始化，从声明到执行到该行之前的区间称为 **TDZ**
- 注意区分两种报错：
  - `Cannot access 'b' before initialization` → 变量存在但在 TDZ 中
  - `b is not defined` → 变量根本没有声明

### Q5：事件循环（Event Loop）与宏任务、微任务

**参考答案：**

JS 是单线程语言，通过事件循环实现非阻塞。

**一句话记忆法：** 宏任务是"下一轮"，微任务是"这一轮结束前必须先清干净"。

| 类型 | 包含内容 |
|------|---------|
| 宏任务 | `setTimeout`、`setInterval`、`setImmediate`（Node）、I/O、渲染事件 |
| 微任务 | `Promise.then`、`async/await`、`queueMicrotask()`、`MutationObserver`、`process.nextTick`（Node） |

**执行顺序题：**
```js
console.log('1');
setTimeout(() => { console.log('2'); }, 0);
Promise.resolve().then(() => { console.log('3'); });
console.log('4');
// 输出：1 4 3 2
```

执行步骤：
1. 同步代码：输出 `1`、`4`
2. 清空微任务队列：输出 `3`
3. 执行宏任务：输出 `2`

### Q6：闭包是什么？手写防抖函数

**闭包定义：** 有权访问另一个函数作用域中变量的函数。

**防抖函数（正确实现）：**

```js
function debounce(fn, delay) {
  let timer = 0  // 闭包变量，持久保存在内存中
  return function (...args) {
    if (timer) clearTimeout(timer)
    timer = setTimeout(() => {   // ⚠️ 必须赋值，否则无法清除上一次定时器
      fn.apply(this, args)
    }, delay)
  }
}
```

**常见 bug：** 忘记 `timer = setTimeout(...)` 赋值，导致每次判断 `if (timer)` 都是 `0`（falsy），永远清除不了上一次定时器，防抖完全失效。

**闭包的潜在问题：**
- 变量被持续引用，无法被 GC 回收，可能造成内存泄露
- 规避方式：使用完毕后将引用置为 `null`，或在组件卸载时清除监听器

## 第三部分：浏览器渲染原理

### Q7：从输入 URL 到页面展示的完整过程

**参考答案：**

1. URL 解析
2. DNS 解析：域名 → IP 地址
3. TCP 三次握手建立连接
4. TLS 握手（HTTPS）
5. 发送 HTTP 请求
6. 服务器处理并返回响应
7. 浏览器解析 HTML → 构建 DOM 树
8. 解析 CSS → 构建 CSSOM 树
9. DOM + CSSOM → 渲染树（Render Tree，不含 `display:none` 节点）
10. Layout（布局）：计算每个可见节点的位置和大小
11. Paint（绘制）：将节点绘制成像素
12. Composite（合成）：多图层合并，GPU 输出到屏幕

---

### Q8：回流（Reflow）与重绘（Repaint）

**定义：**
- **回流**：元素的位置、大小发生变化，触发重新 Layout + Paint + Composite
- **重绘**：元素外观变化（颜色、背景），只触发 Paint + Composite，不触发 Layout

**关系：** 回流一定触发重绘，重绘不一定触发回流。

**触发回流的操作：**
- 修改宽高、margin、padding、border
- 读取 `offsetWidth`、`offsetHeight`、`scrollTop` 等布局属性（强制同步布局）
- 添加/删除 DOM 节点
- 修改字体大小

**触发重绘的操作（不触发回流）：**
- 修改 `color`、`background-color`、`visibility`、`outline`

**⚠️ transform / opacity 的性能优势：**

```
top/left 变化 → Layout → Paint → Composite（主线程，慢）
transform/opacity → 直接 Composite（合成线程/GPU，不阻塞主线程，快）
```

- `transform` 和 `opacity` 在**合成线程（Compositor Thread）** 处理，由 GPU 执行
- 跳过 Layout 和 Paint 阶段，不阻塞主线程
- 注意：是**线程**不是进程

## 第四部分：React / Vue 框架

### Q9：React 虚拟 DOM 与 Diff 算法

**虚拟 DOM：** 用 JS 对象描述真实 DOM 结构，状态变化时先在虚拟 DOM 上做 diff，再批量更新真实 DOM，减少直接操作 DOM 的开销。

**Diff 算法核心策略：**
1. **同层比较**：只比较同一层级的节点，不跨层级对比
2. **type 不同直接替换**：节点类型变了（如 div → span），直接销毁重建
3. **key 作为唯一标识**：同类型节点通过 key 判断是移动、更新还是新增/删除

**⚠️ 为什么不能用 index 作 key：**

```jsx
// 场景：列表含 input，每项 key = index
// 列表：A(0)、B(1)、C(2)，用户在 B 的 input 里输入 "hello"
// 删除 A 后，列表变为 B(0)、C(1)

// 问题：React 认为 key=0 的节点还在（实际是 B 替换了 A 的位置）
// 结果：复用了原来 A 的 DOM，"hello" 跑到了错误的输入框
```

**结论：**
- index 作 key 的根本问题是**节点复用错位**，导致带状态的子元素（input、动画、组件内部 state）状态错乱
- 这是**正确性 bug**，不只是性能问题
- 应使用唯一且稳定的业务 ID 作为 key

### Q10：useEffect 与 useLayoutEffect 的区别

| | useEffect | useLayoutEffect |
|---|---|---|
| 执行时机 | 浏览器**渲染之后**异步执行 | 浏览器**渲染之前**同步执行 |
| 是否阻塞渲染 | ❌ 不阻塞 | ✅ 会阻塞渲染 |
| 适用场景 | 数据请求、订阅、日志 | 需要在渲染前读写 DOM（避免闪烁） |

**依赖数组的三种写法：**

```js
useEffect(() => { /* 每次渲染都执行 */ })             // 不传依赖数组
useEffect(() => { /* 只在首次渲染执行 */ }, [])        // 空数组
useEffect(() => { /* count 变化时执行 */ }, [count])   // 指定依赖
```

## 第五部分：性能优化（项目实战）

### Q11：商详页性能优化 — 如何定位瓶颈并优化？

**定位瓶颈的三条链路（Chrome DevTools）：**
1. Network：查看资源加载顺序、时序（HTML、主 JS、接口请求）
2. Performance：渲染阶段分析，定位 Layout/Paint 耗时
3. 容器冷启动：Hybrid H5 的 WebView 冷启动时间（Native 侧指标）

**优化方案：**

| 方案 | 原理 | 效果 |
|------|------|------|
| 接口拆分 | 非首屏数据延迟加载 | 减少首屏阻塞 |
| 代码分包 | `defineAsyncComponent` + webpack 动态 import | 首屏 bundle 体积降低 40% |
| WebView 预渲染 | 客户端提前预热容器 + 解析 HTML | 消除冷启动耗时（~几百ms） |
| 首图缓存 | 列表页缓存图片 URL，商详页先展示再覆盖 | 消除图片白屏 |
| 图片懒加载 | 非首屏图片延迟加载 | 减少首屏网络消耗 |
| 骨架屏 | 数据未返回时展示骨架 | 改善感知加载速度 |

**关键数据：**
- 首屏时间：878ms → 169ms
- 秒开率：78% → 93.4%
- 预渲染命中率：82% → 95%

**预渲染命中率采集方式：**
- 命中定义：用户进入商详时客户端命中预热缓存，无需冷启动
- 采集方式：在命中判断处埋点，上报至线上性能平台
- 指标：命中 PV / 采样总 PV

**Vue3 懒加载组件写法（⚠️ 注意区分）：**
```js
// ✅ 正确：defineAsyncComponent + 动态 import
const MyComponent = defineAsyncComponent(() => import('./MyComponent.vue'))

// ❌ 错误混淆：defineComponent 是类型辅助，与懒加载无关
```

## 第六部分：项目深挖 — 高并发容灾

### Q12：秒杀场景前端如何处理高并发？

#### 一、流量整形（Traffic Shaping）

控制请求发出的频率、数量和优先级，把瞬时洪峰"削平"成后端能承受的平稳流量。

| 层级 | 手段 | 场景 |
|------|------|------|
| 基础层 | `debounce`（防抖） | 搜索框输入，停止输入 300-500ms 后触发 |
| 基础层 | `throttle`（节流，leading 模式） | 按钮提交，首次立即执行，冷却期内忽略后续点击 |
| 进阶层 | `AbortController` 取消 | 新请求发出时取消旧请求，防止旧响应覆盖新结果；路由切换时批量取消未完成请求 |
| 大促专项 | 请求优先级队列 | HTTP/1.1 同域名并发连接约 6 个，给请求分级，核心链路优先占用连接 |

**请求优先级分级：**
- 高优先级：下单、支付、加购
- 低优先级：埋点上报、推荐、评论
- 大促时埋点请求批量合并延迟上报，释放连接给业务请求

> ⚠️ 概念区分：`debounce` = 防抖（停止触发后执行）；`throttle` = 节流（固定频率执行）

#### 二、幂等设计（Idempotency）

保证同一操作无论执行多少次，结果和执行一次一样。前端"防重"，后端"去重"。

1. **生成唯一 requestId**：前端生成 UUID（或 timestamp + random），作为请求头 `X-Request-Id` 传递给后端
2. **按钮悲观锁**：点击后立即 `disabled + loading`，请求明确返回后才解锁（支付等强一致场景用悲观锁）
3. **超时后不立即重试，先查状态**：网络超时不代表请求未到达后端。先轮询查询订单状态，确认未创建后再携带新 requestId 重试；已创建则直接引导到结果页
4. **本地防重表**：待支付订单 id + requestId 写入 `sessionStorage`，刷新页面时先查本地表，有进行中的支付则引导到结果页
5. **区分读写幂等**：只对下单、支付、退款等写操作做幂等，查询类接口不做

#### 三、容灾兜底（Disaster Tolerance）

后端服务异常时，前端仍保障核心链路可用，不白屏不报错。

**分级降级（从低优先级开始，逐步保留核心路径）：**

| 降级步骤 | 内容 |
|---------|------|
| 第一步 | 浏览链路简化：关闭筛选动效、图片懒加载改占位图、推荐模块隐藏 |
| 第二步 | 非核心功能关闭：关闭评论、直播组件、"猜你喜欢" |
| 第三步 | 数据降级：列表页展示缓存数据 + 提示条"数据可能有延迟" |
| 最后保留 | 核心链路：下单、加购、支付全程保障，不降级 |

**配置中心动态下发开关：**
- 降级开关通过配置中心（Apollo 等）下发，无需发版，秒级生效
- 前端通过长连接（WebSocket 或 SSE，SSE 更轻量）订阅开关变更，服务端主动推送，非轮询
- 开关按模块粒度划分：`RECOMMEND_DISABLED`、`COMMENT_DISABLED`、`FILTER_DISABLED` 等

## 第七部分：项目深挖 — RAG 知识问答平台

### Q13：父子分块策略与混合检索

**父子分块（Parent-Child Chunking）：**

- 直接固定大小切块的问题：切小了条件和步骤被切散，切大了带入无关噪音
- 父子分块把"检索粒度"和"上下文粒度"分开：Child 节点检索精度高，命中后回溯 Parent 补充章节上下文
- 父块粒度：按 Markdown 标题/章节结构切分，超出范围递归按段落/列表/表格拆分
- 子块粒度：在每个父块内进一步切分，保留 **Overlap**（滑动窗口重叠内容）防止语义在边界截断

**混合检索流程：**

```
BM25 关键词召回
       ↓  (并行)
向量 kNN 召回
       ↓
  RRF 融合
       ↓
  Reranker 精排
       ↓
  阈值过滤（0.4）
       ↓
  最终候选集
```

**RRF 原理：** 丢掉原始分数只用排名，`score = 1/(C + rank)`，C=60 做平滑；两路都命中的 chunk 分数叠加，天然置信度最高。解决了 BM25 和向量分数量纲不同无法直接相加的问题。

**Embedding vs Reranker：**

| | Embedding（双塔） | Reranker（交叉编码器） |
|---|---|---|
| 编码方式 | query 和 document 分别编码 | query + document 拼接后送入模型 |
| 交互粒度 | 无 token 级交互 | 每个 token 互相 attention |
| 速度 | 可预存向量，毫秒级 | 无法预存，延迟高 |
| 适合阶段 | 召回（不漏） | 精排（不噪） |

**一句话记忆：Embedding 管召回不漏，Reranker 管精排不噪。**

### Q14：分层记忆架构与记忆污染

**三层分工：**

| 层 | 存储 | 存什么 | 作用域 |
|----|------|--------|--------|
| Redis | 热缓存 | 当前会话最近 20 条对话 | 当前会话，按 session ID 取回 |
| PostgreSQL | 事实源 | 全量历史消息、来源引用文档 | 永久可查 |
| Mem0 | 语义记忆 | 用户自陈述的事实（偏好、背景） | user 层跨会话 / session 层当前会话 |

**Mem0 两层区别：**
- user 层：跨所有会话，如"用户是财务部、喜欢简洁回答"
- session 层：只在当前会话有效，如"本次在排查某个报销问题"

**记忆污染问题与解法：**

问题场景：用户上周问差旅住宿标准，知识库回答 500/晚，若这个答案被存入长期记忆，下周制度改为 600/晚，记忆里的旧数字会污染本轮回答，模型不去检索最新文档。

三道防线：

1. **写入端**：LLM 分类器判断本轮是否写记忆，prompt 明确"知识库内容、制度条文、流程、负责人、金额一律不写成 user 记忆"
2. **注入端**：记忆注入时强制附加"以上仅作背景，制度/流程以本轮检索资料为准"
3. **数据流**：`rememberTurn` 只把用户原话喂给 Mem0，助手回答不作为记忆源，从源头断开"答案回流成记忆"

**跨会话问题处理流程：**

- 记忆检索和意图分类**并行启动**（不串行，节省延迟）
- Mem0 命中内容格式化为 System Message 注入 Agent 上下文
- 记忆只提供用户背景和风格，住宿金额等规则本轮重新检索获取

### Q15：Multi-Agent 知识库增量同步

**Git 变更 → 知识文档映射（三层机制）：**

1. **入口组件锚点**：`page.md` 里每个模块登记入口组件路径，改动文件命中哪个模块的入口组件目录，就映射到该模块文档（不硬编码一级目录，任意层级可命中）
2. **共享代码反查**：改动落在 `components/utils` 等共享目录时，派只读子 Agent grep 引用关系，命中的模块都要刷新
3. **新增/删除判定**：新目录去 init，源码删除进清理队列

映射完再做 ancestor 关系去重：模块知识文档的 `source_commit` 已包含本次变更则直接跳过，不重复生成。

**同步水位机制（Watermark）：**

水位是存在 `page.md` frontmatter 里的字段，记录"知识库已处理到哪个代码版本"。

解决三个问题：
1. **避免全量重建**：下次扫描从水位往后扫，不用全量 diff
2. **失败不丢变更**：全部失败时不推进水位，下次扫描从原起点覆盖，不被静默跳过
3. **可追溯**：每份知识对应的代码版本可查

**三个机制协作：**
- 三层映射 → 决定"哪些文档要更新"
- 水位 → 决定"扫哪个时间段的变更"
- ancestor 去重 → 决定"已经最新的跳过"

## 第八部分：框架延伸 — LangChain vs LangGraph

### Q16：LangChain 和 LangGraph 的区别？

**一句话区别：**
- **LangChain**：链式调用的工具箱，适合线性的"步骤 A → 步骤 B → 步骤 C"流程
- **LangGraph**：有状态的图执行引擎，适合有分支、循环、多 Agent 协作的复杂流程

#### LangChain 是什么

核心抽象是 **Chain**——把 LLM 调用、工具调用、Prompt 模板等步骤串成一个可执行的链。

```
用户输入 → Prompt → LLM → 输出解析 → 工具调用 → 最终输出
```

**适合场景：**
- RAG 问答（检索 → 拼 Prompt → 生成答案）
- 简单的多步 LLM 调用
- 工具链组合（运营知识问答平台的问答链路就是这种模式）

**局限：** 一旦需要"判断要不要重试"、"根据结果走不同分支"、"多 Agent 互相协作"，Chain 难以表达，只能硬编码 if/else，代码乱且难维护。

#### LangGraph 是什么

LangChain 团队在 Chain 之上做的图执行框架，将执行流程建模成**有向图**：

- **Node**：每个节点是一个执行单元（LLM 调用、工具调用、人工审核等）
- **Edge**：边定义节点间的跳转关系，可以是条件边（根据状态决定走哪个分支）
- **State**：图有一个全局共享状态，每个节点可读写，执行过程中持久保存

```
[开始]
  ↓
[意图识别] → 条件边
  ↙         ↘
[检索路由]   [闲聊回复]
  ↓
[执行检索]
  ↓
[生成答案] → 质量不够 → 循环回 [执行检索]
  ↓
[结束]
```

**适合场景：**
- 需要**循环重试**的 Agent（生成答案质量不够，自动重新检索）
- **条件分支**（根据意图走不同子流程）
- **多 Agent 协作**（主 Agent 派发子 Agent、等待结果、验收）
- **Human-in-the-loop**（某个节点需要人工确认才能继续）

#### 核心差异对比

| | LangChain | LangGraph |
|---|---|---|
| 执行模型 | 链式，线性 | 图，支持分支/循环 |
| 状态管理 | 无持久状态 | 有全局 State，节点间共享 |
| 适合场景 | 固定步骤的 RAG/工具链 | 复杂 Agent、多步决策、循环 |
| 可中断恢复 | ❌ | ✅ 可暂停等待人工介入再继续 |
| 复杂度 | 低，上手快 | 高，需要理解图的概念 |

#### 结合简历项目

| 项目 | 适合的框架 | 原因 |
|------|-----------|------|
| 运营知识问答平台 | LangChain | 检索 → 生成这条链路，Chain 抽象足够 |
| AI 全栈工作台 Multi-Agent 同步 | LangGraph | 主流程派发子 Agent、等待结果、失败重试、验收，带循环和状态 |

**面试表达：** LangChain 解决"怎么方便地调 LLM 和工具"，LangGraph 解决"怎么控制复杂 Agent 的执行流程"，两者经常配合使用。

## 第九部分：线上问题排查（滴滴场景题）

### Q17：线上活动页白屏，本地复现不了，怎么排查？

**参考答案（按排查链路分层，从快到深）：**

#### 第一步：确认影响面与定位方向

先不急着查代码，先问三个问题确定排查方向：

- **是全量白屏还是部分用户？** → 看前端监控平台的错误率/白屏率曲线，如果是部分用户，大概率是特定环境问题（低版本浏览器、特定机型、弱网）
- **什么时候开始的？** → 对应哪个版本发布，是不是某次上线引入的，看时间线和发布记录
- **白屏率集中在哪些维度？** → 设备、系统、网络、页面版本，监控平台能切出来

#### 第二步：看前端监控，拿错误堆栈

白屏最常见原因是 JS 执行报错导致渲染中断。看监控平台的 JS 错误日志，重点看：

- **Error 类型**：`TypeError: Cannot read property of undefined` 多半是接口返回结构变了或字段缺失；`SyntaxError` 是兼容性问题
- **堆栈定位到哪个文件哪行**：监控平台一般能映射回源码
- **错误聚合**：是不是同一个错误反复出现，说明是必现 bug 不是偶发

#### 第三步：排除环境与兼容性

如果监控显示集中在特定环境：

- **低版本浏览器**：可能用了 ES6+ 语法但构建没转译到位，查 babel target 配置、browserslist 范围
- **特定机型**：可能是 CSS 兼容（flex 布局老语法）或 WebView 内核 bug
- **弱网**：可能是关键资源加载失败，看资源加载成功率指标

#### 第四步：复现与定位

本地复现不了时，用这些手段：

- **Source Map 线上定位**：如果监控平台有上传 sourcemap，错误堆栈能直接映射回源码行号
- **线上抓包**：让出现问题的用户或测试在出问题时抓 network，看是不是接口超时/返回异常导致渲染崩了
- **灰度环境复现**：用和线上一致的数据、同样的 UA 和网络条件，在预发环境模拟
- **录屏回放**：如果接了类似 LogRocket、rrweb 这类会话回放，直接看用户操作和报错瞬间

#### 第五步：常见白屏根因排查清单

| 根因 | 特征 | 验证方式 |
|------|------|---------|
| JS 报错中断渲染 | 监控有 error 堆栈 | 看错误日志 |
| 接口返回异常字段 | undefined 访问报错 | 抓包看接口响应 |
| 资源加载失败（CDN/CSS） | DOM 渲染了但没样式像白屏 | 看资源加载成功率 |
| 兼容性（语法/CSS） | 集中在低版本 | 按浏览器版本看分布 |
| 容器问题（WebView 冷启动） | Hybrid 场景特有 | 看客户端侧日志 |
| 内存溢出 | 长时间停留后白屏 | 看 memory 指标 |

#### 第六步：应急处理

定位前先止血：

- 如果是某次上线引入 → 回滚到上一版本
- 如果是接口问题 → 降级到缓存数据或兜底页
- 如果是兼容性 → 配置中心下发关闭新功能开关

**追问预判：**

- **"前端监控平台具体怎么接的？"** → 上报 JS 错误用 `window.onerror` + `unhandledrejection`，资源加载失败用 `error` 事件捕获阶段监听，白屏检测用 MutationObserver 看定时内是否有有效 DOM 节点
- **"白屏检测怎么做？"** → 定时（如首屏 3 秒后）检查 `document.body` 子节点数量或关键元素是否渲染，没有就上报白屏事件，结合 performance timing 看资源加载情况

## 第十部分：实时地图场景优化（滴滴场景题）

### Q18：打车结果页地图每秒刷新司机位置，页面卡顿，怎么分析和优化？

**参考答案（先定位后优化）：**

#### 第一步：先定位卡顿原因

用 Chrome DevTools Performance 面板录制卡顿时的帧，重点看：

- **FPS 是否持续低于 60**：掉帧就是卡顿的直接证据
- **Long Task**：主线程有没有超过 50ms 的长任务阻塞渲染
- **Layout/Paint 耗时**：是不是频繁触发回流重绘

#### 第二步：按方向逐一排查

**方向一：地图频繁更新触发回流**

地图每秒刷新司机位置，如果直接改 `top/left` 移动司机图标，会触发 Layout → Paint → Composite 全流程。改用 `transform: translate(x, y)` 代替，只走 Composite，由 GPU 执行，不阻塞主线程。

**方向二：WebSocket / 轮询数据处理在主线程**

每秒收到位置数据后如果在主线程做坐标换算、插值计算，会阻塞渲染。用 Web Worker 把坐标换算、轨迹平滑插值移到后台线程，算完再 `postMessage` 给主线程更新 DOM。

**方向三：React/Vue 频繁 re-render**

每秒收到新坐标就 setState，如果司机位置 state 挂在父组件，会导致整棵子树 re-render。解法：把司机位置状态下沉到最小组件，或用 `useRef` 直接操作 DOM 节点位置，跳过 React diff。

**方向四：动画用 setInterval 而不是 requestAnimationFrame**

`setInterval(fn, 16)` 不和屏幕刷新率对齐，容易丢帧或双帧。改用 `requestAnimationFrame` 驱动动画，浏览器会在每次屏幕刷新前调用，天然 60fps 对齐。

**方向五：轨迹平滑插值**

司机位置每秒一个点，如果直接跳到新坐标会很突兀，视觉上像"瞬移"，也会触发重绘。在两个坐标点之间用线性插值（Lerp）做 60 帧平滑过渡，每帧移动一小步，视觉流畅且减少大幅度重绘。

#### 总结一句话答法

> "地图卡顿一般出在三个地方：频繁回流（用 transform 代替 top/left）、主线程计算压力大（坐标插值移到 Web Worker）、组件频繁 re-render（状态下沉或用 ref 直接操 DOM）。先 Performance 面板录一帧看 Long Task 定位是哪个方向，再针对性优化。"

**追问预判：**

- **"transform 为什么不触发回流？"** → transform 走合成线程（Compositor Thread），由 GPU 直接处理，不经过 Layout 和 Paint 阶段，不占主线程
- **"Web Worker 和主线程怎么通信？"** → `postMessage` 传数据，数据是结构化克隆（深拷贝），大数据可用 `Transferable` 对象零拷贝转移所有权
- **"requestAnimationFrame 和 setInterval(fn, 16) 有什么本质区别？"** → rAF 由浏览器调度，和屏幕刷新率对齐，页面不可见时自动暂停节省资源；setInterval 是定时器，不感知屏幕刷新，页面切后台也照跑

## 第十一部分：工程化 — Webpack vs Vite

### Q19：Webpack 和 Vite 的核心区别？大型项目迁移 Vite 有哪些风险？

**核心区别：**

Webpack 开发时会把所有模块打成 bundle 再启动，项目越大启动越慢，热更新也要重新打受影响的 bundle。

Vite 开发时不打包，直接利用浏览器原生 ESM——启动时只处理入口文件，其他模块按需请求，冷启动时间基本恒定。热更新也只更新改动的模块，不受项目规模影响。

生产构建两者都走打包（Vite 底层用 Rollup），差异主要在开发体验。

| | Webpack | Vite |
|--|--|--|
| 开发启动 | 全量打包，项目大则慢 | 按需编译，启动恒快 |
| 热更新 | 重打受影响 bundle | 只更新单模块，毫秒级 |
| 生产构建 | Webpack 自身 | Rollup |
| 生态成熟度 | 极成熟，插件多 | 成熟但部分插件缺失 |
| CommonJS 支持 | 原生支持 | 需要插件转换 |

**大型项目迁移 Vite 的主要风险：**

1. **CommonJS 依赖兼容问题**：Vite 开发环境基于 ESM，遇到只提供 CJS 格式的老包，Vite 通过 esbuild 预构建转换，但部分边界情况会报错。迁移前要扫一遍依赖。

2. **Webpack 特有配置无法直接迁移**：项目里的 Webpack loader 和 Plugin 不能直接复用，需要找 Vite 对应替代或自己写。

3. **开发和生产构建行为不一致**：Vite 开发用 esbuild，生产用 Rollup，两者对某些语法处理不同，可能出现"开发没问题、生产报错"，需要完整回归测试。

4. **代码分割策略差异**：Rollup 的分包策略默认行为与 Webpack SplitChunks 不同，迁移后包体积分布可能变化，需要重新调优。

5. **环境变量注入方式不同**：Webpack 用 `DefinePlugin` 注入，Vite 用 `import.meta.env`，代码里所有 `process.env.XXX` 要批量替换。

**一句话总结：**

> "核心差别是开发模式——Webpack 打 bundle、Vite 用原生 ESM 按需加载。迁移风险主要是 CJS 依赖兼容、Webpack 插件不能直接复用、开发生产构建行为不一致这三点，需要完整回归验证才能上。"

**追问预判：**

- **"Vite 的预构建是干什么的？"** → 把 node_modules 里的 CJS 依赖预先转成 ESM，缓存到 `.vite/deps`，开发时直接用，避免每次请求都实时转换
- **"esbuild 为什么快？"** → Go 语言实现，原生二进制，并行处理，比 JS 写的 loader 快 10-100 倍；但功能比 Babel 弱，不支持某些高级语法转换

## 第十二部分：React Hooks 深挖

### Q20：useMemo 和 useCallback 的区别？什么时候该用，什么时候不该用？

**核心区别：**

- **useMemo**：缓存计算结果（值），依赖不变时直接返回上次的值，跳过重新计算
- **useCallback**：缓存函数引用，依赖不变时返回同一个函数引用

两者本质都是**保持引用稳定**，区别只在缓存的是值还是函数。

**useCallback 真正解决的问题——引用相等性：**

父组件每次 re-render，内部定义的函数都是新引用，传给子组件的 props 变了，即使子组件用 `React.memo` 包裹，因为函数引用变了，memo 浅比较失败，子组件还是会 re-render。useCallback 让函数引用稳定，配合 memo 才能真正跳过子组件渲染。

**该用 / 不该用的判断：**

| 场景 | 该不该用 |
|------|---------|
| 传给 `React.memo` 子组件的函数 prop | ✅ 该用 useCallback |
| 传给 `React.memo` 子组件的对象/数组 prop | ✅ 该用 useMemo |
| 计算量大的派生值（大列表 filter/sort） | ✅ 该用 useMemo |
| 计算量很小的值（简单拼接、布尔判断） | ❌ 不该用，缓存本身有成本 |
| 函数只在本组件用，没传子组件 | ❌ 不该用 useCallback，没意义 |

**一句话总结：**

> "useMemo 缓存值，useCallback 缓存函数引用，两者本质都是保持引用稳定。该用的场景是：计算成本高、或要传给 memo 子组件。不该用的场景是：计算很轻、或函数只在本组件用——这时候缓存的成本反而大于收益。"

**追问预判：**

- **"依赖数组填错了会怎样？"** → 依赖少了会漏更新（用过期的闭包值），依赖多了缓存失效等于没用，用 ESLint 的 `exhaustive-deps` 规则辅助检查
- **"React.memo 是浅比较还是深比较？"** → 浅比较，只比 props 第一层，嵌套对象/数组引用变了就认为变了，所以传对象给 memo 子组件时要用 useMemo 包一层

## 第十三部分：AI 全栈辅助研发工作台深挖

### Q21：工作流编排 — 各阶段 Skill 怎么衔接的？

**面试官问法：** 你说设计了需求初始化、方案生成、代码实施、交付归档几个 Skill，它们之间怎么传递上下文？怎么保证不重复补充？

**参考答案：**

> 核心是**按需求 ID 归档**。每个需求创建时生成唯一 reqId，所有阶段产出都挂到这个 id 下：需求文档存 `requirements/{reqId}/spec.md`，实施方案存 `schemes/{reqId}/plan.md`，代码变更记录存 `changes/{reqId}/diff.md`。
>
> 下游 Skill 启动时不用重新输入背景，直接读上游归档文件。方案生成 Skill 读 spec.md，代码实施 Skill 读 spec.md + plan.md，评审归档 Skill 读三个文件做完整性校验。
>
> 这样每个阶段的输入是确定的，输出也是确定格式，Skill 之间是**文件驱动**而不是上下文传递，消除跨阶段重复补充的问题。

### Q22：知识检索 — 渐进式两级检索为什么不一次性检索所有知识？

**面试官问法：** 为什么要分前端场景库和后端领域库两级？

**参考答案：**

> 一次性检索的问题是把前端页面知识和后端接口知识混在一起，召回噪音大，而且跨端开发者真正需要的是**关联关系**——"这个页面调了哪些接口，这个接口被哪些页面用"，不是孤立的知识点。
>
> 分两级解决两个问题：
> - **前端场景库**：以页面为入口，描述页面的结构、模块、依赖关系，前端开发者先在这里定位要改的页面
> - **后端领域库**：以接口为入口，描述接口的入参出参、所属模块、调用方
>
> 方案生成阶段把两级串联：从页面下探到模块，再下探到接口和字段，生成"改 A 页面的 B 模块，要动 C 接口的 D 字段"的分服务实施方案，跨端开发者拿到的是精确的改动依据，不是一堆文档自己拼。

### Q23：Multi-Agent 同步 — 为什么并行派子 Agent 而不是顺序更新？

**面试官问法：** 增量同步时为什么要分批并行派子 Agent，主流程统一验收？

**参考答案：**

> 顺序更新的问题是**速度慢 + 单点失败拖垮全局**。一次 Git 变更可能命中十几个模块，一个 Agent 顺序更新每个模块要几分钟，十几个就是几十分钟，中间任何一个失败整个流程中断。
>
> 并行派子 Agent 的好处：
> - **速度**：十几个模块并行，总耗时约等于最慢的那个
> - **隔离**：单个子 Agent 失败不影响其他模块，主流程只重跑失败的
> - **可验收**：主流程收齐所有子 Agent 结果后统一重建索引，保证索引一致性
>
> 配合失败重试机制——单个模块失败重试 3 次仍不成功则标记失败进入人工队列，不阻塞整体同步。

---

### Q24：同步水位机制 — 全部失败时为什么不能推进水位？

**面试官问法：** 水位机制里"全部失败不推进水位"这条规则的意义是什么？

**参考答案：**

> 水位记录的是"知识库已处理到哪个代码版本"。如果推进了水位，这段变更就被**静默跳过**了，下次扫描从新水位往后扫，永远不会重试。
>
> 全部失败时不推进水位，下次扫描从原起点重新覆盖，保证失败不丢变更。只有至少部分成功时，才把已成功部分的最新版本记进水位。
>
> 这和分布式系统里 checkpoint 的思路一样——只有确认成功才推进位点，失败回退到上一个位点重试。

### Q25：三层映射 — 入口组件锚点为什么不硬编码一级目录？

**面试官问法：** 改动文件命中哪个模块，为什么用入口组件锚点而不是直接按一级目录匹配？

**参考答案：**

> 硬编码一级目录的问题是**结构一变就失效**。项目重构、模块迁移后，一级目录路径变了，映射规则全得改。
>
> 入口组件锚点的思路是：每个模块的 `page.md` 里登记该模块的入口组件路径，改动文件落在该目录下就映射到这个模块。锚点是**模块自己声明的**，和目录结构解耦，模块迁移时只更新 page.md 的声明，映射逻辑不用改。
>
> 而且任意层级可命中——不限定一级目录，二级三级模块只要有自己的 page.md 就能匹配，适配嵌套深的业务结构。
