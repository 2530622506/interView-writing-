# 学生认证流程与红包领取设计

> 简历项目：学生专区 · 独立负责前后端全栈开发

---

## 口述版本（面试开场，约 90 秒）

> 学生认证整体是一个跨端流程，横跨转转 App 和微信小程序。用户在 App 里点"去认证"，我先做四项前置检查：同人排重、查实名状态、查微信绑定、决定表单形态——已实名的只填学校信息，未实名的同页填身份证加学校一次性提交，后端统一调风控做二要素核验。通过之后生成一个 biz_token 存 Redis，App 带着这个 token 跳微信小程序。

> 小程序侧拿到 token 后先做两道防复用校验：一是反查 token 里存的 App 侧 uid 跟小程序当前登录的 uid 是否一致，防止 A 账号填表 B 账号来刷脸；二是校验前端传来的微信 openId 在该账号已绑定的 openId 集合里，防用别人的微信认证。两道都通过才让用户发起微信人脸识别。

> 微信核验通过之后写入中台学生身份系统，写入成功后异步发放红包——延保红包和裂变原始红包。发放失败不回滚认证，用三态标记记录每个红包位的领取状态，用户下次进专区页时自动触发补偿补发。

> 红包这块还有裂变助力玩法：认证完成后用户可以邀请好友助力，助力满额后发膨胀红包。防刷设计了三道：Redis Set 天然去重、风控同人交集拦截多号刷助力、邀请人同人拦截防自助力。

## Q1：说一下学生认证的整体流程设计，为什么这么设计？

**参考答案：**

认证流程分为五个阶段：

1. **进入专区页，查认证状态**
   - 调 `queryCertStatus` 接口，返回用户是否已认证、学校信息等
   - 已认证且在有效期内 → 直接展示学生信息，流程结束
   - 已认证但已毕业（入学年份 + 4 年后的 7 月 1 日起）→ 按未认证返回，引导重新认证

2. **点击"去认证"，四项前置检查**
   - 同人排重：调风控查同人 uid 列表，再批量查中台学生身份，任一有有效学生身份 → 硬拦截
   - 查实名状态：已实名则回填脱敏姓名和身份证，未实名则用户自行填写
   - 查微信绑定：未绑微信 → 引导绑定，因为后续认证依赖微信核验
   - 决定表单形态：已实名只填学校信息，未实名同页填身份证 + 学校信息

3. **提交表单，生成 biz_token 跳小程序**
   - 未实名用户：后端调风控做二要素核验（姓名 + 身份证），通过才继续
   - 生成 32 位随机 biz_token（UUID 去横线），存 Redis，TTL 120 分钟
   - biz_token 里存 App 侧 uid + 学校信息 + activityId，**不存身份证明文**
   - App 带 biz_token 跳转转转小程序

4. **小程序两道防复用校验（人脸前）**
   - 校验一：biz_token 反查 App 侧 uid == 小程序内置 uid，防跨账号复用
   - 校验二：前端传入 openId 在该 uid 已绑定 openId 集合中，防用别人的微信认证
   - 两道均通过 → 发起微信人脸识别

5. **微信核验 + 写入中台**
   - 调微信 `quickcheckstudentidentity` 核验学生身份
   - 核验通过 → 写入中台（zzuser 扩展字段）
   - 写入成功 → DEL biz_token，认证完成，发放红包

**为什么这么设计：**

- 实名认证和学生认证合并为一步，减少跳转，路径最短
- 两道防复用校验前置到人脸前，不让用户白做人脸，也不消耗微信日查询配额
- 身份数据存中台而不是自建表，生命周期管理（到期失效、提醒）由中台承担，B2C 侧零开发

## Q2：biz_token 是什么，为什么要设计它，为什么用随机串而不是加密 uid？

**参考答案：**

**是什么：**

biz_token 是一个 32 位随机串（UUID 去横线），存在 Redis 里，TTL 120 分钟，用完即删。它承载三件事：
1. App 侧 uid（供小程序侧校验两端账号是否一致）
2. 表单数据（学校、学历、入学年份——需要跨端从 App 传到小程序）
3. activityId（认证成功后用来查魔方配置发红包）

**为什么需要它：**

认证流程横跨 App 和微信小程序两个端，App 端提交表单后需要把数据"安全地"带给小程序侧，同时还要让小程序能验证"操作的是同一个账号"。直接在跳转链接里带参数不安全（可被篡改），biz_token 是服务端存储、端侧只传 token 的安全方案。

**为什么是随机串而不是加密 uid：**

- 加密 uid 只解决"明文不暴露"，不解决"被复用"——同一 uid 可能每次加密出相同密文，攻击者收集到密文就能重放
- 要达到同等安全需要叠加签名 + 时间戳 + 一次性校验，代码量反而更大
- 随机串天然不可推导（UUID 底层用 SecureRandom），天然防重放（短 TTL + 用后即删），实现更简单

## Q3：防跨账号复用有几道防线，分别防什么？

**参考答案：**

共三道防线：

**防线一：两侧 uid 一致（场景四）**

- 位置：人脸认证前，小程序侧校验
- 原理：biz_token 里存了 App 提交时的 uid，小程序反查 biz_token，比对小程序内置 uid
- 防的是：A 账号填表，B 账号来做人脸，认证结果被写到 B 账号
- 失败提示：「转转 App 与转转小程序登录的账号需保持一致」

**防线二：微信 openId 归属（场景四）**

- 位置：人脸认证前，小程序侧校验
- 原理：前端传入的 openId 必须在该 uid 已绑定的 openId 集合中（Set 包含判断）
- 防的是：用别人绑定的微信做人脸认证
- 失败提示：「该微信不是本账号绑定的微信」

**防线三：同人排重（场景二、三）**

- 位置：点击"去认证"前置检查 + 提交表单
- 原理：调风控 `getSameUserZzAndZlj` 查同一自然人名下全部 uid，再批量查中台学生身份，任一有有效学生身份 → 硬拦截
- 防的是：同一个人多个账号各拿一份学生权益
- 失败提示：「您已认证过学生身份」
- 已知残留：先查后写，极端并发下同一人两账号同时提交可能双双通过，产品知情接受

## Q4：认证回调（certCallback）是怎么保证幂等的？

**参考答案：**

有三层保障：

1. **biz_token 一次性**
   - 写入中台成功后立即 `DEL biz_token`
   - 同一个 biz_token 第二次调用时 Redis 查不到 → 返回 TOKEN_EXPIRED，拦住重复请求

2. **微信 wx_studentcheck_code 作幂等键**
   - 该 code 是微信侧一次性的，有 2 小时有效期
   - 中台写入时以此为幂等判断，重复传同一 code 不会产生第二条学生身份记录

3. **zzuser 写入前先查存量 extendId**
   - 写入前先调 `getUserStudentInfosByUids` 查该 uid 是否已有学生扩展记录
   - 有则走 `updateUserExtendInfo`（带 extendId 更新），无则走 `addUserExtendInfo`
   - 防止重复认证产生多条扩展记录

## Q5：认证成功后发红包，发失败了怎么办？为什么不用事务回滚？

**参考答案：**

**发失败不回滚认证，用补偿机制代替：**

- 认证写中台成功后发红包，发失败只记录 error 日志 + 写 Redis 领取记录（receiveStatus=1 未领取），认证仍返回成功
- 用户下次进专区页触发 `queryCertStatus`，后端检测到已认证 + 有应发未发的红包 → 自动补偿发放
- 补偿按红包位（redPacketType）判定，receiveStatus=1 重试，receiveStatus=3（库存耗尽）终态不再补

**为什么不用事务回滚：**

1. 认证写中台和发红包是两个不同的微服务调用，分布式事务成本高（2PC 性能差，Saga 实现复杂）
2. 红包是认证的附属权益，因为红包服务抖动回滚认证，用户体验反而更差
3. 最终一致性足够：用补偿机制保证"用户迟早能拿到红包"，不需要强一致

## Q6：红包领取的防重复发放是怎么做的？有几层？

**参考答案：**

**三层防重，依次递进：**

**第一层：Redis 本地记录（最快）**

- Key：`student_cert:red:{activityId}:{uid}`
- 发放前读取领取记录，按红包位（redPacketType）查 receiveStatus：
  - receiveStatus=2（已领取）→ 跳过
  - receiveStatus=3（库存耗尽，终态）→ 跳过，不再重试

**第二层：调 zzactivity 查远端状态（兜底）**

- 调 `queryRedByPlanId` 查 `redEnvelopUserStatus`，1-5 任一值即已领取 → 跳过
- 防 Redis 丢失但实际已领取的场景

**第三层：zzactivity receive 接口自身领取上限**

- zzactivity 侧对同一 uid 同一计划有领取次数上限
- 即使前两层都没拦住，这里也会拒绝第二次发放

**已知盲区：**

跨活动换 planId 时，第二层查的是新 planId，查不到旧计划的领取记录，可能重复发。现有设计靠 TTL（活动结束 + 10 天）覆盖活动周期内不过期来规避。更完善的方案是把领取记录落 MySQL，用 `(uid, activity_id, red_type)` 唯一索引兜底。

## Q7：助力防刷是怎么设计的？

**参考答案：**

**三道防刷，全部收敛在助力侧：**

**第一道：Redis Set 天然去重**

- 助力集合 Key：`student_cert:assist:{activityId}:{邀请人uid}`，类型 Set
- 同一助力人 uid `SADD` 天然去重，重复助力不计入

**第二道：同人交集拦截**

- 助力时调风控 `getSameUserZzAndZlj` 查助力人的同人 uid 列表
- 同人 uid 集合与助力集合求交集，任一命中 → 拒绝
- 防「同一自然人多账号刷助力」
- 提示：「您已完成助力，不可重复助力」

**第三道：邀请人同人拦截（防自助力）**

- 额外判断邀请人 uid 是否在助力人的同人集合中
- 主号发起、小号来助力（变相自助力）→ 拒绝
- 提示：「不能为自己的关联账号助力」

**已知残留：**

风控接口异常时降级放行（宁放一个不挡合法用户），降级窗口内多号可穿透，概率低，产品知情接受。

## Q8：助力满额后膨胀红包只发一次，怎么保证的？

**参考答案：**

**两层保障：**

**第一层：领取记录终态判断**

- 发放前读 `student_cert:red:{activityId}:{inviterUid}` 中膨胀位（redPacketType=3）的 receiveStatus
- receiveStatus=2（已领取）或 3（库存耗尽）→ 终态，直接跳过，不再调 receive

**第二层：zzactivity 领取上限兜底**

- 即使并发下两个助力人同时把人数推到满额，各自触发一次发放
- zzactivity receive 接口有同一 uid 同一计划的领取次数约束，第二次会被拒绝

**三个触发点统一收口：**

- `assistForInviter` 满额时（主路径）
- `queryCertStatus` 进页补偿时（开关开启态）
- `queryRedPacketContent` 补发时（开关关闭态）

三处都经过 `grantInflatedRedPacket` 同一个方法，判重逻辑写在这一个地方，不会有遗漏。
