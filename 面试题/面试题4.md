1. 前端转后端，最大的认知转变是什么？请结合一个具体例子说明
   参考答案：
   最大的转变不是"学会写Java语法"，而是建立两个全局视角：
   ● "数据如何在系统中流转"的全局视角：前端调的一个API，背后可能经过BFF → 核心域 → 多个下游服务，出问题要顺链路找，不能只盯着前端报错
   ● "不同场景用不同方案"的工程判断力：选型顺序是"业务语义 → 一致性要求 → 失败模式 → 性能"，而不是先决定用某个中间件再找理由
   具体例子——最容易踩的坑：
   看到Java方法调用，就把它当成本地函数。实际上SCF调用会经过网络、序列化、注册中心和下游实例，任何一层都可能超时或失败。前端Promise失败可以catch兜底，后端RPC失败要考虑：超时预算怎么分配、异常怎么传播、上下文怎么传递、要不要重试、重试会不会放大流量。
   后端必须守住的四件事：数据归属、业务不变量、失败可恢复、接口兼容。
1. 公司六层微服务架构是怎样的？四条架构红线是什么？为什么要这么设计？
   参考答案：
   六层架构（从上到下，调用只能向下）：
1. 用户层：用户、运营人员、第三方系统
1. 接入层：leaseerpweb、转转统一网关，负责HTTP接入和路由
1. 聚合编排层：leaseplatform、finance_open
1. 业务领域服务：订单、商城、风控、仓储、催收、商户等
1. 基础服务层：finance_middle、finance_depot等通用能力
1. 中间件层：MySQL、ES、Redis、ZZMQ、Apollo
   四条架构红线：
1. 调用只能向下：禁止反向依赖或为了方便绕层调用
1. 领域服务不得横向调用：跨领域协作必须经过leaseplatform编排
1. leaseplatform只做编排：不沉淀单领域业务、不持有业务数据、禁止直连DB/ES/Redis
1. 数据由所属领域负责：其他服务通过contract暴露的RPC能力访问，不能直接读写对方数据库
   为什么这么设计：微服务拆分后最容易失控的就是"领域边界被打破"——A领域直接读B领域的表，改表结构就要同时改两个服务。红线保证每个领域的数据自治，改表只需要动一个服务。

1. 为什么后端要用线程池？为什么不能用Executors默认实现？
   参考答案：
   为什么用线程池：
   ● 控制并发数：防止无限创建线程把机器打挂
   ● 复用线程：避免频繁创建销毁线程的开销
   ● 统一管理：监控、调参、熔断都需要
   为什么不能用Executors.newFixedThreadPool：
   它用的是无界队列LinkedBlockingQueue，请求堆积会无限长，最终OOM。所以卖场规范是用HawkeyeBootstrap显式声明core/max/queueSize。
   线程池七大参数（必须背下来）：
   参数 含义与调优
   corePoolSize 核心线程数，常年保持。卖场预检查组设8
   maximumPoolSize 最大线程数，队列满后才扩到这个数。设32
   keepAliveTime 非核心线程空闲多久回收
   workQueue 任务队列。queueSize=200，队列满了才扩max
   threadFactory 线程工厂，给线程起有意义的名字，方便Arthas排查
   handler 拒绝策略。队列满+线程达max后怎么办

@Service
public class AggregateService {

    @Resource(name = "aggPool")
    private MonitorThreadPool aggPool;

    public AggregateResp aggregate(Long uid) {
        // 两个下游无依赖，并发查
        CompletableFuture<UserInfo> userFuture = CompletableFuture.supplyAsync(
                () -> userClient.getUser(uid), aggPool);

        CompletableFuture<List<OrderSummary>> orderFuture = CompletableFuture.supplyAsync(
                () -> orderClient.listRecentOrder(uid), aggPool);

            CompletableFuture.allOf(userFuture, orderFuture)
                    .get(500, TimeUnit.MILLISECONDS);
        } catch (TimeoutException e) {
            log.warn("聚合超时, uid={}", uid);
            // 超时降级：返回空或缓存数据
        }

        AggregateResp resp = new AggregateResp();
        resp.setUser(userFuture.getNow(new UserInfo())); // 超时给默认值
        resp.setOrders(orderFuture.getNow(Collections.emptyList()));
        return resp;
    }

}

参考答案：

1. 对索引列做函数操作：WHERE DATE(create_time) = '2026-01-01' → 改成create_time >= '2026-01-01' AND create_time < '2026-01-02'
2. 隐式类型转换：字符串字段phone用数字查询WHERE phone = 13800138000
3. 违反最左前缀原则：联合索引(a,b,c)，查询条件没有a
4. LIKE以通配符开头：WHERE name LIKE '%张'
5. OR连接的条件中有一个没索引：整体索引失效
6. 小表全表扫描比索引更快时，优化器会放弃索引
7. 深分页问题怎么解决？为什么会有深分页问题？
   问题本质：LIMIT 100000, 10会扫描100010行再丢弃前10万行，越翻越慢，因为MySQL要把前面10万行都读出来再扔掉。
   解决方案：
8. 游标分页（推荐）：基于上一页最后一条的id/时间戳
   -- 传统分页（慢）
   SELECT \* FROM product ORDER BY id LIMIT 100000, 10;

-- 游标分页（快）
SELECT \* FROM product WHERE id > last_id ORDER BY id LIMIT 10; 2. 延迟关联：先查索引页拿到id，再回表查完整数据3. ES代替MySQL：深分页场景用ES，性能更好
注意：排序必须稳定（加唯一字段兜底），否则翻页会漏数据/重复数据。14. Spring事务什么时候会失效？

    四、Redis缓存
12. 缓存和数据库一致性怎么保证？为什么是删缓存而不是更新缓存？
    参考答案：Cache Aside模式
    读路径：先查Redis，命中就返回；miss就查MySQL，拿到后写回Redis并设TTL
    写路径：先更新MySQL，再删除Redis缓存
    为什么是删缓存而不是更新缓存：
    ● 避免并发更新导致旧值覆盖：两个写请求并发，后写DB的先更新缓存，先写DB的后更新缓存，缓存就旧了
    ● 缓存构建成本高：缓存可能是多表join聚合的结果，每次写都更新代价大
    ● 懒加载原则：什么时候读什么时候再重建缓存
    并发写问题——延时双删：
13. 更新数据库
14. 删除缓存
15. sleep一小段时间（比如几百ms）
16. 再删一次缓存
    最终一致性，不追求强一致——业务上能接受短暂不一致，必设TTL作为兜底。
17. 缓存穿透、击穿、雪崩分别是什么？怎么解决？
    问题 现象 解决方案
    穿透 查询不存在的数据，缓存永远miss，请求全打到DB 缓存空值（设短TTL）、布隆过滤器拦截
    击穿 某个热点key过期瞬间，大量并发请求同时打DB 热点key加互斥锁重建、热点key不过期（后台异步刷新）
    雪崩 大量key同时过期，或Redis节点宕机，DB瞬时压力暴增 TTL加随机抖动（如300s±60s）、集群高可用、熔断降级
    真实案例：某个商品详情缓存key过期瞬间DB QPS飙升 → Grafana看Redis命中率和DB QPS时间点吻合 → 解决：热点key加互斥锁重建 + TTL加随机抖动。
18. 分布式锁怎么实现？请给出Redisson标准模板代码
    RLock lock = redissonClient.getLock(lockKey);
    boolean locked = false;

try {
locked = lock.tryLock(3, TimeUnit.SECONDS);
if (!locked) {
// 没拿到锁，快速失败或返回降级
return;
}

    // 只保留必须串行的短逻辑
    handleBusiness();

} catch (InterruptedException e) {
Thread.currentThread().interrupt();
throw new FinanceBizException("获取分布式锁被中断");
} finally {
if (locked && lock.isHeldByCurrentThread()) {
lock.unlock();
}
}
关键点（面试必答）：

1. locked只在当前线程确实获取锁后为true
2. isHeldByCurrentThread()避免释放其他线程后来获得的锁
3. 捕获InterruptedException后恢复中断标记
4. 获取和释放在同一线程完成
5. 临界区避免慢RPC、大文件处理和长事务——锁粒度越小越好
   注意：分布式锁只降低并发冲突，最终正确性仍依赖唯一键、条件更新、状态机。能用DB唯一索引解决的优先用更简单方案。

7. MQ怎么保证消息不丢？生产端、Broker、消费端各做什么？
   三段式保障：
8. 生产端：事务消息/确认机制，确保消息成功发到Broker，失败重试
9. Broker端：消息持久化到磁盘，主从复制
10. 消费端：手动ack，处理成功后再确认；失败重试，超过次数进死信队列

    适用场景 不适用场景
    解耦：订单服务不用直接调库存服务 需要同步拿结果的场景（用SCF RPC）
    削峰填谷：秒杀流量先入MQ再慢慢消费 要求exactly-once精确一次（MQ默认至少一次，需自己做幂等）
    延迟处理：注册后7天发提醒 用MQ当数据库查数据
    最终一致性：DB操作后发消息同步ES、清缓存 强一致要求的场景（必须用事务）
    六、分布式与微服务
16. 接口幂等怎么做？为什么发放类接口必须做幂等？
    核心思路：唯一业务ID + 状态标记
    三层防护：
17. Redis层：发放前先查Redis领取状态，已领取直接返回；发放成功立即写回Redis
18. DB唯一索引层：数据库层面兜底，唯一键冲突就说明重复了
19. 状态机层：红包有明确状态流转（未领取→已领取→已使用），只能从特定状态往下走
    为什么必须做：前端重试、用户重复点击、MQ重试、网络重发都可能导致重复请求，红包发两次就是资损。
    学生认证助力案例：Redis Set结构，key=活动ID+邀请人ID，value=助力人uid，Set自动去重，人数直接size()拿，不单独维护计数字段。
20. SCF RPC调用和本地方法调用有什么区别？
    本质区别：RPC经过网络、序列化、注册中心、下游实例，任何一层都可能超时或失败。不能把RPC当成本地方法调用。
    必须考虑的四件事：
21. 超时预算：整个请求的超时怎么分配给每个下游，生产环境默认600ms
22. 异常传播：下游超时/报错怎么处理，要不要降级返回默认值
23. 上下文传递：traceId、用户信息怎么透传
24. 熔断：下游异常时熔断，防止级联故障（Hystrix）
    命名规范踩坑：IService / Service，实现类不要加Impl后缀，会踩scfProxyFactoryUtil.create的坑。
25. 发版顺序为什么是DB → contract → service → 上层 → 前端？
    核心原则：依赖在前的先发，向后兼容是底线。
26. 先改DB表结构（加字段、加索引）——老代码能兼容新表结构
27. 再发contract接口定义——新接口定义先发，老实现还在
28. 再发service实现——新实现上线，老调用方不受影响
29. 再发上层编排层
30. 最后发前端
    为什么不能反过来：如果先发上层再发下层，新代码调旧接口，会报接口不存在，直接线上故障。
    向后兼容底线：API只加不删，新字段给默认值，永远考虑老客户端/老数据。
31. CAP定理和BASE理论怎么理解？公司里怎么取舍？
    CAP：一致性（Consistency）、可用性（Availability）、分区容错性（Partition tolerance）三者不可兼得。网络分区必然存在，所以实际是在C和A之间取舍。
    ● 注册中心、配置中心偏CP（保证一致）
    ● 缓存、CDN偏AP（保证可用，短暂不一致可接受）
    BASE：Basically Available（基本可用）、Soft state（软状态）、Eventually consistent（最终一致）。ZZMQ异步解耦就是最终一致性的典型。
32. 限流、熔断、降级分别是什么？公司里怎么实现？
    概念 解决什么问题 卖场实现
    限流 控制请求量，防打垮自己 Sentinel / 限流器
    熔断 下游持续失败，直接断开调用，防级联 Avengers Hystrix
    降级 非核心功能出问题时返回兜底数据 缓存兜底、默认值、静态页
    商列渲染是典型降级场景：某个下游商品卡片接口挂了，不能整个商列白屏，要返回骨架屏/缓存数据/默认卡片，核心流（商品图、价格）不能丢。
    七、性能优化与线上排查
33. 接口突然变慢，你怎么排查？请说完整思路
    完整排查思路（从外到内）：
34. Grafana看接口耗时曲线：确认是哪个接口慢、什么时候开始的、突增还是渐变
35. ZZAPM看链路追踪：定位到具体哪个下游调用耗时高——商列慢可能是10个下游里某一个拖的
36. 看那个下游的日志：找慢SQL、慢RPC、GC停顿
37. 数据库排查：Zeye看慢查询日志，EXPLAIN分析执行计划
38. 缓存排查：看Redis命中率，是不是缓存失效了
39. 线程池排查：Hawkeye看是不是线程池满了、队列堆积了
    核心原则：慢SQL要靠ZZAPM链路定位到具体下游，不能只看自己服务日志。
40. 性能优化从哪些层面入手？
    层面 优化手段
    接口耗时 并发编排（Hulk/Avenger）、减少下游调用次数、加缓存、慢SQL优化
    数据库 加索引、避免SELECT \*、深分页改游标、读写分离、分库分表
    缓存 热点数据缓存、Cache Aside、TTL随机防雪崩、本地缓存兜热点
    并发 合理设置线程池参数、异步非阻塞、CompletableFuture
    资源 连接池大小、避免大对象、及时释放、pageSize限制
41. JVM常见OOM原因？卖场里最常见的是哪种？
    常见OOM原因：
    ● 堆OOM：一次查太多数据（pageSize不限制）、缓存无限增长、大对象
    ● 元空间OOM：类加载过多（动态生成CGLIB代理）
    ● 直接内存OOM：Netty/堆外内存没释放
    卖场里最常见的是"一次select了十万行"导致堆OOM——所以pageSize必须限制上限，这也是为什么接口规范里强制要求pageSize限制。
    八、业务场景设计题
42. 设计一个红包发放接口，完整链路怎么设计？
    完整链路（结合学生认证红包案例）：
43. 前端限流：按钮置灰，防止用户重复点击
44. 网关层限流：按uid/IP限流
45. 预检查并发组：用Ultron并发调用——查同人uid（风控）、查用户状态、查已有学生身份、查实名信息、查绑定openId。有依赖串行，无依赖并行
46. Redis预检查幂等：发之前先查Redis领取状态，已领取直接返回
47. Redis预减库存：库存扣减在Redis做，不直接打DB
48. MQ异步落库：扣减成功后发ZZMQ消息，DB异步写红包记录
49. 发放成功写回Redis：立即更新领取状态，防止重复发
50. 配置读取：红包到期时间、活动开关从Apollo/魔方读，不硬编码
51. 日志埋点：所有操作带uid、活动ID、红包ID，关键日志加K=S标识给数仓统计
    安全要求：姓名/身份证不落库、不记日志、不入Redis。
52. 商列渲染接口聚合了10+下游查询，怎么设计才能快？
    前端最容易犯的错：写成串行await——后端P99会慢到不可接受。
    正确做法：
53. 用Hulk做轻量并发调用：无依赖的下游全部并发
    ConcurrentStarter.cmd("商列聚合")
    .maxTimeout(500)
    .executor(商列线程池)
    .addTask(() -> 商品服务.getProductList())
    .addTask(() -> 价格服务.getPriceList())
    .addTask(() -> 标签服务.getTagList())
    .sync(); // 统一等待所有任务完成
54. 复杂场景用Ultron：一个下游一个Handler，无依赖并行，有依赖串行
55. 多级缓存：热点商品数据走Redis，本地缓存兜更热点的key
56. 整体超时预算：给每个下游设合理超时，超过就降级返回默认值，不能一个慢下游拖垮整个接口
57. 降级策略：某个下游挂了，返回缓存数据或默认卡片，不能整个商列白屏
58. 上线前架构自检清单有哪些项？
    ● 能明确说出数据归属的领域服务
    ● 单领域请求没有无意义绕leaseplatform
    ● 跨领域请求没有让领域服务互相横调
    ● leaseplatform没有新增DB/ES/Redis直连
    ● facade/service/dao/mapper职责没混在一起
    ● 对外contract没泄露数据库实体或service实现类型
    ● 接口幂等、超时、降级已考虑
    ● 缓存设了TTL、没滥用缓存掩盖性能问题
    ● 线程池用Hawkeye构建、没自己new
