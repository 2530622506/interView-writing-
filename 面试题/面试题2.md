转转后端面试题（结合公司实际技术栈）

一、架构与分层
Q1：转转的后端服务为什么要分 contract 和 service 两个模块？
参考答案：
转转每个 Java 服务都分 contract 和 service 两个模块：
● contract：对外 API 契约——定义 Facade 接口、Request/Response DTO，发布到私有 Maven 仓库。下游服务依赖这个 jar 包就能调你的接口，不用看你的代码。
● service：业务实现层——真正写业务逻辑、操作数据库的地方。
为什么这么分：

1. 解耦：下游只依赖 contract，不依赖你的实现代码，你内部怎么改都行，只要接口不变
2. 版本管理：contract 发版本，下游升不升级自己决定，不会强制升级
3. 安全：实现层的代码、数据库表结构，下游根本看不到
   分层规范：service 内部还要再分——facade → service → dao → mapper，不能跨层直接调。

Q2：转转的六层架构是什么？为什么领域服务之间不能直接调用？
参考答案：
转转后端是六层架构：

1. 用户层：App、小程序、PC
2. 网关层：转转统一网关 zzGateWay——HTTP 转 RPC、鉴权、反爬
3. 业务逻辑层：各业务域的逻辑服务（订单、商品、金融等）
4. 基础服务层：用户中心、商品中心等中台基础服务
5. 存储层：MySQL、Redis、ES、TiDB
6. 基础设施层：注册中心、配置中心、MQ 平台
   为什么领域服务之间不能横向调用：
   因为如果 A 服务直接调 B 服务、B 服务又调 C 服务，最后就会变成"循环依赖、牵一发动全身"的网状结构。
   转转的做法是——跨领域的流程统一由编排层（比如 leaseplatform）来做，领域服务之间不直接依赖。
   这就保证了：
7. 调用方向单一：只能从上往下，不会出现循环依赖
8. 领域自治：每个领域自己管自己的数据，别人不能直接读写你的库
9. 好维护：改一个领域，不会影响到一堆其他服务

二、中间件与工具
Q3：转转的 RPC 框架 ZZSCF 是什么？和 Dubbo 有什么区别？
参考答案：
ZZSCF 是转转自研的 RPC 框架，服务之间调用都走它，不是走 HTTP。
它解决什么问题：

1. 服务注册与发现：服务启动了就注册到注册中心，调用方不用写死 IP
2. 负载均衡：一个服务有多个实例，自动挑一个调
3. 超时控制：调用超时了就返回，不会一直等着
4. 限流降级：下游挂了，自动降级，不拖垮自己
   和 Dubbo 的思路差不多——都是 RPC 框架，只是转转自己实现了一套，方便和内部的监控、配置、部署平台打通。
   开发上的特点：
   ● 接口命名遵循 IService / Service，实现类不要加 Impl 后缀（会踩坑）
   ● 通过 scf-spring.xml 配置下游服务引用

Q4：转转的 MQ 用的是什么？生产和消费要注意什么？
参考答案：
转转用的是 ZZMQ，底层是 RocketMQ，做了一层封装。
MQ 解决什么问题：

1. 异步解耦：下单之后要发短信、发积分、加优惠券——不用同步一个个等，扔给 MQ 异步处理
2. 削峰填谷：大促的时候请求量突然上来，先放 MQ 里，消费者慢慢处理
3. 最终一致性：分布式事务太复杂，用 MQ 保证数据最终一致
   生产和消费要注意：
   转转内部的规范是：生产和消费都要在 ZZMQ 平台上注册，不是自己瞎用。
   问题 怎么解决
   消息重复消费 消费者要做幂等——用业务唯一 ID 判断有没有处理过
   消息丢了 生产端用事务消息，确保发出去了才算成功
   消费堆积 加消费者实例、监控堆积量

Q5：转转的分布式锁 zzlock 是什么？什么时候用？
参考答案：
转转的分布式锁叫 zzlock，底层是基于 etcd 实现的（强一致），另外也有 Redis 版本的（高性能）。
为什么需要分布式锁：
单机的时候用进程内的锁就行，但如果服务部署了多台机器，进程内的锁就不管用了——你锁住了这台机器的，另一台机器照样能操作。
典型场景：

1. 定时任务：多个实例都在跑，如果不加锁，同一个任务会被执行 N 遍
2. 库存扣减：防止并发扣超
3. 防止重复提交：同一个操作只能执行一次
   etcd 版本 vs Redis 版本：
   ● etcd：强一致，但性能稍差
   ● Redis：性能好，但极端情况可能有锁丢失的问题
   转转内部推荐：强一致要求高的用 etcd 版本（zzlock），一般场景用 Redis 版本。

三、数据库与缓存
Q6：转转的数据库为什么要分 MySQL 和 TiDB？分别用在什么场景？
参考答案：
转转同时用了 MySQL 和 TiDB：
为什么要有 TiDB：
MySQL 单表数据量太大了（比如几千万、上亿行），查询就会变慢，分库分表又很麻烦。
TiDB 的好处是——不用分库分表，SQL 语法和 MySQL 一样，业务代码不用改，数据量大了自动扩。
读多写少、大表查询的场景，转转一般会推荐用 TiDB。
另外还有 ES（Elasticsearch）——做全文搜索、复杂条件检索的场景，MySQL 查不动了就上 ES。
数据库 特点 适用场景
MySQL 成熟、性能好、生态完善 核心业务、数据量适中的表
TiDB 分布式、能水平扩展、兼容 MySQL 协议 数据量大、需要分库分表的场景

Q7：转转的缓存为什么同时用了 Redis Cluster 和 Tendis？
参考答案：
转转的缓存体系：
● Redis Cluster：纯内存，性能最好，放热点数据
● Tendis：冷热分离的大数据场景——热数据在内存，冷数据落盘，省内存成本
为什么要有 Tendis：
Redis 全放内存太贵了——有些数据访问频率不高，但又要缓存（比如大对象、历史数据），全放内存成本太高。
Tendis 的思路是：热数据在内存里，冷数据自动落到磁盘上，性能差不多，但成本低很多。
使用原则：

1. 热点数据（用户信息、商品详情）→ Redis Cluster
2. 大 value、访问频率不高的数据 → Tendis
3. 旧的 Codis 已经废弃了，在往 Redis Cluster 迁

四、工程与运维
Q8：转转的配置中心 Apollo 是干什么的？为什么不用写在配置文件里？
参考答案：
Apollo 是转转的配置中心——所有动态配置都放在 Apollo 上，不用写在代码的配置文件里。
为什么要用配置中心：
典型用法：

1. 功能开关：新功能上线先灰度，开 1% 流量，没问题再全量
2. 限流参数：接口限流阈值，动态调整
3. 降级开关：下游挂了，直接开关一关，走降级逻辑
   转转每个服务都有自己的 namespace，配置是隔离的，不会串。
   场景 写在配置文件里 放在 Apollo 上
   改一个开关 改代码、重新打包、重新发布 页面上改一下，秒级生效
   灰度发布 要发版才能切流量 按比例灰度，随时调
   不同环境不同配置 每个环境改一遍 按环境隔离，自动下发

Q9：线上出问题了，你一般怎么排查？（结合转转的工具链）
参考答案：
转转有一整套线上排查的工具，我一般按这个顺序：

1. 看告警：Prometheus + Grafana 监控——CPU、内存、接口耗时、报错率，哪个指标异常先看哪个
2. 看日志：log.zhuanspirit.com——搜报错堆栈，看是哪行代码挂了
3. 看链路：ZZAPM 全链路追踪——一个请求从网关到各个服务，哪一步慢、哪一步报错，一目了然
4. 用 Arthas 在线诊断：不用重启服务，直接在线看方法调用、看参数、看线程栈
5. 查数据库：iDB 平台——看慢查询、看表数据对不对
   结合实际：
   我之前写红包接口的时候，就遇到过并发超发的问题——通过日志定位到是并发扣减没有加锁，后来用 zzlock 分布式锁解决了。
   核心思路：先看监控发现问题，再用日志定位原因，最后用链路追踪看完整调用链。

五、AI 全栈方向
Q10：如果让你把 AI 能力做到后端服务里，你会怎么设计？
参考答案：
结合转转的 AI 工作台（zzb2c-harness）的经验，我会这么做：

1. 工具层：把后端的能力（查数据库、调 RPC、发 MQ）封装成 AI 能调用的工具（Tool）
2. 记忆层：把内部文档、接口规范喂给向量数据库，AI 能直接检索
3. 运行时：用 Spring Boot 做 Agent 的运行时，管理会话和生命周期
4. 可观测性：接 Prometheus + Grafana，看 AI 调用了哪些工具、花了多久、成功率多少
5. 安全与权限：AI 调接口要走权限校验，不能随便查用户数据
   一句话总结：Agent = 大模型 + 工程体系（Harness）。大模型负责推理，工程体系负责把能力落地、管好。
