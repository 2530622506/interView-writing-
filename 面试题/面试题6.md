# 前端基础面试题

## 1. BFC（块级格式化上下文）

BFC 是 CSS 视觉渲染里的一个独立布局环境。核心规则：**BFC 内部的元素按块级规则排版，且内部布局不影响外部，外部也不影响内部。**

### 触发条件（任一即可）

- `overflow: hidden / auto / scroll`（非 `visible`）
- `display: flow-root`（现代写法，无副作用，推荐）
- `display: flex / inline-flex / grid / inline-grid`
- `position: absolute / fixed`
- `float` 非 `none`
- 根元素 `<html>`

### 三个关键特性

1. **内部 Box 垂直排列**：BFC 内的块级盒子从上到下依次放置。
2. **margin 不与外部折叠**：BFC 内外的垂直 margin 不会合并，用于解决外边距塌陷。
3. **BFC 不与 float 元素重叠**：BFC 区域会收缩避让浮动元素，用于两栏自适应布局。

### 常见应用

- **清除浮动**：父元素建 BFC（`overflow: hidden`），浮动子元素被算进父元素高度。
- **阻止 margin 塌陷**：相邻块级元素垂直 margin 会合并，给其中一个套 BFC 容器隔开。
- **两栏布局**：左侧 float，右侧 `display: flow-root`，右侧自动避开 float 区域。

> 现代实践首选 `display: flow-root`，`overflow: hidden` 有裁剪副作用。

## 2. 宏任务（MacroTask）与微任务（MicroTask）

### 事件循环核心模型

```
取一个宏任务执行
  → 执行完后，清空所有微任务队列（包括微任务里新产生的微任务）
  → 浏览器渲染（如果需要）
  → 取下一个宏任务 → 循环...
```

**微任务在当前宏任务结束后、下一个宏任务开始前，全部清空。**

### 宏任务来源

| 来源 | 例子 |
|------|------|
| 脚本整体 | `<script>` 标签里的代码 |
| 定时器 | `setTimeout`、`setInterval` |
| I/O 回调 | Node.js 文件读写、网络 |
| UI 渲染事件 | `requestAnimationFrame` |
| 用户交互事件 | `click`、`input` |
| `setImmediate` | Node.js 专属 |
| `MessageChannel` | postMessage 通信 |

### 微任务来源

| 来源 | 例子 |
|------|------|
| Promise | `.then()`、`.catch()`、`.finally()` |
| `queueMicrotask()` | 直接入微任务队列 |
| `MutationObserver` | 浏览器 DOM 变动监听 |
| `async/await` | `await` 后面的代码 = `.then()` 回调 |
| `process.nextTick` | Node.js 专属，优先级比 Promise 还高 |

### 经典面试题

```js
console.log('1');

setTimeout(() => console.log('2'), 0);

Promise.resolve().then(() => {
  console.log('3');
  Promise.resolve().then(() => console.log('4'));
});

console.log('5');
```

输出顺序：**1 → 5 → 3 → 4 → 2**

分析：
1. `1` — 同步执行
2. `setTimeout` — 注册宏任务入队
3. `Promise.then` — 注册微任务入队
4. `5` — 同步执行
5. 当前宏任务（script）结束 → 清微任务队列
6. `3` — 微任务执行，同时注册微任务 `4`
7. `4` — 微任务队列未空，继续清
8. 微任务清空 → 取下一宏任务
9. `2` — setTimeout 回调执行

### async/await 的本质

```js
async function foo() {
  console.log('A');
  await bar();       // bar() 同步执行
  console.log('B'); // 等价于 Promise.resolve().then(() => console.log('B'))
}
```

`await` 之后的代码等价于包在 `.then()` 里，是微任务。

> **一句话记忆**：宏任务是"下一轮"，微任务是"这一轮结束前必须先清干净"。

## 3. 深拷贝 vs 浅拷贝

### 根本区别

- **原始值**（string、number、boolean 等）：赋值复制值本身，无深浅拷贝问题。
- **引用类型**（object、array）：变量存的是内存地址，赋值复制的是地址。

### 浅拷贝

复制一层，顶层属性是新的，嵌套对象/数组仍共享引用。

```js
const obj = { x: 1, nested: { y: 2 } };
const copy = { ...obj };

copy.x = 99;           // 不影响 obj.x ✅
copy.nested.y = 99;    // obj.nested.y 也变了 ❌
```

常见浅拷贝方式：

| 方式 | 说明 |
|------|------|
| `{ ...obj }` | 展开运算符 |
| `Object.assign({}, obj)` | 只复制第一层 |
| `arr.slice()` | 数组浅拷贝 |
| `[...arr]` | 数组展开 |

### 深拷贝

递归复制所有层级，新旧对象完全独立。

```js
const deep = structuredClone(obj);  // 现代方式
```

各方式对比：

| 方式 | 优点 | 局限 |
|------|------|------|
| `structuredClone(obj)` | 原生、支持循环引用、支持 Map/Set/Date | 不支持 Function、DOM 节点 |
| `JSON.parse(JSON.stringify(obj))` | 简单 | 丢失 Function/undefined，Date 变字符串，不支持循环引用 |
| 手写递归 | 可控 | 需处理循环引用 |
| lodash `_.cloneDeep()` | 全面 | 引入依赖 |

### 手写深拷贝（面试高频）

```js
function deepClone(target, map = new WeakMap()) {
  // 原始值直接返回
  if (typeof target !== 'object' || target === null) return target;

  // 处理循环引用
  if (map.has(target)) return map.get(target);

  // 处理特殊对象
  if (target instanceof Date) return new Date(target);
  if (target instanceof RegExp) return new RegExp(target);

  // 数组或普通对象
  const clone = Array.isArray(target) ? [] : {};
  map.set(target, clone);

  for (const key of Reflect.ownKeys(target)) {
    clone[key] = deepClone(target[key], map);
  }

  return clone;
}
```

关键点：
- `WeakMap` 解决循环引用（不阻止 GC）
- `Reflect.ownKeys` 能拿到 Symbol 类型的 key
- 递归前判断是否已拷贝，防止死循环

> **一句话区分**：浅拷贝复制一层，嵌套对象共享引用；深拷贝递归复制所有层，完全独立。

## 4. 减少子组件不必要的渲染

父组件状态更新默认导致所有子组件 re-render，以下方法可优化。

### React

#### 1. `React.memo` — props 浅比较跳过渲染

```js
const Child = React.memo(({ value }) => {
  return <div>{value}</div>;
});
// 父组件 re-render，只要 value 引用没变，Child 跳过渲染
```

#### 2. `useCallback` / `useMemo` — 稳定引用，配合 memo 使用

```js
// ❌ 每次父组件渲染产生新函数引用，memo 失效
<Child onClick={() => doSomething()} />

// ✅ useCallback 保证引用不变
const handleClick = useCallback(() => doSomething(), []);
<Child onClick={handleClick} />

// 对象/数组同理用 useMemo
const config = useMemo(() => ({ theme: 'dark' }), []);
<Child config={config} />
```

**`useCallback` / `useMemo` 必须配合 `memo` 子组件才能减少渲染，单独用没意义。**

#### 3. 状态下移 — 最根治的方法

```js
// ❌ 不相关状态放一起，input 变化带着 Child 一起渲染
function Parent() {
  const [count, setCount] = useState(0);
  const [input, setInput] = useState('');
  return <>
    <input onChange={e => setInput(e.target.value)} />
    <Child count={count} />
  </>;
}

// ✅ 把 input 状态下移到独立组件
function Parent() {
  const [count, setCount] = useState(0);
  return <>
    <InputBox />
    <Child count={count} />
  </>;
}
```

#### 4. 拆分 Context — 精细订阅

```js
// ❌ 整个 state 放 context，任何字段变化全部消费者重渲
<Context.Provider value={{ user, theme, cart }} />

// ✅ 拆分 context
<UserContext.Provider value={user}>
  <ThemeContext.Provider value={theme}>
```

更精细用 `zustand` / `jotai`，原子化订阅，只订阅用到的字段。

#### 5. `useTransition` / `useDeferredValue` — 降低更新优先级

```js
const [isPending, startTransition] = useTransition();
startTransition(() => {
  setSearchQuery(input);  // 低优先级更新，可被打断
});

// 或
const deferredQuery = useDeferredValue(searchQuery);
<ExpensiveList query={deferredQuery} />
```

#### 优先级排序

```
状态下移（架构层）> React.memo + useCallback/useMemo（局部）
> 拆分 Context（数据层）> useTransition（体验层）
```

先从架构层解决，memo 是补丁，滥用反而增加比较开销。

### Vue

Vue 响应式系统自带依赖追踪，组件只在用到的响应式数据变化时才重渲，天然比 React 精细。

#### 1. `v-memo` — 显式缓存子树（Vue 3.2+）

```html
<li v-for="item in list" :key="item.id" v-memo="[item.id, selected === item.id]">
  ...
</li>
```

#### 2. 计算属性缓存

```js
// ❌ 方法每次渲染都重新执行
{{ formatDate(date) }}

// ✅ computed 有缓存，依赖不变不重算
const formatted = computed(() => formatDate(date.value));
```

#### 3. 避免模板里传对象字面量

```html
<!-- ❌ 每次渲染都是新引用 -->
<Child :config="{ theme: 'dark' }" />

<!-- ✅ 用 computed 或 reactive 稳定引用 -->
<Child :config="config" />
```

## 5. `v-for` 渲染列表时为什么要传 `key`

**根本原因：虚拟 DOM diff 算法需要 key 来识别节点身份。**

不加 key 时，Vue/React 默认用**索引位置**对比新旧节点，列表顺序变化时会出问题。

### 不加 key 时发生什么

```js
// 初始列表
['A', 'B', 'C']

// 在头部插入 'X'
['X', 'A', 'B', 'C']
```

diff 按位置对比：

| 位置 | 旧 | 新 | 操作 |
|------|----|----|------|
| 0 | A | X | 更新内容 |
| 1 | B | A | 更新内容 |
| 2 | C | B | 更新内容 |
| 3 | — | C | 新增节点 |

结果：更新了 3 个节点 + 新增 1 个，实际上只需要**新增 1 个**。

### 加了 key 之后

diff 通过 key 识别节点身份：

- `key="A"` 的节点还在，只是位置移了 → **复用，移动位置**
- `key="X"` 是新的 → **创建**

结果：只新增 1 个节点，其余复用，DOM 操作最少。

### key 的第二个作用：强制销毁重建

有时候**不想**复用，key 变了就强制重建：

```html
<!-- 切换用户时，强制重置表单组件的内部状态 -->
<UserForm :key="userId" />
```

`userId` 变了 → 旧组件销毁，新组件重建，内部 state 完全重置。

### 为什么不能用 index 做 key

```html
<li v-for="(item, index) in list" :key="index">
```

index 做 key 和不加 key 一样——位置没变，key 就没变，该复用的还是会复用错。

典型问题：列表有输入框，删除第一项后，用 index 做 key，B 的 input 残留了 A 的输入内容。

**应该用数据本身的唯一标识（`item.id`）做 key。**

> **一句话总结**：key 是节点的身份证，让 diff 算法知道"这个节点是移动了"还是"这是一个新节点"，从而最小化 DOM 操作。不加或用 index，等于每次都按位置猜，猜错就出 bug。

### 延伸场景：`[1, 2, 3]` 中间插入 4 变成 `[1, 4, 2, 3]`

用 index 做 key，diff 按位置对比：

| 位置 | 旧值 | 新值 | key | 操作 |
|------|------|------|-----|------|
| 0 | 1 | 1 | 0 | 复用，内容相同 |
| 1 | 2 | 4 | 1 | 复用，**更新内容** 2→4 |
| 2 | 3 | 2 | 2 | 复用，**更新内容** 3→2 |
| 3 | — | 3 | 3 | **新增节点** |

**第一层：视觉上渲染是对的。** 最终显示 `1, 4, 2, 3`，用户看不出问题。

**第二层：带状态的子组件会错乱。** 假设每项有 `<input>`：

插入前：
- index 1（值 2）→ input 输入了 "b"

插入后按 index 复用：
- index 1（现在是值 4）→ **复用了原 index 1 的 DOM**，input 残留 "b"，但显示的是 4 ❌

**视觉对，状态错。** input 里的值和它对应的数字对不上了。

**根本原因**：index 和"位置"绑定，位置没变 key 就没变，Vue 认为是同一节点去复用。插入/删除/排序导致位置和数据身份错配，带状态的子组件（input、动画、内部 state）全部跟着错乱。

- 纯文本无状态的列表：用 index 不出 bug，但性能仍然不优
- 任何带状态的列表：**必须用稳定唯一标识（`item.id`）做 key**

## 6. TypeScript `unknown` 和 `never`

### `unknown` — 类型安全的 `any`

`unknown` 表示"我不知道这是什么类型"，但和 `any` 不同，**用之前必须先收窄类型**。

```ts
let val: unknown = fetchSomething();

// ❌ 不能直接用，编译器拒绝
val.toUpperCase();

// ✅ 先收窄，再使用
if (typeof val === 'string') {
  val.toUpperCase();
}
if (val instanceof Error) {
  console.log(val.message);
}
```

对比 `any`：

| | `any` | `unknown` |
|--|-------|-----------|
| 能赋值给任意类型 | ✅ | ❌ |
| 使用前需类型检查 | ❌ | ✅ |
| 类型安全 | 不安全 | 安全 |

使用场景：

```ts
// 1. 外部输入：API 返回、JSON.parse、用户输入
const data: unknown = JSON.parse(rawString);

// 2. catch 块（TS 4.0+ 默认 error 是 unknown）
try {
  // ...
} catch (e: unknown) {
  if (e instanceof Error) {
    console.log(e.message);
  }
}

// 3. 泛型工具函数，接收任意输入但不假设类型
function safeStringify(val: unknown): string {
  return JSON.stringify(val);
}
```

> 能用 `unknown` 就不用 `any`。`any` 是关掉类型检查，`unknown` 是延迟类型检查。

### `never` — 不可能存在的类型

`never` 表示"这里永远不会有值"，是所有类型的子类型，但没有任何值属于 `never`。

**1. 函数永远不会正常返回**

```ts
function throwError(msg: string): never {
  throw new Error(msg);
}

function loop(): never {
  while (true) {}
}
```

**2. 穷举检查（最重要的场景）**

```ts
type Shape = 'circle' | 'square' | 'triangle';

function getArea(shape: Shape) {
  switch (shape) {
    case 'circle':   return Math.PI;
    case 'square':   return 1;
    case 'triangle': return 0.5;
    default:
      // 所有情况都处理了，shape 此时是 never
      // 漏掉某个 case，这里会编译报错 ✅
      const exhausted: never = shape;
      throw new Error(`Unhandled shape: ${exhausted}`);
  }
}
```

以后 `Shape` 加了 `'hexagon'` 但 switch 没加对应 case，`shape` 就不再是 `never`，赋值给 `never` 类型**编译报错**，防止遗漏分支。

**3. 条件类型中过滤**

```ts
type NonNullable<T> = T extends null | undefined ? never : T;

type A = string | null | undefined;
type B = NonNullable<A>;  // string
```

### 一句话区分

| 类型 | 含义 | 记忆法 |
|------|------|--------|
| `unknown` | 有值，但类型未知，用前要检查 | "不知道是什么，先验证" |
| `never` | 不可能有值，或代码不可达 | "这里永远到不了" |

## 7. AI 开放题三连

### 7.1 AI 承担大部分开发，有什么弊端？

**核心弊端是：理解断层在积累。**

AI 写的代码，开发者没有经历"写出来"的过程，也就没有经历"为什么这么写"的推导过程。短期没问题，代码能跑。但当系统出问题——线上 bug、性能瓶颈、架构需要重构——需要的不是"能写代码"，而是"看懂这段代码在做什么、为什么出错"。这个能力靠写代码和踩坑积累，不是靠 review AI 输出积累。

**结果：初级开发者的成长路径变窄了。**

以前的路径：写代码 → 写烂 → 被 review → 理解为什么烂 → 写好。
现在变成：提 prompt → AI 写 → 能跑就上。跑通了但没有理解，下次遇到相似问题还是得问 AI，不是真的会了。

**还有一个实际风险：AI 的错误不像人的错误那么明显。**

人写的代码逻辑错了，通常结构上也会让人觉得"这里有点奇怪"。AI 生成的代码结构整洁、注释完整，但可能在关键边界条件上悄悄算错，看起来完全没问题。Review 的人如果本身理解不深，就过了。这种错误的发现成本很高。

**这不是 AI 的问题，是使用方式的问题。**

- AI 做得好：生成样板代码、搜索已知方案、加速熟悉领域的执行。
- AI 做不好：理解你系统的历史包袱、判断这个 tradeoff 在你的业务上值不值、感知"这里以后会成为债"。

这些判断需要人真实地理解系统，AI 只是执行。

### 7.2 如何应对这些弊端？

**核心：区分"用 AI 产出"和"用 AI 学习"，前者不能替代后者。**

**第一层：个人层面——保持"手写"的刻意练习**

关键是有意识地**自己先想再问 AI**：

- 遇到问题，先自己定位 5-10 分钟，形成自己的判断，再去对比 AI 的方案，看差异在哪。差异的地方就是认知盲区，是成长点。
- 系统设计这类高判断密度的活，**坚持自己先出方案**，AI 给的方案只当参考。AI 不会理解你的业务历史和约束，它的方案是通用解，不是你的最优解。
- 保留一定量的"不靠 AI"的练习，比如手写算法、手写核心模块。不是为了效率，是为了保持手感。

实践：review AI 生成的代码时，强制自己讲一遍"这段在做什么、为什么这么写"。讲不出来就说明没理解，必须搞懂。**讲得出来才算你的，讲不出来只是 AI 的。**

**第二层：团队层面——用流程强制理解发生**

个人靠自觉不可靠，团队流程可以兜底：

- **Code Review 不能因为 AI 写的就放松**，反而要更严。重点是"提交者能不能解释清楚这段代码为什么这么做"。解释不清就打回，逼着提交者去理解。
- **关键路径的代码不用 AI 写**，或 AI 写完必须有人深度 review。核心业务逻辑、鉴权、支付、高并发这些地方，不能让"能跑"成为标准。
- **让 AI 产出可追溯**。AI 生成的代码要标注、要有 prompt 记录，未来出问题时能回溯到"当时是基于什么前提生成的"。

**第三层：把 AI 的局限变成你的价值**

AI 不会消失，但它的局限是稳定的：

- 不理解你的业务历史和系统约束
- 不会判断 tradeoff 在你的具体场景值不值
- 不知道"这里以后会成为债"

这些判断恰好是经验型开发者的价值所在。**主动去承担 AI 做不了的部分**——架构决策、跨团队对齐、技术债评估、性能瓶颈定位——这是不会被 AI 替代的能力。把这些做深，反而能让 AI 成你的放大器而不是替代者。

> AI 降低了"产出代码"的门槛，但没有降低"理解系统"的门槛。应对的方法不是少用 AI，而是把节省下来的时间投到 AI 做不了的事情上，并且用流程保证"产出之前理解先发生"。

### 7.3 AI Coding 时代对程序员手写代码能力的要求，降低还是提高？



**第一步：先给立场，不骑墙**

> 我的看法是：要求没有降低，而是结构变了。执行层的要求降低了，但判断层的要求提高了，整体是往上移了，不是降了。

**第二步：核心论证**

> AI 把"写出能跑的代码"这件事变容易了，但这恰恰把另外三件事暴露成了硬需求——调试、Review、判断。这三件事 AI 现在做不了，而且恰恰需要手写代码积累出来的理解力。
>
> 以前手写和理解是绑定的，你写代码的过程就是在理解。现在 AI 把这两个解耦了，很多人会发现：代码能跑，但我不懂；AI 换个写法就看不懂了。这就是理解的缺口。

**第三步：金句收尾**

> AI 是杠杆。杠杆放大的不只是好的判断，也放大坏的判断。杠杆越大，判断力越重要，而不是越不重要。

**第四步：落到自己（区别于泛泛而谈的关键）**

> 我自己的体会是，现在反而是积累判断力最关键的时间窗口。用 AI 把执行速度提上去，把时间投到 AI 做不了的事情上——架构决策、性能瓶颈定位、tradeoff 判断。手写代码我自己没有放松，但不是为了产出速度，是为了保持理解力。

**如果被追问"那你是不是觉得手写代码不重要了"**

> 不是不重要，是重要性从"产出手段"变成了"理解手段"。我不靠手写追求速度，但靠手写保持理解。理解一旦断层，调试和 Review 这两个 AI 做不了的事就做不了了。
