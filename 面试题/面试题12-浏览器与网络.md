# 浏览器与网络面试题（中大厂 2024–2026 调研版）

## 一、TCP 握手与挥手

### TCP 三次握手的过程？为什么是三次而不是两次或四次？

**参考答案：**

1. **三次握手流程：**
   - 第一次：客户端发送 SYN（seq=x），进入 SYN_SENT 状态
   - 第二次：服务端收到后回复 SYN+ACK（seq=y, ack=x+1），进入 SYN_RCVD 状态
   - 第三次：客户端收到后发送 ACK（ack=y+1），双方进入 ESTABLISHED 状态

2. **为什么不是两次？**
   - 两次握手只能让服务端确认自己能收到客户端的数据，但无法确认客户端能收到服务端的数据（全双工需要双向确认）
   - 两次握手还容易造成服务端资源浪费：旧的失效 SYN 请求到达服务端时，服务端直接建立连接，但客户端不认这个连接，会忽略服务端的响应

3. **为什么不是四次？**
   - 服务端可以在第二次握手中将 SYN 和 ACK 合并发送，三次已经足够完成双方能力的互相确认，四次是冗余的

4. **三次握手的本质：** 确认双方的发送和接收能力均正常，并同步初始序列号（ISN）

---

### TCP 四次挥手的过程？为什么挥手需要四次而握手只需三次？

**参考答案：**

1. **四次挥手流程：**
   - 第一次：客户端发送 FIN（seq=u），进入 FIN_WAIT_1 状态
   - 第二次：服务端收到后回复 ACK（ack=u+1），进入 CLOSE_WAIT 状态；客户端收到后进入 FIN_WAIT_2 状态
   - 第三次：服务端处理完剩余数据后发送 FIN（seq=v），进入 LAST_ACK 状态
   - 第四次：客户端收到后回复 ACK（ack=v+1），进入 TIME_WAIT 状态；服务端收到后关闭连接

2. **为什么挥手需要四次？**
   - TCP 是全双工通信，两个方向的数据流需要独立关闭
   - 客户端发送 FIN 只是表示客户端不再发送数据，但服务端可能还有数据要发送
   - 服务端的 ACK 和 FIN 不能合并（不像握手时 SYN+ACK 可合并），因为服务端在收到 FIN 后需要等待剩余数据发送完毕才能关闭自己的发送方向
   - 所以必须分两步：先 ACK（表示收到关闭请求），后 FIN（表示自己也准备好关闭了）

---

### TIME_WAIT 状态是什么？为什么需要等待 2MSL？

**参考答案：**

1. **TIME_WAIT 是什么：** 客户端发送最后一个 ACK 后进入的等待状态，持续时间为 2MSL（MSL = Maximum Segment Lifetime，报文最大生存时间，通常为 60s，2MSL = 120s）

2. **为什么等待 2MSL？**
   - **原因一：确保最后的 ACK 能到达服务端。** 如果最后的 ACK 丢失，服务端会重发 FIN，客户端需要在 2MSL 内能接收到这个重发的 FIN 并重新回复 ACK
   - **原因二：让旧连接的报文在网络中消亡。** 等待 2MSL 保证本次连接中所有的报文都从网络中消失，防止新连接收到上一次连接的旧报文造成干扰

3. **TIME_WAIT 过多的问题：** 在高并发服务器上，大量 TIME_WAIT 会占用端口和内存
   - 优化方案：设置 `SO_REUSEADDR`（允许端口复用）、调整内核参数 `tcp_tw_reuse`、`tcp_fin_timeout`

---

### SYN Flood 攻击是什么原理？如何防御？

**参考答案：**

1. **攻击原理：**
   - 攻击者伪造大量源 IP 地址，向服务端发送 SYN 请求
   - 服务端回复 SYN+ACK 后，等待客户端的第三次握手 ACK
   - 伪造的 IP 不会回复 ACK，服务端的**半连接队列**被大量占满
   - 正常用户的连接请求无法进入队列，服务瘫痪

2. **防御方案：**
   - **SYN Cookie：** 服务端收到 SYN 后不分配资源，而是根据源 IP/端口计算一个 Cookie 放入 SYN+ACK 的序列号中，只有收到合法的第三次握手 ACK 后才正式建立连接
   - **增大半连接队列：** 调整内核参数 `tcp_max_syn_backlog`
   - **缩短超时时间：** 减少 `tcp_synack_retries`（SYN+ACK 重试次数）
   - **防火墙限速：** 对同一 IP 的 SYN 频率做限制

---

### TCP 和 UDP 的核心区别？各自适用场景？

**参考答案：**

| 对比项 | TCP | UDP |
|--------|-----|-----|
| 连接 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 可靠（确认/重传/排序） | 不可靠（无确认） |
| 顺序 | 保证有序 | 不保证有序 |
| 速度 | 较慢（开销大） | 较快（开销小） |
| 头部大小 | 20–60 字节 | 8 字节 |
| 流量控制 | 有（滑动窗口） | 无 |
| 拥塞控制 | 有 | 无 |

**适用场景：**
- **TCP：** 文件传输、网页浏览（HTTP/HTTPS）、邮件、SSH——需要可靠传输的场景
- **UDP：** 视频直播、语音通话、DNS 查询、游戏实时对战——对延迟敏感、允许少量丢包的场景
- **HTTP/3（QUIC）：** 基于 UDP 实现了自己的可靠传输，兼顾速度和可靠性

### 半连接队列和全连接队列是什么？SYN Flood 针对哪个队列？

**参考答案：**

1. **半连接队列（SYN Queue）：**
   - 服务端收到客户端 SYN 后，将连接信息存入半连接队列，等待第三次握手
   - 队列大小由 `tcp_max_syn_backlog` 控制
   - SYN Flood 攻击**针对的是半连接队列**，将其填满导致正常连接无法进入

2. **全连接队列（Accept Queue）：**
   - 三次握手完成后，连接从半连接队列移入全连接队列，等待应用层调用 `accept()` 取走
   - 队列大小由 `listen()` 的 `backlog` 参数和内核参数 `somaxconn` 共同决定
   - 全连接队列满时，新完成的握手可能被丢弃

3. **排查思路：**
```bash
ss -lnt  # 查看 Recv-Q（全连接队列当前大小）和 Send-Q（队列上限）
netstat -s | grep "SYNs to LISTEN"  # 查看因队列满被丢弃的连接数
```

## 二、HTTP 协议

### HTTP 和 HTTPS 的区别？HTTPS 能防中间人攻击吗？为什么 HTTPS 也可能被抓包？

**参考答案：**

1. **核心区别：**

| 维度 | HTTP | HTTPS |
|------|------|-------|
| 安全性 | 明文传输，可被窃听/篡改 | TLS 加密，防窃听/防篡改/防伪装 |
| 端口 | 80 | 443 |
| 握手开销 | 仅 TCP 三次握手 | TCP + TLS 握手（额外 1–2 RTT） |
| 证书 | 不需要 | 需要 CA 颁发的数字证书 |
| SEO | 无加权 | Google 对 HTTPS 有排名加权 |

2. **HTTPS 能防中间人攻击：**
   - 通过证书链验证，客户端可以确认服务端的真实身份
   - 中间人即使截获报文也无法解密（没有私钥）
   - 中间人如果伪造证书，浏览器会因证书不受信任而警告

3. **为什么 HTTPS 也可能被抓包（Charles/Fiddler）：**
   - 这些工具会在客户端安装一个自签的根证书
   - 用户/系统主动信任了这个根证书，相当于用户自愿信任了"中间人"
   - 工具扮演中间人，与服务端建立一个 TLS 连接，与客户端建立另一个 TLS 连接，从而解密并查看流量
   - **本质：** 这是用户主动授信的中间人，并不是 HTTPS 的安全缺陷

4. **HTTP/2 要求 HTTPS 吗？**
   - 协议规范上不强制，但主流浏览器（Chrome/Firefox）只在 HTTPS 下支持 HTTP/2

---

### HTTP/1.1、HTTP/2、HTTP/3 核心区别？

**参考答案：**

1. **HTTP/1.1：**
   - 持久连接（Keep-Alive），复用 TCP 连接，但同一连接同一时刻只能处理一个请求（队头阻塞）
   - 浏览器通过开多个 TCP 连接（通常 6 个/域）来并行请求
   - 头部使用纯文本，体积大

2. **HTTP/2：**
   - **多路复用：** 同一 TCP 连接上可以并行发送多个请求/响应，彻底解决 HTTP 层面的队头阻塞
   - **头部压缩（HPACK）：** 使用静态/动态表压缩 Header，减少重复头部传输
   - **二进制分帧：** 请求和响应被分成二进制帧传输，更高效
   - **Server Push：** 服务端可以主动推送资源（Chrome 已于 2023 年移除支持）
   - **仍有 TCP 层队头阻塞：** 一个 TCP 包丢失会导致整个连接的所有流阻塞

3. **HTTP/3（QUIC）：**
   - 基于 **UDP** 而非 TCP，自己实现可靠传输
   - 解决了 TCP 层面的队头阻塞：每个流独立，一个流丢包不影响其他流
   - **0-RTT / 1-RTT 握手：** 将 TLS 握手和传输握手合并，大幅减少连接建立时间
   - 连接迁移：基于 Connection ID 而非 IP+端口，网络切换（Wi-Fi → 4G）不需要重新建立连接

---

### HTTP/2 的多路复用和 HTTP/1.1 的 Keep-Alive 有什么本质区别？

**参考答案：**

1. **Keep-Alive（HTTP/1.1）：**
   - 复用同一个 TCP 连接发送多个请求，但请求是**串行**的
   - 必须等上一个请求的响应完成，才能发下一个请求（应用层队头阻塞）
   - 虽然支持 Pipeline（流水线），但服务端必须按请求顺序响应，实际很少使用

2. **多路复用（HTTP/2）：**
   - 同一 TCP 连接上可以同时发送多个请求和接收多个响应，完全**并行**
   - 每个请求/响应被拆分为独立的**帧（Frame）**，帧上带有流 ID（Stream ID）标识归属
   - 不同流的帧可以交错传输，接收方根据 Stream ID 重新组装
   - 彻底消除了应用层的队头阻塞

3. **一句话总结：** Keep-Alive 是"共用跑道但只能一辆车"，多路复用是"多辆车同时在跑道上跑"

---

### HTTP/3 为什么基于 UDP？QUIC 如何解决队头阻塞？

**参考答案：**

1. **为什么基于 UDP：**
   - TCP 的队头阻塞问题根植于协议本身，难以在不改变协议的前提下修复
   - UDP 是无连接、无序的基础传输协议，QUIC 在其上自行实现了可靠传输、拥塞控制、流量控制等能力
   - 基于 UDP 还便于在用户态更新协议（不需要等待操作系统内核升级）

2. **QUIC 如何解决队头阻塞：**
   - HTTP/2 的问题：虽然应用层多路复用，但多个流共享同一条 TCP 连接，TCP 层一个包丢失会触发重传，导致所有流等待
   - QUIC 的方案：每个流（Stream）在 QUIC 层面是独立的，一个流的包丢失只会阻塞该流自己，其他流正常传输
   - 本质：将流的独立性从应用层下沉到了传输层

3. **其他 QUIC 优势：**
   - **连接建立快：** 首次连接 1-RTT（TLS+传输握手合并），再次连接可 0-RTT
   - **连接迁移：** 使用 Connection ID 标识连接，IP 变化（如切换网络）不需要重新握手

### HTTP 强缓存 vs 协商缓存？Cache-Control: no-cache vs no-store 区别？

**参考答案：**

1. **强缓存：** 浏览器直接使用本地缓存，不向服务器发请求
   - `Cache-Control: max-age=3600`：缓存 3600 秒内有效
   - `Expires: Wed, 01 Jan 2025 00:00:00 GMT`：HTTP/1.0 的过期时间（已被 Cache-Control 替代）
   - 命中时状态码为 **200（from cache）**

2. **协商缓存：** 浏览器向服务器发请求验证缓存是否仍然有效
   - `Last-Modified / If-Modified-Since`：基于文件修改时间（精度为秒）
   - `ETag / If-None-Match`：基于文件内容哈希（精度更高）
   - 命中时服务器返回 **304 Not Modified**，浏览器使用本地缓存
   - 未命中时服务器返回 **200** 和新内容

3. **优先级：** 强缓存 > 协商缓存；ETag > Last-Modified

4. **no-cache vs no-store：**
   - `no-cache`：**不是不缓存**，而是每次都要向服务器验证（走协商缓存），验证通过才用本地缓存
   - `no-store`：**真正不缓存**，每次都完整请求新资源，不存储任何缓存

5. **完整缓存决策流程：**
```
请求资源
  → 有本地缓存？
    → 是：Cache-Control 未过期？
      → 是：直接用（强缓存命中，200 from cache）
      → 否：向服务器发送 If-None-Match / If-Modified-Since
        → 服务器返回 304：用本地缓存（协商缓存命中）
        → 服务器返回 200：使用新资源并更新缓存
    → 否：直接请求服务器
```

### ETag 强校验 vs 弱校验（W/"xxx"）区别？

**参考答案：**

1. **强 ETag（`"abc123"`）：**
   - 精确匹配，表示资源内容完全一致（字节级别）
   - 任何内容变化（哪怕一个字节）都会导致 ETag 变化
   - 适合精确缓存控制

2. **弱 ETag（`W/"abc123"`）：**
   - 语义上等价（资源"实质上"没有变化），允许细微差异（如 HTTP 头、空格、换行等）
   - 服务端可以主动选择什么算"实质变化"
   - 适合不需要字节级精确匹配的场景（如压缩版本和非压缩版本可视为等价）

3. **实际应用：** Nginx 默认生成弱 ETag（基于文件大小和修改时间），Apache 生成强 ETag（基于 inode、大小、时间）

### Service Worker 缓存与浏览器缓存的优先级关系？

**参考答案：**

1. **优先级顺序（从高到低）：**
   - Service Worker（fetch 事件拦截）
   - Memory Cache（内存缓存，当前会话）
   - Disk Cache（磁盘缓存，即 HTTP 缓存）
   - 网络请求

2. **SW 拦截后 Cache-Control 还生效吗？**
   - **取决于 SW 的实现**
   - 如果 SW 的 fetch 事件直接 `return cache.match(request)`，则完全绕过 HTTP 缓存，`Cache-Control` 不生效
   - 如果 SW 不拦截（`fetch(request)` 透传），则浏览器正常走 HTTP 缓存逻辑，`Cache-Control` 生效
   - SW 本身的脚本文件（`sw.js`）受 HTTP 缓存控制，但浏览器默认对其有特殊处理（不超过 24 小时）

3. **常见 SW 缓存策略：**
   - Cache First：先查缓存，没有再请求网络（适合静态资源）
   - Network First：先请求网络，失败再用缓存（适合 API 请求）
   - Stale While Revalidate：先返回缓存，同时在后台更新缓存

### HTTP 状态码：301 vs 302 vs 307 vs 308 的语义差异？

**参考答案：**

| 状态码 | 类型 | 方法保留 | 永久/临时 | 说明 |
|--------|------|---------|-----------|------|
| 301 | 永久重定向 | ❌ POST→GET | 永久 | 旧 URL 永久移走，SEO 权重转移，POST 可能变 GET |
| 302 | 临时重定向 | ❌ POST→GET | 临时 | 旧 URL 临时不可用，POST 可能变 GET |
| 307 | 临时重定向 | ✅ 保留 | 临时 | 严格保留请求方法，POST 还是 POST |
| 308 | 永久重定向 | ✅ 保留 | 永久 | 301 的严格版，保留请求方法 |

**关键区别：**
- 307/308 是 HTTP/1.1 新增，解决了 301/302 不明确保留请求方法的问题
- **SEO：** 301/308 会让搜索引擎更新索引，302/307 不会
- **实际使用：** HTTPS 强制跳转用 301；登录后重定向用 302；API 保留方法重定向用 307

### preload、prefetch、preconnect 分别什么时机触发？

**参考答案：**

1. **preload（`<link rel="preload">`）：**
   - **当前页面**的关键资源，高优先级，立即下载
   - 告诉浏览器"这个资源当前页面马上要用"
   - 适合：当前页关键 CSS、字体、首屏图片
   ```html
   <link rel="preload" href="font.woff2" as="font" crossorigin>
   ```

2. **prefetch（`<link rel="prefetch">`）：**
   - **下一个页面**可能用到的资源，低优先级，在浏览器空闲时下载
   - 告诉浏览器"用户可能接下来会访问这个资源"
   - 适合：路由懒加载的下一个页面 chunk

3. **preconnect（`<link rel="preconnect">`）：**
   - 提前与目标域名建立 TCP 连接 + TLS 握手，但不下载资源
   - 减少后续请求该域名资源时的连接建立时间
   - 适合：CDN 域名、第三方 API 域名
   ```html
   <link rel="preconnect" href="https://fonts.googleapis.com">
   ```

4. **dns-prefetch（`<link rel="dns-prefetch">`）：**
   - 只做 DNS 解析，不建立连接，开销更小，兼容性更好
   - preconnect 不兼容时的降级方案

## 三、HTTPS / TLS

### HTTPS 建立连接的完整过程？总共几个 RTT？

**参考答案：**

1. **完整流程（TLS 1.2，共 3 RTT）：**
```
RTT 1：TCP 三次握手（SYN → SYN+ACK → ACK）
RTT 2：TLS ClientHello → ServerHello + Certificate + ServerHelloDone
RTT 3：Client Key Exchange + ChangeCipherSpec → Server ChangeCipherSpec + Finished
        → 发送第一个 HTTP 请求
```

2. **TLS 1.3（共 2 RTT，首次）：**
```
RTT 1：TCP 三次握手
RTT 2：TLS 1.3 单次握手（Client Hello → Server Hello + Finished → 发送数据）
```

3. **HTTP/3（QUIC，首次 1 RTT，复连 0 RTT）：**
   - 将 TCP 握手和 TLS 握手合并，一次 RTT 完成
   - 再次连接可 0-RTT 直接发送数据

---

### HTTPS 握手过程（TLS）？对称加密和非对称加密分别用在哪里？

**参考答案：**

1. **TLS 1.2 握手流程：**
   - **Client Hello：** 客户端发送支持的 TLS 版本、加密套件列表、随机数 Random_C
   - **Server Hello：** 服务端选择加密套件、发送随机数 Random_S、发送证书（含公钥）
   - **证书验证：** 客户端验证证书链（CA 签名）确认服务端身份
   - **密钥协商：** 客户端生成 Pre-Master Secret，用服务端公钥加密后发送
   - **生成会话密钥：** 双方用 Random_C + Random_S + Pre-Master Secret 生成对称密钥
   - **完成握手：** 双方用对称密钥加密 Finished 消息，确认握手完整性

2. **非对称加密的作用：** 仅用于**密钥协商阶段**，用服务端公钥加密 Pre-Master Secret（或 ECDHE 的密钥交换）

3. **对称加密的作用：** 握手完成后的**所有数据传输**都使用对称加密（如 AES-GCM），因为对称加密速度快

4. **为什么不全程用非对称加密？** 非对称加密计算开销远大于对称加密，不适合大量数据传输

---

### TLS 1.2 和 TLS 1.3 握手次数各是几次？TLS 1.3 的改进？

**参考答案：**

1. **握手 RTT 数：**
   - TLS 1.2：2 RTT（两次来回）
   - TLS 1.3：1 RTT（首次），0 RTT（复连，有安全风险）

2. **TLS 1.3 的主要改进：**
   - **减少握手 RTT：** 将密钥协商集成到 Client Hello，服务端收到后直接回复并开始加密传输
   - **废弃不安全算法：** 移除 RSA 密钥协商（存在前向安全问题）、RC4、SHA-1、DES 等弱算法
   - **只保留 ECDHE：** 所有密钥交换必须使用前向安全（Forward Secrecy）的算法，即使私钥泄漏也无法解密历史流量
   - **加密范围扩大：** TLS 1.3 握手中更多的内容被加密（Server Certificate 也被加密）

3. **前向安全（Forward Secrecy）：** 每次会话使用临时密钥，会话结束后密钥销毁，历史流量无法被解密

---

### 0-RTT 是什么？有什么安全隐患？

**参考答案：**

1. **0-RTT 是什么：**
   - TLS 1.3 支持的特性，客户端在首次连接时保存会话票据（Session Ticket）
   - 再次连接时，客户端在第一个包里就携带加密的应用数据，无需等待握手完成
   - 实现了"零往返时间"建立连接并发送数据

2. **安全隐患——重放攻击（Replay Attack）：**
   - 攻击者截获 0-RTT 请求，在会话票据有效期内重复发送
   - 服务端无法区分重放请求和正常请求，可能导致重复操作（如重复扣款）

3. **缓解方案：**
   - 0-RTT 只用于幂等请求（GET 等），不用于 POST/PUT 等有副作用的操作
   - 服务端维护 0-RTT 请求的防重放机制（nonce 记录）

---

### 证书链验证流程？中间人攻击如何被发现？

**参考答案：**

1. **证书链验证流程：**
   - 浏览器收到服务端证书后，提取证书中的颁发者（Issuer）信息
   - 在操作系统/浏览器内置的**根证书库**中查找对应的 CA
   - 通常是：服务端证书 → 中间 CA 证书 → 根 CA 证书（根证书内置，无需传输）
   - 逐级验证：用上级 CA 的公钥验证下级证书的签名
   - 验证内容：证书签名、有效期、域名（CN/SAN）、是否被吊销（OCSP/CRL）

2. **中间人攻击如何被发现：**
   - 中间人需要伪造服务端证书，但无法通过受信任 CA 的签名
   - 浏览器验证证书签名时发现不可信，显示安全警告（"您的连接不是私密连接"）
   - 若中间人使用的是被盗/泄漏的合法证书，Certificate Transparency（CT）日志可以发现异常证书

3. **HSTS 的额外防护：** 浏览器记录该域名只能用 HTTPS 访问，防止降级攻击（将 HTTPS 请求改为 HTTP 再中间人）

---

### HSTS（HTTP Strict Transport Security）解决了什么问题？

**参考答案：**

1. **解决的问题：HTTPS 降级攻击（SSL Stripping）**
   - 用户输入 `example.com`，浏览器默认先发 HTTP 请求
   - 中间人可以拦截这个 HTTP 请求，与用户通过 HTTP 通信，与服务端通过 HTTPS 通信
   - 用户浏览器始终显示 HTTP，数据被中间人明文查看

2. **HSTS 的工作原理：**
   - 服务端在 HTTPS 响应头中返回：`Strict-Transport-Security: max-age=31536000; includeSubDomains`
   - 浏览器记录该域名，在 `max-age` 期间内，所有对该域名的请求强制使用 HTTPS
   - 即使用户输入 `http://`，浏览器也会在内部将其改为 `https://`，不发出 HTTP 请求

3. **HSTS Preload：**
   - 将域名提交到 Chrome 维护的 HSTS Preload 列表，浏览器出厂即内置，首次访问也强制 HTTPS

---

### HTTP/3（QUIC）为什么能减少握手 RTT？

**参考答案：**

1. **QUIC 将 TLS 握手和传输握手合并：**
   - TCP + TLS 1.2：TCP 握手（1 RTT）+ TLS 握手（2 RTT）= 3 RTT
   - TCP + TLS 1.3：TCP 握手（1 RTT）+ TLS 握手（1 RTT）= 2 RTT
   - QUIC（首次）：QUIC+TLS 合并握手 = 1 RTT
   - QUIC（复连）：0 RTT（利用之前的会话凭证直接发数据）

2. **为什么能合并：**
   - QUIC 在 UDP 基础上自行实现了可靠传输，不需要 TCP 的连接状态机
   - QUIC 的握手帧直接包含 TLS 握手数据，一次来回即可完成连接建立和密钥协商

3. **连接迁移：**
   - TCP 连接由 四元组（源 IP+端口，目标 IP+端口）标识，网络切换时四元组变化，连接必须重建
   - QUIC 使用 **Connection ID** 标识连接，IP 变化后仍可继续使用同一连接（对移动设备友好）

---

## 四、浏览器渲染原理

### 从输入 URL 到页面完全展示，发生了什么？

**参考答案：**

1. **URL 解析：** 浏览器解析 URL（协议/域名/路径/参数），检查 HSTS 列表决定是否升级为 HTTPS

2. **DNS 解析：**
   - 检查顺序：浏览器 DNS 缓存 → 操作系统 DNS 缓存（hosts 文件）→ 路由器缓存 → ISP DNS 服务器 → 递归查询根域名服务器
   - 最终获取目标 IP 地址

3. **建立连接：**
   - TCP 三次握手建立连接
   - 若是 HTTPS，进行 TLS 握手（1–2 RTT）

4. **发送 HTTP 请求：** 构造请求行（方法/URL/协议版本）+ 请求头（Cookie/UA/Accept 等）+ 请求体

5. **服务器处理并响应：** 返回响应状态码、响应头（Content-Type/Cache-Control 等）、响应体

6. **浏览器渲染：**（多进程架构）
   - **网络进程** 接收响应数据
   - **渲染进程** 进行渲染：解析 HTML → 构建 DOM → 解析 CSS → 构建 CSSOM → 合并为 Render Tree → Layout（布局计算位置大小）→ Paint（绘制像素）→ Composite（合成层显示）

7. **2024 新考法——多进程架构细节：**
   - Browser 进程：负责 UI、地址栏、前进后退
   - Renderer 进程：每个 Tab/站点独立，负责渲染
   - Network 进程：负责所有网络请求
   - GPU 进程：负责 GPU 加速合成
   - Plugin 进程：Flash 等插件

---

### 浏览器渲染流程：DOM → CSSOM → Layout → Paint → Composite

**参考答案：**

1. **解析 HTML → DOM 树：** 字节流 → 字符 → Token → Node → DOM 树；遇到 `<script>` 默认阻塞解析（可用 defer/async 避免）

2. **解析 CSS → CSSOM 树：** CSS 解析不阻塞 DOM 构建，但会阻塞渲染（需等 CSSOM 完成才能进行 Layout）

3. **Render Tree（渲染树）：** 合并 DOM + CSSOM，只包含可见节点（`display:none` 的节点不包含，`visibility:hidden` 包含）

4. **Layout（布局/回流）：** 计算每个可见节点的几何信息（位置、大小），输出盒模型

5. **Paint（绘制）：** 将 Layout 的结果绘制成像素，生成绘制指令列表（不是真正写入屏幕）

6. **Composite（合成）：** 将不同图层（Layer）合并，通过 GPU 输出最终画面到屏幕

7. **关键阻塞关系：**
   - JS 阻塞 DOM 解析（因为 JS 可能修改 DOM）
   - CSS 阻塞渲染但不阻塞 DOM 解析
   - CSS 阻塞 JS 执行（因为 JS 可能访问计算样式）

---

### 回流（Reflow）和重绘（Repaint）的区别？如何优化？

**参考答案：**

1. **回流（Reflow）：**
   - 当 DOM 元素的**几何属性**（位置、大小）发生变化时，浏览器需要重新计算布局
   - 触发回流的操作：修改 `width/height/margin/padding/border`、修改 DOM 结构、改变字体大小、窗口大小变化、读取 `offsetWidth/offsetHeight/scrollTop` 等属性（强制同步布局）
   - **回流一定触发重绘**

2. **重绘（Repaint）：**
   - 当元素的**外观**（颜色、背景、阴影等）变化但几何属性不变时，跳过 Layout，直接 Paint
   - 触发重绘的操作：修改 `color/background/box-shadow/visibility`
   - **重绘不一定触发回流**

3. **优化方案：**
   - 批量修改 DOM：使用 `DocumentFragment` 或离线 DOM（先 `display:none`，修改完再显示）
   - 避免频繁读取强制回流的属性，如必须读取应缓存结果
   - 使用 `transform` 替代 `top/left`（不触发回流，走合成层）
   - 使用 `requestAnimationFrame` 将 DOM 修改集中在每帧开始时
   - 使用 CSS `will-change` 提升到合成层（避免影响其他元素）
   - 减少 CSS 选择器嵌套深度

---

### transform/opacity 为什么不触发回流？合成层的触发条件？

**参考答案：**

1. **为什么不触发回流/重绘：**
   - `transform` 和 `opacity` 的变化由 **GPU 在合成阶段**处理，不经过 Layout 和 Paint
   - 浏览器为这些属性单独创建一个合成层（Compositing Layer），GPU 直接对该层进行变换/透明度调整
   - 不影响其他元素，也不需要重新计算布局和绘制

2. **合成层（Compositing Layer）的触发条件：**
   - `transform: translateZ(0)` 或 `will-change: transform`（最常用的提升方式）
   - `opacity` 值发生变化（配合动画）
   - `position: fixed` 的元素
   - `video`、`canvas`、`iframe` 等元素
   - 有 CSS 动画或过渡（animation/transition）的元素
   - `overflow: scroll` 容器（滚动优化）

3. **`will-change` 的使用建议：**
   - 只在真正需要动画的元素上使用，不要滥用（每个合成层消耗额外内存）
   - 动画开始前设置，结束后移除
   ```css
   .animate-on-hover:hover { will-change: transform; }
   ```

---

### will-change: transform 如何优化性能？代价是什么？

**参考答案：**

1. **优化原理：**
   - `will-change` 告诉浏览器该元素即将发生指定属性的变化
   - 浏览器提前将该元素提升到独立的合成层
   - 动画发生时，只需 GPU 操作该层，不影响其他层，避免了触发整个页面的 Layout 和 Paint

2. **代价：**
   - **内存消耗：** 每个合成层都需要额外的 GPU 内存来存储该层的像素数据
   - **合成开销：** 合成层过多时，合并（Composite）多个层本身也有开销
   - **过度使用的问题：** 给所有元素加 `will-change` 反而会降低性能，导致内存不足、页面卡顿

3. **最佳实践：**
   - 只在需要动画的元素上使用，且在动画完成后移除
   - 配合 JS 动画使用：开始前 `el.style.willChange = 'transform'`，结束后 `el.style.willChange = 'auto'`

---

### 浏览器事件循环（Event Loop）原理？宏任务和微任务的执行顺序？

**参考答案：**

1. **事件循环基本流程：**
   - 执行当前调用栈中的同步代码
   - 调用栈清空后，清空**微任务队列**（全部执行完）
   - 从**宏任务队列**取一个任务执行
   - 执行完后再次清空微任务队列
   - 必要时浏览器执行渲染（render）
   - 重复上述过程

2. **常见微任务（Microtask）：**
   - `Promise.then/catch/finally`
   - `queueMicrotask()`
   - `MutationObserver`（属于微任务）
   - `async/await`（`await` 后的代码等同于 `Promise.then`）

3. **常见宏任务（Macrotask）：**
   - `setTimeout / setInterval`
   - `MessageChannel`
   - `requestAnimationFrame`（特殊：在渲染前执行，不完全算宏任务）
   - 用户事件（click、input 等）
   - I/O 操作

4. **关键规则：** 每执行一个宏任务后，必须**清空所有微任务**，才能执行下一个宏任务

---

### 代码题：混合执行顺序问题

**参考答案：**

```js
console.log('1')

setTimeout(() => console.log('2'), 0)

Promise.resolve().then(() => {
  console.log('3')
  queueMicrotask(() => console.log('4'))
})

async function asyncFn() {
  console.log('5')
  await Promise.resolve()
  console.log('6')
}

asyncFn()
console.log('7')
```

**执行顺序分析：**
1. `1`（同步）
2. setTimeout 回调入宏任务队列
3. Promise.then 回调入微任务队列
4. `asyncFn()` 调用 → `5`（同步），遇到 `await` 暂停，后续放入微任务队列
5. `7`（同步）
6. 调用栈清空，清空微任务队列：
   - `3`（Promise.then）→ 同时 `queueMicrotask(4)` 加入微任务队列
   - `6`（await 后续）
   - `4`（queueMicrotask）
7. 取出宏任务：`2`（setTimeout）

**输出：`1 5 7 3 6 4 2`**

### defer vs async vs 动态插入 script 的区别？type="module" 的加载行为？

**参考答案：**

1. **普通 `<script>`：**
   - 立即下载并执行，**阻塞** HTML 解析
   - 放在 `</body>` 前是常见优化手段

2. **`defer`：**
   - 异步下载，**不阻塞** HTML 解析
   - 等 HTML 解析完成后，**按顺序**执行
   - 适合有依赖关系的脚本（执行顺序有保证）

3. **`async`：**
   - 异步下载，**不阻塞** HTML 解析
   - 下载完**立即执行**，**不保证**执行顺序
   - 适合独立脚本（如统计、广告）

4. **动态插入 `<script>`：**
   - 默认行为类似 `async`（下载完立即执行）
   - 设置 `script.async = false` 可改为 defer 行为（保证顺序）

5. **`type="module"`：**
   - 模块脚本**默认行为等同于 defer**（异步加载，HTML 解析完后执行）
   - 模块内部的 `import` 依赖会递归异步加载
   - 模块代码自动在严格模式（'use strict'）下运行
   - 模块有自己的作用域，不污染全局

| | 阻塞解析 | 执行顺序 | 执行时机 |
|---|---------|---------|---------|
| 普通 script | ✅ | 顺序 | 立即 |
| defer | ❌ | 顺序 | DOM 解析完后 |
| async | ❌ | 不保证 | 下载完立即 |
| type="module" | ❌ | 顺序 | DOM 解析完后 |

## 五、浏览器架构与进程

### 浏览器多进程架构（Browser/Renderer/GPU/Network 进程分工）？

**参考答案：**

1. **多进程架构的优势：**
   - 一个 Tab 崩溃不影响其他 Tab（进程隔离）
   - 安全沙箱：渲染进程在沙箱中运行，即使被恶意代码利用，也难以影响操作系统

2. **各进程职责：**
   - **Browser 进程（主进程）：** UI 管理（地址栏、书签、前进后退）、Tab 管理、子进程启动/通信
   - **Renderer 进程（渲染进程）：** 每个 Tab/跨域 iframe 独立一个，负责 HTML 解析、JS 执行、布局、绘制
   - **Network 进程：** 所有网络请求（HTTP、WebSocket）统一由网络进程处理
   - **GPU 进程：** 接收渲染进程的绘制指令，通过 GPU 加速合成并输出到屏幕
   - **Plugin 进程：** 每个浏览器插件独立进程（现代浏览器已逐步淘汰插件）

3. **进程间通信（IPC）：** 各进程通过 IPC（Inter-Process Communication）消息传递通信，渲染进程无法直接访问磁盘/网络，需通过 Browser 进程代理

---

### Chrome 站点隔离（Site Isolation）是什么？为什么要做？

**参考答案：**

1. **站点隔离（Site Isolation）：**
   - Chrome 的安全策略，确保**不同站点的页面运行在不同的渲染进程**中
   - 即使同一窗口打开的 iframe，如果来自不同源，也运行在独立进程中（进程外 iframe，OOPIFs）

2. **为什么需要站点隔离——Spectre 漏洞（2018）：**
   - Spectre 是一种利用 CPU 推测执行（Speculative Execution）的侧信道攻击
   - 同一进程中的恶意代码可以读取同进程其他页面的内存（包括 Cookie、密码等）
   - 站点隔离确保不同站点的数据在不同进程的内存中，即使 Spectre 攻击成功，也只能读取同站点的数据

3. **对前端开发的影响：**
   - 使 `SharedArrayBuffer` 等高精度计时器 API 需要特殊 Header（COOP+COEP）才能使用
   - 跨域 iframe 无法直接通过 JS 访问父页面的 DOM

---

### COOP 和 COEP 是什么？为什么 SharedArrayBuffer 需要它们？

**参考答案：**

1. **背景：** 为了缓解 Spectre，Chrome 降低了 `performance.now()` 精度、限制了 `SharedArrayBuffer` 的使用（因为高精度计时器配合 SharedArrayBuffer 可以实现 Spectre 攻击）

2. **恢复使用的条件——跨域隔离（Cross-Origin Isolation）：**
   - 页面必须同时设置 COOP 和 COEP，进入"跨域隔离"状态
   - 跨域隔离状态下，浏览器保证该页面与其他跨域页面完全隔离，Spectre 攻击无法跨进程读取数据

3. **COOP（Cross-Origin-Opener-Policy）：**
   ```
   Cross-Origin-Opener-Policy: same-origin
   ```
   - 禁止跨域页面通过 `window.opener` 获取对当前页面的引用
   - 确保页面在独立的浏览上下文组（Browsing Context Group）中，与跨域页面没有共享内存

4. **COEP（Cross-Origin-Embedder-Policy）：**
   ```
   Cross-Origin-Embedder-Policy: require-corp
   ```
   - 要求页面加载的所有跨域资源必须显式声明允许被嵌入（通过 `Cross-Origin-Resource-Policy` 或 CORS）
   - 防止攻击者通过嵌入跨域资源（如图片）来探测其内容

5. **启用后可用的 API：** `SharedArrayBuffer`、高精度 `performance.now()`、`Atomics` 等

---

## 六、网络安全

### XSS 的三种类型及各自防御方案？

**参考答案：**

1. **反射型 XSS：**
   - 恶意脚本包含在 URL 参数中，服务端将其直接反射到响应 HTML 中
   - 需要诱使用户点击恶意链接
   - 防御：服务端对输出内容进行 HTML 转义

2. **存储型 XSS：**
   - 恶意脚本被存储在服务端数据库（如评论、用户名）
   - 其他用户访问时，恶意脚本被包含在页面中执行
   - 危害最大，无需诱导点击
   - 防御：存入数据库前过滤，渲染时转义

3. **DOM 型 XSS：**
   - 恶意脚本通过 JavaScript 直接操作 DOM 触发，不经过服务端
   - 如 `document.write(location.hash)`，URL Hash 含恶意脚本
   - 防御：避免使用 `innerHTML`、`eval`、`document.write` 插入不可信内容，改用 `textContent`

4. **通用防御方案：**
   - **输入验证：** 对用户输入进行白名单校验
   - **输出转义：** HTML 实体转义（`<` → `&lt;`），根据上下文（HTML/JS/URL）选择不同的转义方式
   - **HttpOnly Cookie：** 防止 XSS 通过 `document.cookie` 窃取 Cookie
   - **CSP（Content Security Policy）：** 最有效的防线，限制脚本来源

---

### CSP（Content Security Policy）怎么配置？script-src 'nonce-xxx' 是什么？

**参考答案：**

1. **CSP 的作用：** 通过 HTTP 响应头告诉浏览器只允许加载/执行来自指定来源的资源，即使注入了恶意脚本，也因来源不在白名单而被阻止

2. **配置方式：**
   ```
   Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.example.com; img-src *
   ```
   - `default-src 'self'`：默认只允许同源资源
   - `script-src`：指定 JS 允许的来源
   - `img-src *`：图片允许任意来源
   - `upgrade-insecure-requests`：将 HTTP 请求升级为 HTTPS

3. **nonce 机制（`script-src 'nonce-xxx'`）：**
   - 服务端为每次请求生成一个随机 nonce 值，放入 CSP 头和内联脚本标签
   ```
   Content-Security-Policy: script-src 'nonce-abc123'
   ```
   ```html
   <script nonce="abc123">// 合法的内联脚本</script>
   ```
   - 攻击者注入的脚本没有正确的 nonce，浏览器拒绝执行
   - 解决了"禁用所有 `unsafe-inline`" 与"需要内联脚本"的矛盾

4. **Report-Only 模式：**
   ```
   Content-Security-Policy-Report-Only: script-src 'self'; report-uri /csp-report
   ```
   - 违规时只上报不阻止，用于测试 CSP 策略

---

### Trusted Types 是什么？能防哪类 XSS？

**参考答案：**

1. **Trusted Types 是什么：**
   - 浏览器 API，要求向 DOM 插入 HTML 的代码必须经过"受信任"的处理函数（policy）处理
   - 开启后，直接将字符串赋给 `innerHTML`、`eval()` 等危险 API 会抛出异常

2. **解决的问题——DOM 型 XSS：**
   - 传统 CSP 可以阻止外部脚本加载，但无法阻止 JS 代码把字符串插入 DOM
   - Trusted Types 在"注入点"处拦截，要求所有 DOM 写入都经过白名单 policy

3. **使用示例：**
   ```js
   // 创建受信任的 policy
   const policy = trustedTypes.createPolicy('escape', {
     createHTML: (input) => input.replace(/</g, '&lt;').replace(/>/g, '&gt;')
   })

   // 使用 policy 创建受信任的 HTML，才能赋值给 innerHTML
   el.innerHTML = policy.createHTML(userInput)  // ✅
   el.innerHTML = userInput  // ❌ 抛出 TypeError
   ```

4. **CSP 配置开启：**
   ```
   Content-Security-Policy: require-trusted-types-for 'script'
   ```

### CSRF 攻击原理？为什么 SameSite=Strict Cookie 能防 CSRF？

**参考答案：**

1. **CSRF 攻击原理：**
   - 用户已登录 A 网站（浏览器保存了 A 的 Cookie）
   - 用户访问恶意网站 B，B 中包含向 A 发送请求的代码（如 `<img src="https://a.com/transfer?amount=1000">`）
   - 浏览器发送请求时自动携带 A 的 Cookie，服务端认为是合法用户操作

2. **为什么 SameSite=Strict 能防 CSRF：**
   - `SameSite=Strict`：Cookie 只在**同站请求**中发送，跨站请求**完全不携带**该 Cookie
   - 恶意网站 B 发起的对 A 的请求属于跨站请求，不会携带 A 的 Cookie，攻击失败

3. **SameSite 三个值：**
   - `Strict`：任何跨站请求都不带 Cookie（包括从外部链接点进来的 GET 请求，影响用户体验）
   - `Lax`：大多数跨站请求不带 Cookie，但顶层导航（点击链接）的 GET 请求例外（Chrome 默认值）
   - `None`：所有请求都携带 Cookie（需配合 `Secure` 使用，即只在 HTTPS 下发送）

---

### SameSite=Lax 有什么例外？Token 防 CSRF 和 SameSite Cookie 哪个更可靠？

**参考答案：**

1. **SameSite=Lax 的例外（允许携带 Cookie）：**
   - 顶层导航（用户点击链接 `<a href>`）的 GET 请求
   - `<link rel="prerender">` 预渲染
   - 表单 GET 提交（`<form method="GET">`）
   - 以上三种情况下，Lax Cookie 会随请求发送

2. **因此 Lax 无法防止的 CSRF：**
   - 诱使用户点击特定链接触发 GET 请求（如银行的 GET 接口）
   - 所以 GET 接口不应该有副作用（修改数据）

3. **Token 防 CSRF vs SameSite Cookie：**
   - **CSRF Token 更可靠：** Token 存储在 HTML 或 localStorage 中（非 Cookie），跨站脚本无法读取，防御更彻底
   - **SameSite Cookie 更方便：** 无需修改业务代码，浏览器原生支持
   - **最佳实践：** 两者结合使用
   - **SameSite 的局限：** 旧浏览器不支持；子域名可能被视为"同站"（如 `evil.example.com` 和 `bank.example.com` 是同站）

---

### 同源策略是什么？为什么浏览器要限制跨域？

**参考答案：**

1. **同源策略（Same-Origin Policy）：**
   - 同源 = 协议 + 域名 + 端口三者完全相同
   - 非同源的页面之间不能通过 JS 相互读取 DOM、Cookie、LocalStorage、IndexedDB

2. **为什么限制跨域：**
   - **保护用户数据：** 防止恶意网站通过 JS 读取用户在其他网站的 Cookie、账户信息
   - **防止 CSRF：** 配合 SameSite Cookie 限制跨域请求携带凭证
   - **防止信息泄露：** 防止攻击者通过跨域请求探测内网资源

3. **同源策略的限制范围：**
   - JS 发起的跨域 XMLHttpRequest / fetch 请求（需 CORS 授权）
   - 跨域 iframe 中的 DOM 访问
   - 跨域读取 Cookie/LocalStorage

4. **不受同源策略限制的：**
   - `<script src>` / `<img src>` / `<link href>` / `<iframe src>` 的加载（只能加载，不能读取内容）
   - 表单提交（CSRF 利用了这一点）

---

### 简单请求 vs 预检请求（OPTIONS）的区别？预检请求什么条件触发？

**参考答案：**

1. **简单请求（不触发预检）：**
   满足以下**所有**条件：
   - 方法：GET / POST / HEAD
   - Content-Type：`text/plain` / `multipart/form-data` / `application/x-www-form-urlencoded`
   - 没有自定义 Header（如 `Authorization`、`X-Custom-Header`）
   
   简单请求直接发送，服务端在响应头中返回 `Access-Control-Allow-Origin` 即可

2. **预检请求（Preflight）：**
   不满足简单请求条件时，浏览器先发 OPTIONS 请求询问服务端是否允许，服务端返回允许后再发实际请求
   
   **触发条件（满足任一即触发预检）：**
   - 方法：PUT / DELETE / PATCH / CONNECT 等
   - Content-Type：`application/json` 等
   - 包含自定义 Header

3. **预检请求响应头：**
   ```
   Access-Control-Allow-Origin: https://example.com
   Access-Control-Allow-Methods: POST, GET, OPTIONS
   Access-Control-Allow-Headers: Content-Type, Authorization
   Access-Control-Max-Age: 86400  // 预检结果缓存时间（秒）
   ```

---

### Access-Control-Allow-Origin: * 和指定域名的区别？为什么带 Cookie 时不能用 *？

**参考答案：**

1. **`*` 的作用：** 允许任意来源的请求，无需匹配具体域名，适合公开 API

2. **为什么带 Cookie 时不能用 `*`：**
   - 携带凭证（Cookie/Authorization）的请求是高权限操作，涉及用户身份
   - 如果允许任意来源携带凭证，任何恶意网站都可以代表用户发起请求
   - 因此规范要求：**当请求包含凭证时，`Access-Control-Allow-Origin` 必须指定具体域名**（不能用 `*`），同时需要 `Access-Control-Allow-Credentials: true`

3. **正确配置（带凭证）：**
   ```
   Access-Control-Allow-Origin: https://trusted-origin.com  // 不能是 *
   Access-Control-Allow-Credentials: true
   ```
   前端请求需设置：`fetch(url, { credentials: 'include' })`

### 点击劫持（Clickjacking）原理及防御？X-Frame-Options vs CSP frame-ancestors？

**参考答案：**

1. **点击劫持原理：**
   - 攻击者将目标网站（如银行转账页）嵌入透明 iframe，覆盖在诱饵内容上
   - 用户点击看似无害的按钮，实际点击了 iframe 中的操作按钮
   - 无需用户知晓，静默触发操作

2. **X-Frame-Options（旧方案）：**
   ```
   X-Frame-Options: DENY           // 禁止任何 iframe 嵌入
   X-Frame-Options: SAMEORIGIN     // 只允许同源 iframe 嵌入
   X-Frame-Options: ALLOW-FROM https://trusted.com  // 允许指定来源（部分浏览器支持）
   ```
   - 局限：`ALLOW-FROM` 兼容性差，只能指定一个域名

3. **CSP frame-ancestors（新标准，推荐）：**
   ```
   Content-Security-Policy: frame-ancestors 'none'           // 禁止嵌入
   Content-Security-Policy: frame-ancestors 'self'           // 只允许同源
   Content-Security-Policy: frame-ancestors https://a.com https://b.com  // 多个来源
   ```
   - 比 X-Frame-Options 更灵活，支持多个来源，是目前推荐的方案

4. **JS 防御（辅助）：**
   ```js
   if (window.top !== window.self) {
     window.top.location = window.self.location  // 强制跳出 iframe
   }
   ```
   但可被 iframe sandbox 属性绕过，不应作为主要防御手段

## 七、性能指标与实时通信

### LCP / FID / CLS 各测量什么？FCP 和 LCP 的区别？

**参考答案：**

1. **Core Web Vitals（核心网页指标）：**

   - **LCP（Largest Contentful Paint）：** 最大内容绘制，测量页面主要内容（最大可见图片或文本块）的加载时间，反映**加载性能**
     - 良好：≤ 2.5s
   
   - **FID（First Input Delay）：** 首次输入延迟，测量用户首次与页面交互到浏览器响应的时间，反映**交互响应性**
     - 2024 年已被 INP 替代，不再是 Core Web Vitals

   - **CLS（Cumulative Layout Shift）：** 累计布局偏移，测量页面加载过程中元素的意外位移总量，反映**视觉稳定性**
     - 良好：≤ 0.1

2. **FCP vs LCP：**
   - **FCP（First Contentful Paint）：** 首次内容绘制，第一个 DOM 内容（文本/图片/SVG）显示的时间
   - **LCP：** 最大内容元素绘制的时间，通常是首屏最大的图片或标题文字
   - LCP 比 FCP 更能代表用户感知的"页面有没有加载出来"（FCP 可能只显示了一个小图标）

---

### INP（Interaction to Next Paint）是什么？为什么 2024 年替换了 FID？

**参考答案：**

1. **FID 的局限性：**
   - FID 只测量页面加载后**第一次**交互的延迟
   - 只测量"浏览器开始处理"的时间，不包括实际渲染完成的时间
   - 很多页面 FID 很好，但后续交互（如点击按钮）仍然很慢

2. **INP（Interaction to Next Paint）：**
   - 测量用户与页面**所有交互**（点击、键盘输入、触摸）的延迟
   - 取所有交互中**最差的延迟**（第 98 百分位）作为指标
   - 延迟范围：从用户操作到**下一帧显示**（包含事件处理 + 渲染时间）
   - 良好：≤ 200ms

3. **改进意义：** INP 更全面地反映页面整个生命周期的交互性能，而不仅仅是首次加载时的一次交互

---

### 如何用 PerformanceObserver API 采集 Core Web Vitals 指标？

**参考答案：**

```js
// 采集 LCP
new PerformanceObserver((entryList) => {
  const entries = entryList.getEntries()
  const lastEntry = entries[entries.length - 1]
  console.log('LCP:', lastEntry.startTime)
}).observe({ type: 'largest-contentful-paint', buffered: true })

// 采集 CLS
let clsValue = 0
new PerformanceObserver((entryList) => {
  for (const entry of entryList.getEntries()) {
    if (!entry.hadRecentInput) {  // 排除用户主动触发的偏移
      clsValue += entry.value
    }
  }
  console.log('CLS:', clsValue)
}).observe({ type: 'layout-shift', buffered: true })

// 采集 INP（使用 event 类型）
new PerformanceObserver((entryList) => {
  for (const entry of entryList.getEntries()) {
    const duration = entry.duration
    console.log('Interaction duration:', duration)
  }
}).observe({ type: 'event', durationThreshold: 16, buffered: true })
```

**实际推荐：** 使用 Google 官方的 [`web-vitals`](https://github.com/GoogleChrome/web-vitals) 库，封装了上述逻辑并处理了各种边界情况：
```js
import { getLCP, getCLS, getINP } from 'web-vitals'
getLCP(console.log)
getCLS(console.log)
getINP(console.log)
```

### SSE（Server-Sent Events）vs WebSocket 选型？AI 应用为何大量用 SSE？

**参考答案：**

1. **核心区别：**

| 对比项 | SSE | WebSocket |
|--------|-----|-----------|
| 通信方向 | 单向（服务端 → 客户端） | 双向 |
| 协议 | 基于 HTTP | 独立的 ws:// 协议 |
| 断线重连 | 浏览器自动重连 | 需手动实现 |
| 数据格式 | 纯文本（UTF-8） | 文本或二进制 |
| 兼容性 | 好（IE 不支持，其他浏览器均支持） | 好 |
| 实现复杂度 | 简单（服务端只需 HTTP 长连接） | 较复杂（需 WebSocket 服务器） |

2. **AI 对话产品（ChatGPT/Claude 等）为何用 SSE：**
   - AI 模型是**流式输出**（token by token），天然是"服务端推送"场景
   - 客户端只需发一次请求，服务端持续推送生成的文字，不需要双向通信
   - SSE 基于 HTTP，与现有 CDN/负载均衡/代理基础设施天然兼容
   - 实现简单，无需专门的 WebSocket 服务器

3. **何时选 WebSocket：**
   - 需要双向实时通信：在线聊天、多人协作、游戏
   - 需要发送二进制数据
   - 延迟要求极低（WebSocket 开销更小）

---

### HTTP/1.1 下 SSE 有什么连接数限制？HTTP/2 下如何解决？

**参考答案：**

1. **HTTP/1.1 的连接限制：**
   - 浏览器对**同一域名**最多维持 **6 个** TCP 连接
   - SSE 的每个连接会占用一个 TCP 连接并保持不关闭
   - 如果同时打开多个 SSE 连接（如多个 Tab 或多个 SSE 源），很快用完 6 个配额，后续请求被阻塞

2. **HTTP/2 的解决方案：**
   - HTTP/2 的多路复用允许**单个 TCP 连接**上并发多个流（Stream）
   - 多个 SSE 连接可以复用同一个 TCP 连接，不受 6 个连接数的限制
   - 实际上 HTTP/2 下每个域名只需 1 个 TCP 连接

3. **其他解决方案（HTTP/1.1 下）：**
   - 使用 SharedWorker 让多个 Tab 共享一个 SSE 连接
   - 在不同子域名下建立 SSE 连接（变相绕过限制，但增加复杂度）

### Service Worker 生命周期（install/activate/fetch）？skipWaiting() 的作用？

**参考答案：**

1. **生命周期三个关键阶段：**

   - **install（安装）：**
     - SW 脚本首次被注册时触发
     - 通常在此阶段**预缓存**静态资源
     - 若 `event.waitUntil(Promise)` 的 Promise 失败，SW 安装失败，不会激活
     ```js
     self.addEventListener('install', event => {
       event.waitUntil(
         caches.open('v1').then(cache => cache.addAll(['/index.html', '/style.css']))
       )
     })
     ```

   - **activate（激活）：**
     - 旧版本 SW 不再控制任何 Tab 后才激活
     - 通常在此阶段**清理旧缓存**
     ```js
     self.addEventListener('activate', event => {
       event.waitUntil(
         caches.keys().then(keys =>
           Promise.all(keys.filter(k => k !== 'v2').map(k => caches.delete(k)))
         )
       )
     })
     ```

   - **fetch（请求拦截）：**
     - SW 激活后拦截所有受控页面的网络请求
     - 在此实现缓存策略（Cache First / Network First 等）

2. **skipWaiting() 的作用：**
   - 默认情况下，新版 SW 安装完成后，需要等所有旧版 SW 控制的 Tab 都关闭，才能激活
   - `self.skipWaiting()` 让新版 SW 跳过等待，**立即激活**取代旧版
   - 通常配合 `clients.claim()` 使用，让新 SW 立即控制所有 Tab
   - 注意：立即激活可能导致页面在同一会话中混用新旧缓存资源，需谨慎使用

| 主题 | 2022 前考法 | 2024–2026 新考法 |
|------|-------------|-----------------|

| TCP 握手 | 三次握手/四次挥手 | 结合 HTTPS 总 RTT、HTTP/3 对比 |
