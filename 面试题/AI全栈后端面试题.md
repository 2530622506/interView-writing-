## 一、后端与 HTTP 基础

### 1. 浏览器发出一个请求后，后端大致经历哪些环节？

- **参考回答：**请求先经过 DNS、TCP（HTTPS 还包括 TLS）等网络过程，到达网关或负载均衡；网关执行路由、鉴权、限流等通用逻辑，再转发到服务实例。服务端完成协议解析、参数校验、认证授权、业务处理，按需访问缓存、数据库或其他服务，最后将结果序列化并返回。日志、指标和 trace 应贯穿链路。

- 面试时不要只背网络层名词。要说明**每一层可能失败**：DNS 或网络失败、网关拒绝、服务超时、下游 RPC 异常、数据库慢、响应序列化失败等；排查时需要 requestId/traceId 将各层日志关联起来。

### 2. GET、POST、PUT、PATCH、DELETE 有什么区别？

| 方法 | 常见语义 | 关键点 |
|---|---|---|
| GET | 查询资源 | 语义上应安全且幂等；参数常放 URL，但不能据此放敏感信息 |
| POST | 创建资源或执行命令 | 通常不保证幂等；重复提交要结合业务设计 |
| PUT | 用请求表示替换资源 | 设计良好时通常幂等，重复执行得到相同目标状态 |
| PATCH | 部分更新资源 | 是否幂等取决于更新语义和请求内容 |
| DELETE | 删除资源 | 语义上通常幂等；重复删除可返回成功或资源不存在，按 API 契约约定 |

- 这是 HTTP 方法的**语义约定**，不是说不同方法天然带来安全、事务或权限保障。实际接口要有明确的请求/响应格式、状态码、鉴权规则和重复请求处理策略。

### 3. 常见 HTTP 状态码如何区分？

- `200`：请求成功并有正常响应；`201`：资源创建成功；`204`：成功但无响应体。
- `400`：请求格式或参数不合法；`401`：缺少有效身份认证；`403`：身份已知但无权访问；`404`：资源或路由不存在，也可按安全策略隐藏资源是否存在。
- `409`：请求与资源当前状态冲突，例如重复创建；`429`：触发限流。
- `500`：服务端未预期错误；`502/503/504` 常用于上游网关或服务不可用、超时等情况。

- 状态码与业务错误码是两层表达：HTTP 状态码描述协议层结果，响应体中的业务码可以细分“余额不足”“状态不允许”等。不要把所有失败都返回 `200`，否则监控、缓存和调用方重试判断都会变困难。

### 4. Cookie、Session 和 Token 有什么区别？

- Cookie 是浏览器向同一站点保存并自动携带的一种机制；Session 是服务端保存登录状态、客户端通常只拿到 sessionId 的模式；Token 是承载或索引身份声明的凭证，可以是有状态或无状态设计。JWT 是一种 Token 格式，不等于“加密后的用户信息”：签名通常用于防篡改，内容可能只是 Base64URL 编码，不能放秘密。

- 选择时要看客户端类型、跨域、撤销需求、存储安全和多端会话管理。Cookie 需要关注 `HttpOnly`、`Secure`、`SameSite` 和 CSRF；浏览器存储的 Token 要评估 XSS 窃取风险。无论哪种方式，服务端都必须校验身份和资源权限。

### 5. 同步调用和异步调用分别适合什么场景？

- 同步调用适合调用方必须立刻拿到结果才能继续的操作，例如查询或校验；链路简单、结果即时，但调用方会承担下游延迟和故障。

- 异步调用适合耗时较长、可以稍后完成的任务，例如发送通知、生成报表、更新搜索索引。它能解耦并削峰，但会引入任务状态、重复执行、失败重试、顺序和最终一致性等问题。不能只因为“异步更快”就把必须立即确认的业务结果异步化。

## 二、API 设计与服务端分层

### 6. 一个接口的参数校验应该放在哪里？

- 入口层做协议和基础校验：必填、格式、长度、数值范围；Service 层仍要守住业务不变量，例如用户是否有资格、状态是否允许流转。数据库约束（如唯一键、非空）可作为最后一道防线。校验不能只依赖前端，因为客户端可以被绕过或伪造。

- 错误响应应稳定、可识别，并避免把 SQL、堆栈、密钥等内部信息返回给调用方。对需要组合校验的请求，尽量一次性返回可操作的错误信息，而不是让用户反复试错。

### 7. Controller/Facade、Service、DAO/Repository 为什么要分层？

- 入口层负责协议适配、参数校验和响应转换；Service 承载用例或业务规则；DAO/Repository 负责数据读写。分层的价值是让每层职责清楚、测试更聚焦、实现可以替换，而不是为了层数多。

- 小项目不必机械地为每个方法建多层空壳。判断标准是职责是否混杂、业务逻辑是否可测试、数据访问是否泄漏到接口层，以及修改是否会牵连无关代码。

### 8. 分页接口怎么设计？偏移分页有什么问题？

- 小数据量或需要跳页时可用 `offset + limit`，但偏移越大，数据库可能需要扫描并丢弃很多行；并发插入/删除还可能让翻页重复或漏数据。大数据量、持续滚动列表可以考虑游标/seek 分页，例如按 `(created_at, id)` 作为稳定排序键，下一页查询大于上一页最后一个键的记录。

- 排序必须稳定且最好有匹配索引；限制单页最大条数。不要只用非唯一时间字段作游标，否则相同时间戳的数据可能被跳过。

### 9. 什么是接口幂等？怎么实现？

- 幂等是同一业务操作重复提交时，不会重复产生额外副作用。它对网络超时后的客户端重试、用户连点、消息重复投递尤其重要。

- 常见方案：客户端生成幂等键，服务端记录“键 + 请求结果”；数据库唯一约束防止重复创建；状态机只允许合法状态迁移；扣减类操作使用带条件的原子更新。幂等键需要有作用域、有效期和并发处理规则。前端禁用按钮只能改善体验，不能作为后端幂等保障。

### 10. 接口版本和兼容性怎么处理？

- 尽量采用向后兼容的演进：新增可选字段、保留旧字段一段迁移期、给新字段设置合理默认值；删除或改变语义属于破坏性变更，应有版本或分阶段迁移。发布时通常先部署能兼容新旧格式的下游，再逐步切换调用方，最后清理旧逻辑。

- “字段不删”不是绝对规则，长期兼容也有成本。应明确弃用时间、调用方迁移状态和回滚方案，并用契约测试或集成测试验证兼容性。

## 三、Java 与 Spring 常见问题

### 11. Java 中 `==` 和 `equals()` 有什么区别？

- 对基本类型，`==` 比较值；对引用类型，`==` 比较是否指向同一个对象。`equals()` 用于表达对象的逻辑相等，具体规则由类实现。重写 `equals()` 时必须遵守相等关系，并同步重写 `hashCode()`：相等对象必须有相同哈希值，否则放进 `HashMap`、`HashSet` 会出现难以理解的问题。

### 12. `HashMap` 适合什么场景？并发访问要注意什么？

- `HashMap` 是普通键值映射，适合方法内或由外部同步保护的场景；它不是线程安全容器。多线程读写时，使用合适的并发容器（如 `ConcurrentHashMap`）或锁，并思考复合操作是否原子。即便容器线程安全，“先判断不存在、再写入”这样的两步业务也不一定整体原子，需要原子 API 或额外同步。

### 13. Spring Bean 默认是单例，这意味着什么？

- 默认 singleton 表示 Spring 容器中一个 Bean 通常只有一个实例，不代表它自动线程安全。无状态 Service 通常适合单例；不要把某次请求的用户、临时结果放进可变成员变量，否则并发请求会互相覆盖。请求级数据应放局部变量、明确的上下文对象或框架提供的请求作用域中。

### 14. Spring `@Transactional` 常见失效原因有哪些？

- 常见原因包括：同类内部自调用绕过代理；方法或类不满足代理条件；异常被捕获吞掉；默认回滚规则与抛出的异常类型不匹配；事务方法中执行耗时外部 RPC，导致数据库锁持有过久；多数据源或线程切换后事务上下文未按预期传播。

- 事务注解不是“加上就万事大吉”。要确认代理调用路径、传播行为、隔离级别、回滚规则和事务边界。数据库事务一般只包住必要的数据操作，不宜把不稳定的远程调用随意放进长事务。

### 15. 线程池有哪些重要参数？为什么不能无限创建线程？

- 核心参数包括核心线程数、最大线程数、任务队列、空闲线程回收时间和拒绝策略。线程太多会造成上下文切换、内存和下游资源竞争；队列无限增长则会把过载延后，最终造成延迟和内存风险。

- 参数要结合任务类型（CPU 密集或 I/O 密集）、下游容量、延迟目标和压测结果确定。还要监控活跃线程、队列长度、拒绝次数和任务耗时，并设计拒绝后的降级或错误反馈。

### 16. 什么是死锁？怎么减少死锁风险？

- 多个事务或线程互相持有对方需要的资源，彼此等待，就可能形成死锁。数据库通常能检测并回滚其中一个事务，但应用仍须正确处理失败。

- 降低风险的方法：按固定顺序获取多把锁；缩短事务；减少锁范围；为查询提供合适索引，避免意外锁住大量记录；对可重试的死锁做有限次数、带退避的重试。重试前要确认操作具备幂等性。

## 四、MySQL、事务与索引

### 17. 数据库事务 ACID 是什么？

- **原子性（Atomicity）：**一次转账包含“账户 A 扣 100”和“账户 B 加 100”，不能只完成其中一步。发生异常时，两步一起回滚。
- **一致性（Consistency）：**事务前后都要满足业务不变量，例如账户余额不能小于 0、转账前后总金额守恒。数据库约束能帮忙，但正确业务规则仍需代码保障。
- **隔离性（Isolation）：**并发事务按隔离级别规定的规则互相可见。比如两个人同时抢最后一张票，不能都基于“库存为 1”成功扣减。
- **持久性（Durability）：**数据库确认提交后，即使服务进程重启，已提交结果也应由数据库恢复机制保留。
- **适用边界：**同一个数据库中的扣款和入账可以放在一个本地事务里；如果两个步骤在不同服务/数据库，本地事务不能自动覆盖全链路，要考虑 Saga、可靠消息和补偿。

### 18. 脏读、不可重复读、幻读是什么？隔离级别如何理解？

- **脏读**：读到其他事务尚未提交的数据。
- **不可重复读**：同一事务两次读取同一行，结果不同。
- **幻读**：同一范围条件重复查询，匹配到的行集合发生变化。

- SQL 标准常见隔离级别从低到高是 Read Uncommitted、Read Committed、Repeatable Read、Serializable；隔离越强通常越能限制并发异常，但也可能增加等待、锁竞争并降低吞吐。
- **通俗例子：**事务 A 正在修改一条订单但尚未提交，事务 B 是否能看到这个中间值，取决于隔离规则；若事务 A 回滚，事务 B 之前读到的值就属于脏读。
- **注意：**具体数据库对 MVCC 和锁的实现不同。MySQL InnoDB 常见默认值是 Repeatable Read，但线上需检查实际配置；不要只背“某隔离级别绝不发生某现象”而不说明数据库和读写方式。

### 19. 索引为什么能加快查询？有什么代价？

- 索引是为特定访问模式维护的有序数据结构。InnoDB 常见 B+ 树索引能缩小查找范围，并支持范围扫描和排序。索引会占磁盘与内存，写入时也要维护；索引过多会拖慢写入、增加存储和优化器选择成本。

- 建索引应从真实查询出发，结合过滤条件、排序、选择性和执行计划评估，而不是“常用字段都加索引”。

### 20. 什么是联合索引的最左前缀？

- 假设有联合索引 `(user_id, status, created_at)`，可以把它想成先按 `user_id` 排序；相同用户内再按 `status` 排序；相同状态内再按 `created_at` 排序。
- 通常能利用的连续前缀包括：`user_id`；`user_id + status`；`user_id + status + created_at`。
- 只按 `status` 查通常无法直接定位到索引中的连续范围，因为整个索引首先按 `user_id` 排序。
- **例子：**`WHERE user_id=7 AND status=1 ORDER BY created_at` 与索引顺序较匹配；`WHERE status=1` 则需要检查大量不同用户区间，通常无法像前一种查询那样高效定位。
- **易错点：**跳过中间列不代表后续列“完全没用”。优化器仍可能用索引扫描、索引下推或覆盖查询；范围条件也会影响后续列缩小范围的能力。最终要结合具体 SQL 和 `EXPLAIN` 判断。

### 21. 哪些情况可能导致索引效果变差？

- 常见原因：对索引列做函数或计算、隐式类型转换、字符串前置通配符、联合索引条件不匹配、低选择性字段、返回列过多导致大量回表、统计信息不准确。优化步骤是先确认慢 SQL 和执行计划，再根据扫描行数、实际耗时、索引选择和数据分布做针对性修改。

- 不要为了“强制走索引”就盲目加索引或使用 `FORCE INDEX`；小表全表扫描可能更快。优化后要对比真实数据量和典型参数验证。

### 22. 如何排查和优化慢 SQL？

1. 从监控、慢查询日志或调用链定位具体 SQL、参数和耗时分布。
2. 用 `EXPLAIN`（必要时使用实际执行计划能力）看访问类型、候选索引、估算行数、排序和临时表等信息。
3. 检查是否扫描过多、索引是否合适、是否发生回表、锁等待或返回数据过大。
4. 尝试减少返回字段和行数、调整联合索引、改写查询、优化分页或拆分不必要的关联。
5. 在相近数据量和并发下验证收益，并观察写入成本和其他查询是否退化。

- `SELECT *` 不是所有场景都绝对错误，但接口通常应只取所需列；分库分表也不是慢 SQL 的默认解法，应先定位瓶颈和数据增长趋势。

### 23. 什么是 MVCC？

- MVCC（多版本并发控制）通过保存数据版本，让符合条件的读操作读取某个一致性视图，减少读写互相阻塞。它与行锁配合，不等于“完全没有锁”。不同数据库对版本、快照和可见性规则实现不同；面试可结合 InnoDB 的 Read View 解释事务何时能看到哪些已提交版本。

### 24. 乐观锁和悲观锁怎么选？

- 悲观锁假设冲突频繁，先锁定资源再操作，例如数据库 `SELECT ... FOR UPDATE`；适合必须串行保护且冲突较多的短事务。乐观锁假设冲突较少，更新时带版本号或旧值条件，检查影响行数判断是否冲突；适合冲突较少、允许失败后重试的场景。

- 二者都不是“绝对安全/绝对高性能”。悲观锁要控制持锁时间和死锁风险；乐观锁要设计冲突反馈、重试上限，并避免高冲突下大量无效重试。

## 五、Redis 与缓存

### 25. Redis 常见数据结构及使用场景有哪些？

- String：缓存值、计数器、短时 Token。
- Hash：对象字段或小型映射。
- List：队列类场景（需评估可靠性能力）。
- Set：去重集合、成员关系。
- Sorted Set：排行榜、按分数排序。
- Stream：带消费组的消息流能力。

- 数据结构选择要看原子操作、数据规模、过期策略和恢复要求。Redis 不是所有数据的默认主存储；若数据不可丢且需要复杂查询或强约束，应选适当持久化存储并设计备份恢复。

### 26. 缓存穿透、击穿、雪崩有什么区别？

- **先看一次典型缓存查询：**

1. 应用先根据业务 Key（例如 `product:1001`）查询 Redis。
2. Redis 命中时直接返回缓存内容，不访问数据库。
3. Redis 未命中时，应用查询 MySQL，并通常把查到的结果写回 Redis。
4. 三类问题的共同风险是：某种原因让请求集中绕过缓存，数据库来不及处理。

#### 缓存穿透（Cache Penetration）

- **定义：**请求的数据在缓存和数据库中都不存在，缓存无法拦截它，每次请求都会打到数据库。
- **例子：**商品详情接口允许查 `productId=1001`。攻击脚本不断发送随机 ID（例如 `-1`、`999999999`）；Redis 每次都未命中，数据库也查不到，于是每次请求都执行一次无结果查询。
- **后果：**如果请求量很大，即使每次 SQL 很快，累计的无效查询也会占满数据库连接和 CPU，挤压正常用户请求。
- **常用处理：**
  1. **参数校验：**ID 必须是正整数、格式正确；明显非法的请求在访问缓存和数据库前拒绝。它挡得住格式错误，挡不住格式正确但不存在的随机 ID。
  2. **缓存空结果：**第一次查库确认不存在后，将“空对象/不存在”以较短 TTL（如几十秒到数分钟，按业务设置）放入缓存。之后同一个不存在的 ID 可由缓存拦截。代价是缓存占用，以及新创建数据可能在空值 TTL 内仍被误认为不存在，所以创建成功时可主动删除对应空缓存。
  3. **布隆过滤器：**在访问 Redis/DB 前快速判断某个 ID 是否可能存在。若明确不存在，可直接拒绝；若判断“可能存在”，仍需查缓存或数据库。布隆过滤器有误判“存在”的可能，不能保证查到数据；新增数据要及时更新，删除场景也要设计重建或计数型结构，不能把它当成数据库真相。
  4. **限流与监控：**按 IP、用户或接口限制异常请求速率，并观察不存在 ID 的比例。限流是保护措施，不代替数据校验。

#### 缓存击穿（Cache Breakdown / Hot Key Expiration）

- **定义：**某一个访问量很高的热点 Key 恰好过期或被淘汰，许多并发请求同时发现缓存未命中，一起查询同一份数据库数据。
- **例子：**热门商品详情每秒有数千次请求，缓存 TTL 都是 30 分钟。热点 Key 到期的瞬间，数千个请求都执行“查 Redis → 未命中 → 查 MySQL”；缓存重建尚未完成时，数据库已经承受了洪峰。
- **后果：**影响通常集中在一个或少数热点数据，但可能因数据库过载进一步扩散到其他接口。
- **常用处理：**
  1. **互斥重建：**缓存 miss 后，只有成功获取互斥锁的一个请求查库并重建缓存；其他请求短暂等待、重试读缓存，或返回可接受的兜底结果。锁要有超时、唯一持有者标识和安全释放；否则可能死锁，或误删别人的锁。要限制等待时长，避免把请求线程都堵住。
  2. **逻辑过期/后台刷新：**缓存数据本身不立即物理删除，而是在值中带业务过期时间。过期后先返回旧值，同时只触发一个后台任务刷新。优点是热点读取不必等待；缺点是可能返回短暂旧数据，且要处理刷新失败、任务重复和后台积压。仅适合业务允许短时间陈旧的内容。
  3. **提前刷新或延长热点 TTL：**识别高频 Key，在过期前刷新；或对允许陈旧的数据延长有效期。它降低过期瞬间风险，但需要热点识别和刷新机制，不能无限期保留变化敏感数据。
  4. **请求合并：**同一进程内可让同一 Key 的并发 miss 共享一个查询结果（single-flight）；多实例场景还需跨实例协调或接受每台机器各查一次。

#### 缓存雪崩（Cache Avalanche）

- **定义：**大量缓存 Key 在相近时间集中失效，或者 Redis 集群整体不可用，导致大量原本由缓存承接的请求集中回源数据库。
- **例子一：TTL 同时到期：**服务在发布/活动开始时批量写入几十万个配置 Key，并统一设置 1 小时 TTL。1 小时后这些 Key 集中失效，请求同时打到 MySQL。
- **例子二：缓存整体不可用：**Redis 网络故障或集群故障，应用的大量缓存读写失败；若应用无保护地直接回源，数据库会瞬间接住几乎全部流量。
- **形象比喻：**图书馆里 1000 本热门书都规定下午 5 点归还，读者恰好在 5 点集中来借；若图书管理员（Redis）此时也停工，所有人只能挤到仓库（数据库）逐本找书，仓库就会过载。
- **常用处理：**
  1. **TTL 加随机抖动：**不要让同批 Key 使用完全相同的过期时刻。例如基础 TTL 为 60 分钟，每个 Key 再随机增加 0～10 分钟，使失效请求分散。它缓解“同时到期”，不能解决 Redis 宕机。
  2. **缓存高可用：**通过合适的副本、故障转移、容量隔离和监控降低单点故障概率。Redis Cluster/Sentinel 等架构只能降低部分故障风险，不代表永不故障；应用仍要定义 Redis 不可用时的行为。
  3. **限流、熔断和降级：**检测到 Redis/数据库压力过高时限制非核心流量；对可降级数据返回默认值或短时旧值；核心业务保留受控容量。不能把关键交易数据随意用默认值替代。
  4. **本地缓存作为缓冲：**Caffeine 等进程内缓存可在 Redis 故障时承接一部分热点读，但各实例数据可能不一致、容量有限，且不能仅靠本地缓存保护所有数据。
  5. **预热和错峰：**发布或活动前分批加载热点数据，避免同时初始化；需控制预热速率，避免预热本身压垮数据库。
  6. **数据库保护：**连接池上限、并发隔离、查询超时和排队上限可以限制回源对 DB 的冲击。必要时快速失败比无限排队更能保护整体服务。

#### 三者对比

| 对比点 | 缓存穿透 | 缓存击穿 | 缓存雪崩 |
|---|---|---|---|
| 核心原因 | 查询的数据本来就不存在 | 单个热点 Key 失效，很多请求同时回源 | 大量 Key 同时失效，或缓存整体不可用 |
| 影响范围 | 大量不存在的 Key/特定异常流量 | 一个或少量热点 Key | 大范围缓存流量 |
| 常见例子 | 随机商品 ID 不断查库 | 热门商品缓存刚好过期 | 批量缓存同一时刻过期、Redis 故障 |
| 主要保护 | 校验、空值缓存、布隆过滤器、限流 | 互斥重建、逻辑过期、请求合并 | TTL 抖动、高可用、预热、限流降级和 DB 保护 |

#### 实际组合方式与边界

1. 普通缓存 Key 可加入 TTL 随机抖动，降低批量过期概率。
2. 对真正的热点 Key 单独加互斥重建或逻辑过期，不要给所有 Key 都加重锁。
3. 对非法参数先校验；对合法但不存在且可能被反复查询的 ID，可使用短 TTL 空值缓存；大规模 ID 集合再评估布隆过滤器的维护成本。
4. Redis 故障时应有限回源、限流或降级，不能让“Redis 高可用 + 本地缓存”成为没有容量边界的无限兜底。
5. **通用示例：**商品详情适合短暂返回旧缓存；账户余额、库存等强一致数据不能直接用陈旧值做扣减决策。
6. **与指定工程的关系：**学生认证 Service 使用 Redis `SETEX` 暂存短时 `bizToken` 流程数据，并用 TTL 控制有效期。这说明 Redis 可承载有时效的流程状态，但不是 Cache-Aside 热点数据缓存，不能据此声称该项目实现了穿透/击穿/雪崩防护。

- **面试总结：**穿透是“查的东西根本没有”，击穿是“一个热点刚过期”，雪崩是“很多缓存一起失效或缓存整体不可用”。先识别故障范围，再选择方案；没有一种单独措施能覆盖三类问题。
### 27. 如何处理数据库与缓存的一致性？

- **常见读流程：**先读 Redis；未命中再查 MySQL；查到后写回 Redis 并设置 TTL。
- **常见更新流程：**先提交 MySQL 更新，再删除对应缓存；下一次读请求再从数据库读新值并重建缓存。
- **为什么常选“删缓存”而非“同时更新缓存”？**更新缓存涉及并发覆盖：旧请求可能晚于新请求写回旧值。删缓存把重建交给后续读取，流程通常更简单。
- **仍然存在竞态：**读请求先从 DB 读到旧值并暂停；更新请求提交新值并删缓存；旧读请求随后把旧值写回 Redis。此时短时间内仍可能读到旧数据。
- **可选增强：**缓存删除失败时重试或发可靠消息；对允许短暂陈旧的数据延迟再删一次；对强一致要求的数据直接读权威存储或用版本号校验。每种方案都增加复杂度，需按业务一致性要求选择。
- **底线：**余额、库存等关键写入不能把缓存当唯一事实来源；数据库条件更新、事务或业务状态约束才是正确性的核心。

### 28. Redis 为什么常被用于分布式锁？实现时有哪些坑？

- Redis 可用原子写入（如带过期时间的 `SET key value NX PX ...`）竞争锁。释放锁必须确认当前值仍是自己的唯一标识后再删除，避免误删其他持有者的锁。锁需要过期时间防止持有者崩溃后永久占用，但过期过短可能出现任务尚未完成锁已失效。

- 重要场景还要考虑续租、时钟/网络延迟、主从切换语义和 fencing token（栅栏令牌）避免过期持有者继续写入。若数据库可通过唯一约束或条件更新解决，不一定需要分布式锁。

### 29. 缓存命中率高是不是就代表系统健康？

- 不一定。命中率高但缓存数据过期策略错误，可能返回陈旧数据；命中率高也可能掩盖热点 key、大 value、内存碎片或淘汰问题。还要看 Redis 延迟、错误率、连接池、内存、淘汰量、回源比例和数据库压力，并针对关键业务验证数据正确性。

## 六、并发、幂等与分布式

### 30. 进程内锁和分布式锁有什么区别？

- `synchronized`、`Lock` 等进程内锁只协调同一个进程中的线程；多个服务实例各自有自己的锁，互相看不到。分布式锁协调多个实例，但需要面对网络分区、租约过期、持有者暂停等问题，复杂度远高于本地锁。

- 先问是否真的需要跨实例互斥：有时唯一索引、CAS 更新、分片路由或单消费者机制更简单可靠。

### 31. 什么是限流？令牌桶和漏桶有什么区别？

- 限流控制单位时间允许的请求量，保护服务和下游。固定窗口实现简单但窗口边界可能突发；滑动窗口更平滑但实现成本较高。令牌桶按速率补充令牌，允许桶容量范围内的突发；漏桶以较稳定速率处理请求，更强调平滑出口流量。

- 限流策略应明确维度（用户、IP、接口、租户或全局）、超限响应、白名单和降级行为。只在单实例内限流无法天然形成集群全局配额。

### 32. 限流、熔断、降级分别解决什么问题？

- **限流**：控制进入系统的请求速率，避免自身或下游过载。
- **熔断**：下游持续失败时暂时停止调用，给依赖恢复时间并避免故障扩散。
- **降级**：非核心能力不可用时提供可接受的简化结果，例如隐藏非关键推荐区。

- 它们可以组合，但降级不能偷偷违反业务不变量。要定义恢复探测、超时阈值、错误比例和用户可见提示，并监控触发情况。

### 33. 什么是 CAP？为什么“只能三选二”容易误导？

- CAP 描述分布式数据系统在发生网络分区时，对一致性（Consistency）与可用性（Availability）的取舍，同时必须容忍分区（Partition tolerance）。不是任何时刻从三项中随意挑两项，也不是所有系统固定属于“CP 或 AP”。网络正常时的行为和具体一致性定义也很重要。

- 面试回答可用具体场景说明：分区发生时，是拒绝部分请求以维持一致，还是接受请求并允许短暂不一致；选择取决于业务能否接受错误余额、重复扣款或暂时读旧数据。

### 34. 什么是最终一致性？

- 多个系统通过异步消息或重试逐步收敛到一致状态。它提升解耦和可用性，但中间状态可能暂时不一致；设计时需要明确允许的延迟、失败告警、补偿机制、重复处理和对账手段。

- “最终”不能只靠希望。必须有可观测的处理状态、可重试错误分类、死信/人工补偿入口或周期性对账，并定义长时间未收敛的处置流程。

## 七、消息队列与异步处理

### 35. 消息队列解决什么问题？代价是什么？

- 消息队列常用于系统解耦、异步处理和削峰填谷。生产者把事件交给队列，消费者按自身能力处理，避免主请求同步等待所有后续任务。

- 代价是系统增加消息积压、重复投递、消费失败、顺序、延迟和链路追踪等问题。消息不能代替业务数据库，也不适合调用方必须立即拿到业务结果的场景。

### 36. 如何避免消息丢失？

- **生产端：**等待 Broker 的发送确认；发送失败或超时要记录并按有限策略重试。超时不一定代表 Broker 没收到，因此重试可能产生重复消息。
- **Broker：**按可靠性要求配置持久化、副本和故障恢复策略；要了解所用 MQ 对确认和持久化的具体语义。
- **消费端：**通常在业务处理成功后再确认消息；若先确认、后处理，进程崩溃时消息可能丢失；若先处理、后确认，崩溃可能导致重复消费，因此业务必须幂等。
- **数据库与发消息的一致性：**“先写 DB 再发 MQ”可能在两步之间崩溃，造成 DB 有记录但消息没发；“先发 MQ 再写 DB”则可能通知了尚未落库的业务。
- **可选方案：**Transactional Outbox 在同一 DB 事务中同时写业务记录和待投递事件，后台任务可靠发送；消费者再通过业务唯一键做幂等。代价是增加 Outbox 清理、重试、监控和积压治理。
- **运行保障：**监控发送失败、消费积压、重试次数和死信；为人工重放保留事件上下文和审计记录。

### 37. 消息队列能保证 Exactly Once 吗？

- 产品可能提供某种范围内的幂等生产或事务能力，但跨数据库、队列和外部服务的端到端“精确一次副作用”通常不能只靠 Broker 保证。工程上常以至少一次投递 + 消费端幂等 + 状态约束实现业务上的一次效果。

- 不要以消息 ID 是否重复作为唯一业务判断；应使用业务唯一键，并在数据库写入或状态迁移时原子地防止重复副作用。

### 38. 如何处理失败消息和重试？

- 区分可重试错误（临时超时、限流）与不可重试错误（格式错误、业务条件不满足）。采用有限重试、退避和抖动，避免失败时立即无限重试造成雪崩；多次失败进入死信或人工处理，并保留足够上下文。重放前先确认幂等和下游状态，避免重复扣款、重复发奖。

## 八、安全、稳定性与线上排查

### 39. 认证和授权有什么区别？

- 认证回答“你是谁”，授权回答“你能对哪个资源做什么”。登录成功不意味着可以访问任意用户的数据。服务端应基于可信身份上下文进行资源归属和权限检查，不能相信前端传来的 `userId` 就代表当前登录用户。

### 40. SQL 注入怎么产生，如何防止？

- 当程序把不可信输入拼接进 SQL 语句并作为 SQL 语法执行时，攻击者可能改变查询含义。使用参数化查询/预编译语句，将数据和 SQL 语法分开；动态排序字段、表名等不能作为普通参数绑定时，应通过白名单映射。ORM 也不能防住开发者主动拼接原始 SQL 的风险。

### 41. 如何保护个人敏感信息和密钥？

- 密钥放在密钥管理或受控配置系统，不写入代码仓库、日志或前端包；服务端按最小权限访问外部服务，支持轮换。身份证、手机号等个人信息按必要性收集、最小化保存，传输加密、存储加密或脱敏展示，并限制日志、监控和测试数据中的明文暴露。

- 日志中即使没有完整原文，也要评估组合字段是否可重新识别个人。发生泄露时应有密钥撤销、审计和事件响应流程。

### 42. 什么是超时、重试和熔断？为什么重试不能无限做？

- **超时：**为一次调用设置最长等待时间，避免线程和连接被永久占用。超时只说明调用方没及时得到响应，不一定说明下游没有执行成功。
- **重试：**针对短暂网络波动、限流等可恢复错误再次调用。应设最大次数、退避时间和随机抖动；参数错误、权限错误通常不应重试。
- **熔断：**当依赖在一段时间内持续失败时暂时停止调用，快速失败或走降级；经过冷却期再小流量探测恢复。
- **超时预算例子：**如果入口总预算是 1 秒，不能给三个下游各设置 1 秒并串行调用。要为自身处理和每个下游分配预算，并给调用链总时间留余量。
- **重试放大：**若每层都最多重试 3 次，层层嵌套可能把一次用户请求放大成多倍下游流量，形成重试风暴。
- **幂等要求：**请求可能已在下游成功、只是响应丢失。对创建订单、发权益等非幂等操作，应使用幂等键/业务唯一约束或先查询状态，避免重试产生重复副作用。

### 43. 接口突然变慢，你怎么排查？

1. 确认影响范围：单接口还是全站、所有用户还是特定流量、何时开始；看 P50/P95/P99、错误率和流量。
2. 用 trace 找耗时最长的服务段，判断时间花在本服务、RPC、数据库、Redis 还是线程池排队。
3. 检查近期发布、配置变更、流量变化和依赖状态。
4. 深入看慢 SQL 执行计划、锁等待、缓存回源、连接池/线程池队列和 GC 等证据。
5. 先止损（限流、回滚、关闭非核心功能或降级），再修根因并验证指标恢复。

- 不能只凭一条错误日志就下结论，也不要在没有定位证据时直接加机器或加索引。

### 44. 日志、指标、链路追踪各自解决什么问题？

- 日志记录具体事件和上下文；指标用低成本时间序列观察趋势、分位数和告警；链路追踪把一次请求跨服务的调用串起来，帮助定位耗时和错误位置。三者互补，通常通过 traceId/requestId 关联。

- 日志应结构化并注意脱敏；指标标签不要使用无限变化的用户 ID 等高基数字段；追踪采样要兼顾成本和故障分析价值。

### 45. 线程池或数据库连接池耗尽时会有什么现象？

- 请求可能在队列中等待，延迟升高并出现超时；超时重试又可能增加压力。应同时观察活跃数、等待队列、拒绝数、连接获取耗时和下游耗时。扩大池子不一定有用：下游容量有限时，更多并发会加剧拥塞。需要控制并发、缩短占用时间、隔离不同类型任务并为过载设计拒绝或降级策略。

## 九、AI 应用后端面试题

### 46. AI 全栈应用里，为什么模型调用通常要经过后端？

- 后端可以保护供应商 API Key，统一鉴权、额度、计费、审计、限流和模型路由；也可在服务端拼装业务上下文、执行检索、调用工具并过滤结果。若直接从浏览器调用受保护供应商接口，密钥容易泄漏，用户也可能绕过额度控制。

- 公开、无需密钥的客户端能力可以由前端直接使用，但凡涉及秘密凭证、付费额度或敏感业务数据，应由可信服务端控制。

### 47. 调用大模型 API 时要处理哪些工程问题？

- 至少考虑连接/读取超时、有限重试、限流与并发控制、供应商错误映射、成本和 Token 预算、输入输出校验、日志脱敏、用户取消和供应商不可用时的降级。不同错误要区别处理：鉴权错误不应盲目重试，限流可按响应建议退避，超时后重试前需评估重复计费和重复工具副作用。

- 将模型供应商封装在服务端适配层，业务层依赖统一接口，便于切换模型和做灰度；但不要为了抽象而丢掉供应商特有能力和诊断信息。

### 48. 如何实现流式输出？流式接口有哪些额外问题？

- 服务端可以把模型分段生成的内容以 SSE 或 WebSocket 等方式转发给客户端。要处理客户端断开后的上游取消、心跳、代理缓冲、超时、部分内容错误、结束标记和资源释放。流式输出降低首字延迟，但不一定降低完整答案总耗时，也增加连接占用和错误恢复复杂度。

- 如果生成过程会执行工具或改变业务状态，不应把“已输出一部分文本”误当成业务操作已成功提交；需要明确事务边界和最终状态。

### 49. RAG（检索增强生成）解决什么问题？

- RAG 在生成前从业务知识库检索相关片段，并把有限上下文提供给模型，目标是让回答贴近私有或更新较快的资料，并便于给出来源。常见链路包括文档清洗切分、Embedding、索引、召回、重排、上下文构造和生成。

- RAG 不保证答案一定正确：召回可能漏资料，文档可能过期，模型也可能误读。应做权限过滤、来源展示、文档版本管理、检索质量评测和无答案时的拒答策略。

### 50. 如何防止 Prompt Injection 和越权检索？

- 把用户输入、检索到的文档都视为不可信内容；模型提示词不能代替真正的权限系统。检索前依据用户身份过滤可访问文档；工具调用由后端逐次校验权限、参数和额度；高风险动作要求用户确认或业务规则校验。不要因为模型输出“用户有权限”就放行。

- 同时限制工具白名单、输入长度和执行时间，对输出做结构校验；避免把密钥、系统提示词或其他租户数据放进模型可见上下文。

### 51. AI 功能如何控制成本并评估效果？

- 成本控制包括模型分级路由、输入上下文裁剪、缓存可复用结果、设置每用户/租户额度、限制并发和最大输出长度。评估不能只看主观“回答不错”，还要定义离线样本、正确性/引用准确率、拒答率、延迟、成本和线上用户反馈，并持续回归。

- 缓存模型输出要考虑用户权限、上下文版本和个性化信息，避免把一个用户的结果泄给另一个用户。

### 52. AI 编程工具生成的后端代码能直接上线吗？

- 不能。AI 适合生成样板代码、测试草稿、解释陌生代码和提出排查思路，但可能误用 API、遗漏边界、引入安全问题或编造依赖。开发者仍需核对需求、检查权限与数据边界、补测试、做代码审查和运行验证；生产责任不能转交给工具。

## 十、学生认证项目实战题

> 本节根据用户提供的 `btocactivity` 学生认证实现提炼。下面区分**源码可确认的实现事实**与**面试时可讨论的通用改进方向**。业务实现会变化，面试前应重新核对当前代码，不要暴露真实个人数据、凭证或无关内部配置。

### 53. 请介绍一下这个学生认证流程，你负责的系统如何组织？

- **建议口述：**这是一个异步外部核验参与的认证流程。接口入口在 Facade 做用户身份和请求参数的基础校验；Service 负责组织业务步骤；认证前校验、实名核验、微信学生身份核验和身份信息写入等职责由不同 Handler 承担，通过共享的上下文对象传递阶段结果。用户提交信息后拿到短时业务 Token，进入小程序核验；回调到达后再读取 Token、完成学生身份核验并把认证结果写入中台。必要的附属权益发放与认证主结果分离，避免非核心权益失败反向影响认证成功状态。

- 只讲自己实际参与和能解释的部分。不要把项目说成单体三层的“controller 直接查库”，也不要把框架名堆成项目亮点。

### 54. 为什么提交接口返回 `bizToken`，而不是把所有表单数据放在客户端等回调再传？

- **源码事实：**提交阶段生成随机 UUID 形式的 `bizToken`，在 Redis 保存短时流程数据，包括用户 ID、活动 ID、学校、学历和入学年份；身份核验完成后由回调凭 Token 恢复业务上下文。实现注释明确说明身份明文不落库、不写日志、不进入 Redis；它只在当前请求上下文中暂存并用于核验调用。

- **设计价值：**客户端只需持有一个不可预测的流程引用，不必自行回传整份业务上下文；服务端可校验归属并设置过期时间。但 Token 本身是敏感的短期凭证，设计上应随机生成、绑定用户、限制有效期、避免写入可被滥用的日志，并在流程终态清理。当前参考代码的多处日志会记录 `bizToken`，这是面试中可以审慎讨论的日志脱敏/凭证暴露风险；不要把推荐做法误说成当前实现事实。它不是登录 Token，也不应成为长期授权凭证。

### 55. 如何防止用户拿别人的 `bizToken` 完成认证？

- **源码事实：**`verifyBeforeCert` 读取 Token 并校验其中的用户 ID 与当前登录用户一致；还会检查传入 `openId` 的绑定归属，若该微信在有效期内绑定了其他账号则拦截。认证成功后建立 `openId → uid` 的限时绑定记录。

- **重要边界：**可见的 `certCallback` 代码读取 Token 后继续处理，但未看到它在该入口再次比较 Token 内的用户 ID 与当前登录用户。因此不要笼统声称“回调入口也完成了归属校验”；如果由你负责设计，应在回调入口重新校验当前用户与 Token 绑定，或通过可信签名回调/一次性状态机制完成等价验证。关键校验必须由后端完成，不能相信前端页面状态；还需考虑 Token 过期、重放、并发回调、用户取消和失败重试。

### 56. 外部实名核验失败和外部服务故障，处理上有什么区别？

- **源码事实：**实名核验 Handler 将核验结果写入上下文；业务未通过与调用异常/无响应会被区分，后续映射为不同业务错误。这样用户信息不匹配不会被误报成系统故障，外部风控不可用也不会让用户误以为自己填错资料。

- **通用回答：**业务拒绝属于可解释的终态或可修改后重试；依赖超时、网络错误属于系统故障，应记录可观测信息并按安全策略重试或稍后重试。不能无限重试，也不能把异常吞掉后伪装成认证通过。

### 57. 回调链路如何处理多个步骤及依赖？

- **源码事实：**回调阶段通过 Handler 链组织外部微信学生身份核验、身份信息写入等步骤；写入 Handler 依赖核验结果，只有核验通过才写。微信 Access Token 获取与学生身份核验之间也声明了先后依赖；Service 在链路结束后统一裁决结果。认证成功后再写绑定关系、处理附属权益并清理流程 Token。

- **通用追问：**哪些步骤可并行，哪些必须串行？并行可以降低总延迟，但共享数据依赖必须显式表达；失败后需要清晰区分“核验失败”“依赖不可用”“写入失败”。外部调用超时预算应小于入口整体预算。

### 58. 认证成功了，但后续红包/附属权益发放失败怎么办？

- **源码事实：**当前实现将认证结果与附属红包权益区分；发放异常被记录，但不回滚已成功的认证，并返回可供前端展示的权益状态或失败提示。

- **设计解释：**这是按业务重要性划分主流程与附属流程。若权益必须最终送达，需要有领取记录、幂等重试、库存状态和对账补偿；若业务明确允许失败，则要让用户知道结果并避免重复发放。不要笼统回答“所有步骤放进一个事务”，跨服务发放通常不受同一个数据库事务保护。

### 59. 项目里如何处理敏感身份信息？

- **源码事实：**Service 类注释约定身份证明文仅用于核验调用、不落库、不写日志、不进 Redis，并在请求上下文中短暂传递。不过相关 Handler 会记录外部核验返回的 message，需核验供应商错误信息是否可能包含敏感字段；同时当前代码多处日志确实记录 `bizToken`。因此面试时应区分“代码注释中的数据处理约定”和“仍需审计的实际日志行为”，不能说整个链路已完全脱敏。演示时不要展示真实姓名、证件号或完整 Token。

- **改进讨论：**从日志框架、异常堆栈、APM 参数采集、线程池上下文和外部依赖全链路检查敏感值；对短时凭证使用不可逆摘要或关联 ID 代替原值，按最小必要原则做脱敏和访问控制，并明确数据保留周期。

### 60. 你会如何测试这条认证链路？

- **建议回答：**Facade 测参数边界和错误映射；Service 测分支和状态转换；Handler 对外部 RPC 使用 Mock/Stub 覆盖通过、拒绝、超时和异常；Redis 测 Token 归属、TTL、过期和重复回调；集成测试验证“核验成功后才能写身份”以及“附属权益失败不回滚认证”等关键不变量。再补并发重复提交、用户不匹配、回调重放和外部依赖变慢的场景。

- 测试应关注业务不变量，而不只是验证每个 Mock 被调用了一次。涉及真实敏感数据的测试应使用合成数据。

### 61. 如果重做这个流程，你会优先评估什么？

- 可以讨论：流程状态是否显式持久化、回调重放是否有稳定幂等键、Redis 不可用时的降级与一致性、外部依赖的超时和熔断、Token 失效后的用户恢复体验、异步补偿与对账、敏感信息全链路审计、关键指标和告警。

- 回答时先说明现有实现已解决什么，再明确这是待评估的改进，而不是声称项目已经有数据库状态机、消息队列补偿或 Exactly Once 能力。设计取舍要结合认证量、法规要求、失败恢复目标和团队运维能力。

## 十一、补充工程实践题

### 62. SQL 的逻辑执行顺序是什么？

- **常见逻辑顺序：**`FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT`。这是帮助理解查询语义的逻辑顺序，不代表数据库物理执行计划必须按这个顺序逐条执行；优化器会重排操作。
- **例子：**统计每个城市的有效用户数并只保留人数超过 100 的城市：

  ```sql
  SELECT city, COUNT(*) AS user_count
  FROM users
  WHERE status = 1
  GROUP BY city
  HAVING COUNT(*) > 100
  ORDER BY user_count DESC
  LIMIT 20;
  ```

- `WHERE` 在分组前筛行，因此通常不能直接用聚合结果；`HAVING` 在分组后筛组。
- 面试易错点：`SELECT` 别名在不同数据库/上下文里可用范围不同；更稳妥的写法是在 `HAVING` 中写聚合表达式，并以实际数据库语法为准。

### 63. 如果采用统一 API 返回格式，业务错误码和 HTTP 状态码如何配合？

- **通用原则：**HTTP 状态码表达协议层结果；响应体业务码表达应用层具体原因。比如参数格式错误可返回 `400`，未认证返回 `401`，库存不足可以在业务错误码中细分。
- **统一包装的好处：**调用方可以稳定读取 `code/message/data` 等字段，监控也能聚合业务错误；业务码应稳定、可枚举，不能拿易变的自然语言文案当判断条件。
- **需要避免：**把所有失败都包装成 HTTP `200` 会削弱网关、浏览器、监控系统基于状态码的判断；但若既有 RPC 协议统一用业务结果对象，也要遵循其契约并把协议错误与业务拒绝区分清楚。
- **转转专项材料口径：**`面试题3.md` 描述过 `ApiResult` 使用 `code=0` 表示成功、非 0 表示业务错误的模式。它是旧题库中的专项知识，不等同于已从 btocactivity 验证的全公司统一规范；面试前应按目标团队当前接口契约核实。

### 64. 分布式事务是什么？常见方案怎么选？

- **问题定义：**一个业务操作跨越多个服务或数据库，例如订单服务创建订单后还要扣库存、扣款。单个数据库的本地事务无法原子覆盖这些独立资源。
- **本地事务 + 可靠消息：**先在本地事务保存业务变化和待发送事件，再可靠投递；消费者幂等处理，最终收敛。可使用事务消息或 Outbox 等机制，但必须明确发送确认、重复投递、积压和补偿规则。
- **Saga/补偿事务：**每个服务提交自己的本地事务，失败时按业务设计执行补偿动作。补偿不是简单“回滚数据库”，例如退款可能是新的业务动作，也可能失败，需要状态机和人工兜底。
- **TCC：**Try/Confirm/Cancel 预留并确认资源，能较强地控制业务资源，但实现复杂、需要处理空回滚、悬挂和重复调用等问题。
- **选择思路：**先确认是否真的需要跨服务原子性、业务能否接受短暂不一致，再比较一致性要求、开发复杂度、恢复能力和用户体验。不要把 MQ 本身当成自动事务。
- **转转专项材料口径：**旧题库提到本地事务配合事务消息、状态机和消费幂等实现最终一致性；这属于题库里的团队实践说法，不能推断为 btocactivity 学生认证当前使用的机制。

### 65. `ThreadLocal` 在线程池中有什么风险？

- `ThreadLocal` 把值绑定在线程上，不是绑定在一次请求上。线程池会复用线程，如果请求结束后没有清理，下一次复用该线程的请求可能读到上个请求残留的用户信息或 traceId。
- **例子：**线程 T 处理用户 A 时设置 `userId=A`；任务结束未调用 `remove()`；线程 T 随后处理用户 B，若代码没有覆盖该值，就可能把 A 的上下文用于 B 的请求，造成串数据甚至越权。
- **处理方法：**在 Filter/Interceptor 或任务包装器中使用 `try/finally`，任务完成后调用 `ThreadLocal.remove()`；异步线程需显式、安全地传递必要上下文，不能假设自动继承正确。
- 线程池传递上下文时要防止敏感信息扩散，并测试异常、超时和任务取消路径，确保清理逻辑一定执行。

### 66. JVM 常见 OOM 有哪些原因？怎么排查？

- **Java heap space：**堆对象太多或大对象长期存活，例如一次查出几十万行并全部放进 List、无界缓存持续增长、对象被静态集合意外持有。
- **GC overhead limit / 长时间 GC：**可用堆很少，GC 频繁回收但释放不出足够空间，常和内存泄漏或峰值对象过大有关。
- **Metaspace：**类元数据过多或 ClassLoader 未释放，可能与动态生成类、重复部署或类加载器泄漏有关。
- **Direct buffer memory：**堆外直接内存使用过多或未及时释放；网络框架等可能使用这类内存。
- **排查步骤：**先看 OOM 类型、容器内存与堆配置、GC 日志和近期流量/发布；按需保留 heap dump 并用 MAT 等工具找大对象和引用链；结合线程栈、监控和代码确认根因。不要未分析就单纯扩大堆。
- **预防：**限制分页大小和批量任务规模、为缓存设容量/淘汰策略、避免无界队列、及时释放资源，并通过压测覆盖峰值数据量。
- **来源提醒：**旧版面试题举过“单次查询过多导致堆 OOM”的例子，这是合理的通用风险，不代表 btocactivity 发生过该故障。

### 67. 高并发库存/红包发放接口如何避免超发和重复发放？

- **先定义不变量：**同一用户同一活动最多领取一次；成功发放总量不能超过库存；失败、超时和重试后状态仍可恢复。
- **入口保护：**校验用户和活动资格；网关或服务端按用户/IP/活动做限流。前端按钮置灰只是体验优化，不能代替服务端校验。
- **原子扣减：**可用数据库条件更新（如 `stock > 0` 时扣减并检查影响行数），或 Redis 原子脚本完成预扣。单纯 `GET stock` 后再 `DECR` 会有并发竞态；Redis 预扣还要处理扣减成功但后续落库失败的补偿。
- **幂等去重：**使用业务唯一键（用户 + 活动/奖项）和数据库唯一约束兜底；Redis 状态可作快速拦截，但不能只靠“先查再写”两步非原子操作。
- **异步与一致性：**高峰时可排队处理，但需处理消息重复、丢失、积压、库存预留、失败补偿和最终对账；队列长度也要有上限，不能无限堆积。
- **项目边界：**btocactivity 学生认证流程含附属权益发放逻辑，但旧题库中的“Redis 预减库存 + ZZMQ 异步落库”不能据此认定为该工程当前实现；若作为面试设计题，应明确说这是候选架构方案。

### 68. 聚合接口要并发调用多个下游，怎么控制总耗时？

- 如果 5 个互不依赖的下游各耗时约 100 ms，串行调用总耗时可能接近 500 ms；并行调用的理论等待时间接近最慢的一个下游，但还要加线程调度、网络和汇总开销。
- **先梳理依赖：**无依赖请求并行；有依赖的步骤串行或按 DAG 分阶段执行，不能为了并发而破坏数据依赖。
- **设总预算：**入口总超时例如 800 ms，就要给网关、业务计算、各下游和响应组装分配预算；不能给每个下游各 800 ms 后再串行等待。
- **控制并发资源：**使用有界、隔离的线程池或异步客户端；设置队列上限、拒绝策略和下游并发限制，避免请求洪峰被无限排队。使用 `CompletableFuture.supplyAsync` 时显式传入业务线程池；不传线程池会使用公共 ForkJoinPool，阻塞式 RPC 可能影响其他任务。
- **部分失败降级：**非核心卡片可以用缓存/默认值，核心价格或权限信息则不能随意伪造。清晰区分部分成功、整体失败和超时，并记录具体下游耗时。`allOf` 只负责组合等待，不会自动提供默认值；还需用 `exceptionally/handle` 等处理异常。超时也不保证底层 RPC 一定被取消，应确认客户端取消语义。
- **转转专项材料口径：**旧题库把 Hulk 描述为轻量并发编排工具、Ultron 描述为 Handler/依赖编排框架、Hawkeye 用于线程池监控或管理。具体能力、API 和现行推荐需按目标团队资料核验；底层原则仍是依赖建模、超时预算、隔离与降级。

### 69. AI 全栈工程师与普通全栈工程师有什么不同？

- 两者都需要端到端交付能力：能理解需求、实现前后端功能、处理数据和上线问题。
- AI 全栈岗位通常还需要把模型能力工程化接入产品：选择模型/API、组织 Prompt 和上下文、处理流式输出、检索或工具调用，并评估延迟、成本、稳定性和效果。
- 关键不是“会写 Prompt”而已，还要守住鉴权、租户隔离、内容安全、个人信息保护和工具调用权限；模型输出不应未经校验直接执行高风险操作。
- AI 编码工具可以提升实现效率，但需求判断、代码审查、测试和生产责任仍由工程师承担。

## 十二、转转内部技术栈专项

> **来源说明：**本节整理自仓库已有 `面试题2.md`、`面试题3.md`、`面试题4.md` 中的转转专项口径。它们不都能由指定的 btocactivity 工程验证，内部架构、组件能力、工具名称及当前推荐可能随团队和时间变化；面试前请以目标团队的最新规范为准。回答时先解释通用原理，再说明题库中的专项说法，不要把未经核实的内容说成个人实际经历。

### 70. 转转专项接口规范里，为什么强调 Request 对象、BaseRequest 和入口校验？

- **Request 对象：**把一组相关参数封装成明确 DTO，比 `Map` 或多个裸参数更容易校验、阅读和兼容后续字段演进；响应也应有明确类型，避免把内部数据库实体直接暴露出去。
- **BaseRequest / kid：**旧面试材料称后台请求继承 `BaseRequest`（分页请求使用 `PageRequest`），其中带有操作人标识 `kid`，用于识别操作者和审计。该规则属于公司专项口径，适用范围和当前定义需核实。
- **分层校验：**格式、必填和范围等入口校验可用 JSR/Bean Validation 注解集中表达；Service 仍要校验业务不变量（如状态是否允许变更），不能为了避免重复而把业务安全寄托在 Facade 一层。
- **数据约定：**旧材料还提到金额按“分”等最小货币单位存整数，避免二进制浮点误差；同一业务字段在不同表里类型应一致。实际设计需明确币种、精度和舍入规则。
- **代码规范口径：**旧材料提到项目使用 MyBatis-Plus 封装常见查询/CAS，特殊 SQL 才落 Mapper；另强调限制 `pageSize`、枚举和实体字段保持稳定一致。ORM 只是实现工具，仍要检查生成 SQL 和执行计划。DDL 变更应走团队审核流程。
- **返回和异常：**遵循团队统一结果对象与错误码；内部异常应保留足够诊断信息，对外只返回稳定、用户可理解且不泄露堆栈的错误信息。远程结果可能为空，使用前需校验；分页参数要限制最大值。
- **来源边界：**以上 BaseRequest、kid、注解校验等来自 `面试题3.md`、`面试题4.md`，不能自动视为 btocactivity 所有接口的现行统一规范。

### 71. 读写分离会带来什么问题？刚写完为什么可能读不到新数据？

- **基本机制：**写请求进入主库，读请求可能被路由到一个或多个只读副本，以分担读取压力。
- **主从延迟：**主库事务提交后，变更需要复制到副本；在复制完成前从库仍是旧数据。因此“写成功后马上读”若路由到从库，可能读到旧值。
- **常见处理：**对读后写一致性敏感的短链路强制读主库；或使用会话粘滞、复制位点等待、版本校验等策略。不同方式在延迟、可用性和实现复杂度上有取舍。
- **不要默认所有读都能走从库：**订单状态、余额等场景要先定义允许的陈旧窗口。读主库比例增加又会提高主库负载。
- **转转专项材料口径：**`面试题3.md` 提到数据源代理层使用 ShardingSphere 做读写分离，并举 `MasterAccessor` 处理刚写后立即读的情况；这只是旧题库描述，需按目标团队当前组件和 API 核实。

### 72. 转转专项材料里的网关、SSO、JWT 和 `kid` 分别负责什么？

- **认证（Authentication）：**确认请求代表哪个用户/操作者；**授权（Authorization）：**判断该身份能否访问某个接口或数据。身份可信不代表对所有资源都有权限。
- **JWT：**一种可携带声明并通过签名验证的 Token 格式；签名用于验证完整性，不等于内容加密。JWT 便于跨服务传递身份，但主动撤销、密钥轮换和权限实时变更需要额外机制。
- **网关/SSO：**旧题库称 C 端由统一网关校验 Cookie 并接入 SSO，服务间通过 RPC 上下文传递调用信息，而不是每个业务服务自行签发登录 Token。具体流程需目标团队核实。
- **`kid`：**旧材料称后台请求对象包含操作人标识，用于权限校验或审计。它不是可由客户端随意填写并信任的认证凭证；服务端应从可信认证上下文校验其来源和权限。
- **面试回答重点：**说明身份在哪层建立、怎样安全透传、授权在哪里执行、如何审计，以及 Token/会话如何过期和撤销。不要仅说“有 JWT 所以接口安全”。

### 73. 为什么服务拆成 `contract` 和 `service` 两个模块？

- `contract` 通常放对外接口、请求/响应 DTO 等契约；调用方依赖契约包，不需要依赖服务实现代码。
- `service` 放接口实现和业务逻辑。这样可以隔离实现细节，并通过契约版本管理控制调用方升级节奏。
- 契约设计应保持向后兼容，避免把数据库实体、内部实现类型直接暴露出去；接口变更仍需协调发布顺序和调用方迁移。
- **btocactivity 工程可验证事实：**其 Maven 根工程包含 `contract` 与 `service` 两个模块；`README.md` 说明 contract 模块用于发布接口类、参数和返回值，service 是部署服务模块。模块编译配置并不相同：service source/target 为 Java 21，contract 为 1.8，因此不能将整个工程笼统称为 Java 8。

### 74. 转转“六层架构”是什么？为什么强调调用方向和领域边界？

- **旧题库给出的分层口径：**用户层、接入层、聚合/编排层、业务领域服务层、基础服务层、中间件/基础设施层。不同材料对层名和组件归属略有不同，面试时应以目标团队当前架构图为准。
- **强调向下调用的原因：**减少循环依赖和网状耦合；跨领域流程集中在编排层，领域服务保持职责清楚。
- **领域数据自治：**订单服务拥有订单数据，其他领域通过契约/RPC 使用能力，而不是直接读写对方数据库；否则表结构一变会牵连多个服务。
- **判断边界：**分层是治理依赖的工具，不是任何情况下都禁止服务间调用的自然定律；要按组织的领域划分和平台规范回答。

### 75. ZZSCF 是什么？RPC 和 HTTP 调用有什么区别？

- RPC（Remote Procedure Call，远程过程调用）让调用方以接口/方法形式调用远程服务，框架通常负责服务发现、序列化、负载均衡、超时和监控等能力。
- HTTP 是应用层协议；RPC 可以基于不同传输协议实现，不能把“RPC”和“HTTP”简单理解为互斥，因为很多 RPC 也使用 HTTP/HTTP2。
- **旧题库专项口径：**ZZSCF 被描述为转转内部 RPC 框架，并与内部注册发现、监控和配置体系集成。指定 btocactivity 工程中存在 SCF 注解和服务 Facade，但本文不据此推断所有 ZZSCF 特性或其与 Dubbo 的完整差异。
- 使用任何远程调用都要考虑网络超时、错误传播、版本兼容、重试放大和调用身份；不能像本地函数一样默认“必定成功”。

### 76. ZZMQ 解决什么问题？生产端和消费端要注意什么？

- 消息队列适合异步解耦、削峰和最终一致性；调用方不需要在主请求内等待所有后置任务。
- 生产端关注发送确认、持久化、重复发送以及数据库更新与发消息之间的一致性；消费端关注幂等、顺序、重试、死信和积压。
- **旧题库专项口径：**材料称 ZZMQ 是内部消息平台/对 RocketMQ 的封装，并提到平台注册、事务消息等使用方式。队列底层实现和具体 SDK/配置应按目标团队现行文档核实，不要只凭旧题库背 API。
- MQ 不会自动保证跨数据库和外部服务端到端 Exactly Once；仍需业务唯一键、状态约束和补偿/对账。

### 77. 什么是 `zzlock`？etcd 锁和 Redis 锁如何比较？

- 分布式锁用于多实例间互斥；进程内 `synchronized` 无法协调不同机器。
- 锁设计要处理租约/过期、唯一持有者、释放校验、持有者暂停、网络分区和过期后旧持有者继续执行等问题；关键写操作可结合 fencing token 或数据库条件更新。
- **旧题库专项口径：**材料称 `zzlock` 有基于 etcd 的实现，也存在 Redis 版本，并概括 etcd 偏一致性、Redis 偏性能。这个比较过于简化：正确性取决于具体实现、租约语义、故障模型和业务保护，不能仅凭中间件名字做绝对保证。
- 能用数据库唯一约束、CAS 或单消费者解决时，优先评估更简单的机制；分布式锁不是并发控制的默认答案。

### 78. 什么时候会考虑 MySQL、TiDB 或 Elasticsearch？

- MySQL 常用于事务型业务数据；索引、事务和成熟生态适合多数在线业务。
- TiDB 是分布式 SQL 数据库，常用于需要水平扩展和分布式存储/计算能力的场景；是否适合需结合事务模型、延迟、运维能力、成本和具体查询压测，不能简单说“大表就换 TiDB”。
- Elasticsearch 适合全文检索、相关性排序和复杂检索，不应直接取代事务数据库作为所有业务数据的权威来源；索引同步和最终一致性需要设计。
- **转转专项口径：**旧面试材料提及 MySQL、TiDB、ES 的用途划分。这是复习线索，不代表当前所有业务的统一选型规则；需按目标团队和实际负载核实。

### 79. Redis Cluster 和 Tendis 分别适合什么数据？

- Redis Cluster 通过分片扩展容量和吞吐，常用于低延迟缓存/计数等场景；它并不自动解决缓存一致性或所有高可用问题。
- **旧题库专项口径：**材料把 Tendis 描述为支持冷热分层、让冷数据落盘以降低内存成本的缓存方案，并把热点数据与大 value/低频数据作场景区分；还提到统一使用团队封装的 Redis 工具、设置 TTL、治理大 Key/热 Key。产品形态、部署方式和团队使用现状需核实。
- 选缓存要看访问热度、value 大小、延迟目标、淘汰策略、持久化和成本；不能只依据“哪个更快”或“哪个省内存”。
- 缓存失效、节点故障时仍要有回源限流、降级和数据库保护，缓存产品本身不是完整容灾方案。

### 80. Apollo 配置中心有什么用？动态配置需要注意什么？

- 配置中心把环境配置与业务代码/构建产物分离，支持集中管理、环境隔离和部分动态变更；适合功能开关、可调参数和服务地址等配置。
- 动态配置有风险：错误值可能快速扩散；需要权限控制、变更审计、灰度、校验、默认值和回滚能力。
- 机密凭证应使用合适的密钥管理能力，不应因为放进配置中心就认为天然安全。
- **转转专项口径：**旧面试材料将 Apollo 描述为配置中心，并举功能开关、限流参数和降级开关为例。具体 namespace、推送时效和平台规范须面试前核实。

### 81. 转转线上排障工具链怎么回答？

- 先按通用步骤说明：看告警和影响范围 → 用日志/trace 定位服务段 → 查 SQL、缓存、线程池或 JVM 证据 → 先止损再验证修复。
- **旧题库提到的工具名：**Prometheus/Grafana 看指标，ZZAPM 看链路，Arthas 做 JVM 在线诊断，日志平台查日志，iDB/Zeye 等用于数据库排查；工具的实际名称、权限和可用范围可能随团队变化。
- 不要只罗列平台名；应说清楚自己会看什么指标、如何缩小范围、用何种证据判断根因、如何回滚/降级和验证恢复。
- 复盘时补充影响范围、根因、止损措施、长期修复和防复发监控，而非只讲“重启后好了”。

### 82. Avengers 材料中的五个核心组件分别解决什么问题？

- **通用目标：**把无依赖的 RPC 并发执行，显式声明有依赖的步骤，设置总超时、任务隔离、异常处理和降级，避免串行等待拖慢接口。
- **旧题库专项口径：**材料把 Hulk 描述为轻量并发调用/聚合，把 Ultron 描述为基于 Handler 和依赖关系的事件编排，把 Hawkeye 描述为线程池构建/监控/调参，把 Hystrix 描述为隔离与熔断组件，把 Candy 描述为 Apollo 配置的可视化管理能力。
- 这些名称和边界来自旧题库，不保证当前版本仍如此，也不代表每个项目都必须使用全部组件。
- 不要把并发当作“越多越快”：线程池必须有界，下游要有限流，超时后还要取消或忽略迟到结果，并考虑部分失败。
- 具体组件 API 和职责边界请以目标团队代码与平台文档核实；回答可补充自己熟悉的 `CompletableFuture` 等通用机制作对照。

### 83. 什么是 FSM 状态机？为什么适合复杂业务流程？

- FSM（Finite State Machine，有限状态机）用有限个明确状态和合法事件/条件描述流程，例如“待认证 → 核验中 → 已通过/已拒绝/失败待重试”。
- **价值：**把散落在多个 `if/else` 中的状态判断变成显式迁移规则，便于限制非法跳转、记录状态和测试边界情况。
- **需要设计：**状态定义、事件、迁移条件、重复事件处理、超时和失败恢复；状态机本身不会自动解决分布式一致性或消息丢失。
- **例子：**认证回调重复到达时，状态机可以只允许“核验中 → 已通过”执行一次；已通过状态收到重复成功事件时返回既有结果，而不是重复执行业务副作用。
- **转转专项材料：**旧题库提到内部部分业务使用 FSM 并与异步任务/消息通知协作。不要据此声称 btocactivity 学生认证已使用 FSM；该工程当前源码应单独核对。

### 84. AI Agent 后端通常由哪些部分组成？

- **模型层：**负责语言理解和生成；通过服务端适配层管理模型供应商、超时、限额和流式输出。
- **工具层：**把检索、业务查询等能力封装成有输入输出契约的工具；每次工具调用都由后端校验参数、身份和权限，不能让模型自行绕过授权。
- **上下文/检索层：**管理会话上下文和知识检索，控制长度、来源、租户隔离和文档新鲜度。
- **运行时与治理：**管理任务步骤、状态、超时、重试、人工确认、审计和可观测性；长任务需要可恢复的状态，而不是只依赖一次 HTTP 请求。
- **转转专项材料：**旧题库把 Agent 概括为“大模型 + Harness 工程体系”，并提到内部研发工作台 `zzb2c-harness`，以及工具、记忆/检索、运行时、监控和安全权限。这是旧材料中的项目口径，不证明该工作台在目标团队中的现状或你本人参与过；面试时需核实并只讲自己的真实经历。

### 85. 为什么有些团队建议按 DB → contract → service → 上层调用方的顺序发布？

- **目标：**让发布过程保持向后兼容，避免新调用方先上线却调用了尚不存在的新接口，或新代码无法兼容旧表结构。
- **常见渐进式流程：**先做兼容性数据库变更（如新增可空字段/索引）；再发布兼容的新契约；部署能兼容新旧契约的服务实现；最后逐步切换上层调用方，确认无旧调用后再清理废弃字段或逻辑。
- **重要修正：**顺序不是所有变更都固定“DB 必须第一、contract 必须第二”。破坏性变更应采用 expand-migrate-contract：先扩展兼容能力、迁移读写、观察后再收缩；DDL 锁表和回滚风险也要评估。
- **转转专项材料：**旧题库给出 DB → contract → service → 上层 → 前端的示意发布序列。回答时重点讲“依赖兼容与分阶段迁移”，并按目标团队发布平台和具体变更核实顺序。

### 86. 上线前做架构自检，会检查哪些内容？

- **边界：**数据归属清楚；跨服务通过契约交互；没有绕层访问他人数据库或形成循环依赖。
- **接口：**参数校验、鉴权、错误码、幂等、兼容性和敏感信息处理到位。
- **可靠性：**下游超时、有限重试、限流/熔断/降级、线程池和连接池容量有明确策略。
- **数据：**索引和分页合理，缓存有 TTL/失效策略，消息有幂等、重试和积压告警。
- **可观测和发布：**日志/指标/trace 可定位；灰度、回滚、配置开关和数据迁移顺序已考虑。
- **转转专项：**旧题库还提到检查领域调用方向、聚合层职责、contract 不暴露实现、线程池使用团队组件等；具体红线需按目标团队当前规范核实。

## 十三、复习顺序与答题方法

### 建议优先级

- **P0：必须能讲清楚**：HTTP 状态码与接口设计、参数校验与鉴权、事务和索引、慢 SQL 排查、缓存穿透/击穿/雪崩、幂等、超时与重试、常见安全问题。
- **P1：能结合项目说明取舍**：Spring 事务边界、线程池、分布式锁、MQ 可靠性、限流/熔断/降级、线上性能排查、个人信息保护。
- **P2：理解边界并举例**：CAP、最终一致性、RAG、Prompt Injection、模型流式输出与成本治理。

### 单题口述模板

1. **定义**：先用一句话说清概念。
2. **场景**：说明它解决什么问题，什么情况下会用。
3. **做法**：讲清关键机制，而不是罗列名词。
4. **代价与边界**：说明失败模式、风险和不适用场景。
5. **项目例子**：只讲自己能核验和解释的事实，再补充可改进方向。

### 面试前自检

- 能否不用术语堆砌，向前端同事解释事务、缓存和幂等？
- 能否从一个慢接口沿 trace、RPC、缓存、SQL 一层层定位？
- 能否区分业务失败和系统故障，并解释各自的重试策略？
- 能否说清自己在项目中的职责、关键决策、失败处理和验证方式？
- 是否把通用建议误说成项目现状，或把 AI 生成代码当作已验证代码？
