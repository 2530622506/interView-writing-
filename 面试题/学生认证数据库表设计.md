# 学生认证数据库表设计

> 简历项目：学生专区 · 独立负责前后端全栈开发 · Spring Boot + MySQL + Redis

---

## ⚠️ 真实架构提示

学生认证功能 B2C 侧**没有自建 MySQL 业务表**。技术方案明确：

- "学生身份存中台，btocactivity 不新增表"
- "学生身份的存储、生命周期由中台学生身份系统承担，B2C 侧零开发"
- 业务状态全在 Redis：biz_token、魔方配置缓存、红包领取记录、助力集合等

面试中**不建议现编表结构**——一旦追问唯一约束、联合索引、慢查询优化，容易露馅。推荐**诚实回答真实架构**，反而显得设计思路清晰、有架构判断力。

---

## 推荐口述回答

> 学生认证这块，我们 B2C 侧其实没有自建业务表。学生身份数据是存在中台的——具体是 zzuser 服务的扩展字段，userExtendtype=3 标记学生信息，里面存学校名称、学历、入学年份。这样设计是因为学生身份有生命周期管理：到期失效、到期前 30 天提醒，这些能力中台学生身份系统是内建的，如果我们自己建表，到期扫描、提醒推送这些都要自己做，而且业务规则一调整就得改库。所以职责上，中台负责存储和生命周期，B2C 只负责认证成功时把算好的有效期传进去写入。

> 业务侧的状态我全放 Redis 了。比如认证用的 biz_token，承载 App 侧 uid 和表单数据，TTL 120 分钟，用完即删；红包领取记录用三态标记（未领/已领/库存耗尽），防重复发放；助力人集合用 Redis Set 天然去重。这些状态都是临时性的、读多写少、对一致性要求不强，放 Redis 比落 MySQL 更合适，也不用考虑索引设计。

> 唯一性约束这块是业务侧硬拦的，没靠数据库唯一索引。比如同一个身份证在有效期内只能有一份学生身份，这个同人排重是我在提交认证时调风控查同人 uid 列表，再批量查中台学生身份，任一有有效身份就拦截。这是个"先查后写"的设计，文档里也标注了已知残留——极端并发下同一人同时操作两个账号可能双双通过，产品知情接受。我选这个方案是因为中台写入接口不要求唯一约束，而我们又不想为了一个边缘场景去改中台的存储结构。

1. **显得有架构判断力**：能讲清楚为什么不建表、职责怎么划分，比"我设计了一张表，加了三个索引"高级。
2. **防追问**：面试官问索引，可以说"业务侧没建表，谈索引意义不大；如果要看中台那边的查询，是按 uid 查扩展记录，uid 上有索引，但那个表不是我设计的，我只调用"。
3. **诚实但专业**：承认先查后写的并发残留，本就是文档里产品知情接受的取舍，讲出来显得懂权衡。

## 中台真实表结构（zzuser 反编译确认）

> 来源：从 `zzuser.contract-0.8.45-sources.jar` 反编译，`UserExtendInfo` 实体带有 `@Table(name="user_extend_info")` 注解，字段与列名一一对应。

### 表名：`user_extend_info`

```sql
CREATE TABLE user_extend_info (
  extend_id          BIGINT       NOT NULL AUTO_INCREMENT COMMENT '扩展记录主键',
  uid                BIGINT       NOT NULL                COMMENT '用户 uid',
  user_extend_type   INT          NOT NULL                COMMENT '扩展信息类型（3=学生信息）',
  user_extend_content TEXT                                COMMENT '扩展内容 JSON',
  added_time         BIGINT                               COMMENT '记录创建时间（毫秒时间戳）',
  update_time        BIGINT                               COMMENT '记录更新时间（毫秒时间戳）',
  reset              TINYINT(1)                           COMMENT '是否重置标记',
  PRIMARY KEY (extend_id)
);
```

`user_extend_content` 中学生信息的 JSON 结构：

```json
{
  "studentInfo": {
    "schoolName": "清华大学",
    "education": 2,
    "enrollmentYear": "2024"
  }
}
```

| education 枚举值 | 含义 |
|-----------------|------|
| 1 | 大专 |
| 2 | 本科 |
| 3 | 硕士 |
| 4 | 博士 |

### 索引设计（推断）

从代码调用方式推断中台的查询模式：

| 查询方式 | 对应代码 | 推断索引 |
|----------|----------|----------|
| 按 uid 单查 | `getUserExtendInfoByUid(uid)` | `idx_uid`（uid 上的普通索引） |
| 按 uid 批量查 | `getUserStudentInfosByUids(uidList)` | 同上，走 `uid IN (...)` |
| 按 uid + type 过滤 | 查询后代码过滤 `userExtendtype=3` | 推断有 `idx_uid_type(uid, user_extend_type)` 联合索引 |

> 注意：表里没有唯一索引保证"一个 uid 只有一条学生记录"——这是设计上的已知缺陷，由 B2C 侧"先查后写"（先查 extendId，有则 update、无则 add）在应用层保证幂等，而不是依赖数据库约束。

## 如果自己设计，应该怎么弄？（面试标准答案）

> 面试官追问"如果让你自己设计这张表"时，用这个版本回答。

### 设计思路

学生认证的核心数据有两类：
1. **学生身份**：一个 uid 对应一份有效的学生认证记录，有有效期，认证状态需要快速查询
2. **认证流水**：每次认证动作的记录（用于审计、补偿、排查问题）

两类数据职责不同，拆成两张表。

---

### 表一：学生身份表 `student_identity`

```sql
CREATE TABLE student_identity (
  id              BIGINT        NOT NULL AUTO_INCREMENT  COMMENT '主键',
  uid             BIGINT        NOT NULL                 COMMENT '用户 uid',
  school_name     VARCHAR(100)  NOT NULL                 COMMENT '学校名称',
  edu_level       TINYINT       NOT NULL                 COMMENT '学历：1大专 2本科 3硕士 4博士',
  enroll_year     SMALLINT      NOT NULL                 COMMENT '入学年份',
  id_card_hash    VARCHAR(64)   NOT NULL                 COMMENT '身份证 hash（SHA-256，不存明文）',
  wx_open_id      VARCHAR(64)                            COMMENT '认证时绑定的微信 openId',
  status          TINYINT       NOT NULL DEFAULT 1       COMMENT '状态：1有效 2已毕业/失效',
  expire_time     DATETIME      NOT NULL                 COMMENT '有效期截止时间',
  created_time    DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  updated_time    DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_uid (uid),
  KEY idx_id_card_hash (id_card_hash),
  KEY idx_expire_time (expire_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='学生身份认证记录';
```

---

### 表二：认证流水表 `student_cert_log`

```sql
CREATE TABLE student_cert_log (
  id              BIGINT        NOT NULL AUTO_INCREMENT  COMMENT '主键',
  uid             BIGINT        NOT NULL                 COMMENT '用户 uid',
  cert_result     TINYINT       NOT NULL                 COMMENT '认证结果：1成功 2失败',
  fail_reason     VARCHAR(200)                           COMMENT '失败原因（失败时记录）',
  school_name     VARCHAR(100)                           COMMENT '用户填写的学校',
  edu_level       TINYINT                                COMMENT '用户填写的学历',
  enroll_year     SMALLINT                               COMMENT '用户填写的入学年份',
  wx_open_id      VARCHAR(64)                            COMMENT '本次认证使用的微信 openId',
  created_time    DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_uid (uid),
  KEY idx_created_time (created_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='学生认证流水';
```

### 索引设计说明（这部分是面试官最想听的）

**`student_identity` 表：**

| 索引 | 类型 | 原因 |
|------|------|------|
| `uk_uid` | **唯一索引** | 一个用户只能有一条有效学生身份，唯一索引同时保证了数据正确性和查询效率。查认证状态（`SELECT * FROM student_identity WHERE uid = ?`）是最高频操作，必须走索引 |
| `idx_id_card_hash` | 普通索引 | 同人排重需要查"这个身份证有没有被其他账号认证过"——按身份证 hash 查，不存明文是安全合规要求 |
| `idx_expire_time` | 普通索引 | 定时任务扫描到期记录（`WHERE expire_time < NOW() AND status = 1`）需要走这个索引，否则全表扫描 |

**`student_cert_log` 表：**

| 索引 | 类型 | 原因 |
|------|------|------|
| `idx_uid` | 普通索引 | 查某个用户的认证历史，客服排查问题时用 |
| `idx_created_time` | 普通索引 | 按时间范围统计认证量、排查异常时用；流水表数据量大，时间索引是标配 |

**为什么流水表不建联合索引 `(uid, created_time)`？**

> 流水表主要是写多读少的审计场景，按 uid 查的频率不高，先上单列索引够用。如果上线后发现按 uid 分页查历史是高频操作，再加联合索引——避免过早优化，多余索引会拖慢写入速度。

---

### 为什么不用 Redis 替代 MySQL 存身份？

| 维度 | Redis | MySQL |
|------|-------|-------|
| 持久化 | 非强持久（AOF/RDB 有窗口丢失风险） | 强持久，WAL 保证 |
| 唯一性约束 | 无，需业务层实现 | 唯一索引，DB 层兜底 |
| 到期扫描 | 需自己轮询或用 keyspace 事件（不可靠） | 定时任务 + 索引扫描，精准 |
| 数据量 | 全量常驻内存，成本高 | 冷数据不占内存 |

> 结论：Redis 适合存**临时会话态**（biz_token、助力集合），学生身份是**持久化业务数据**，应该落 MySQL。认证状态可以在 Redis 加缓存层提速，但 MySQL 是数据真源。

---

### 口述版本（一段话）

> 如果让我自己设计，我会拆两张表：一张 `student_identity` 存有效的学生身份，一张 `student_cert_log` 存认证流水。核心设计有几个点：第一，身份表在 uid 上加**唯一索引**，从数据库层面保证一个用户只有一条记录，比在业务层做先查后写更可靠；第二，身份证不存明文，存 SHA-256 hash，在 hash 字段上建索引，支持同人排重查询；第三，`expire_time` 上建索引，支持定时任务按时间扫描到期记录批量失效，不然数据量大了就得全表扫。流水表相对简单，uid 和时间各建一个索引，主要服务于排查问题和统计。

## 高频追问 8 题

### 一、接着表设计追问

**Q1：唯一索引 vs 业务层去重，怎么选？**

两层都要，职责不同。业务层先查是为了减少冲突频率，给用户友好的错误提示；DB 唯一索引是最后一道防线，有并发漏网时兜底报错，保证数据正确性。只靠业务层先查后写是不够的——先查和后写之间没有原子性，并发下两个请求都能通过查询然后都写入。

---

**Q2：expire_time 索引扫描会不会很慢？**

到期扫描加 `status = 1` 过滤，把单列索引换成联合索引 `(status, expire_time)` 更精准：

```sql
KEY idx_status_expire (status, expire_time)
-- 查询：WHERE status = 1 AND expire_time < NOW()
-- 先过滤有效状态，再按时间范围扫，失效记录被 status 过滤掉不参与扫描
```

status 基数低（只有 1/2），单独建索引意义不大，但放联合索引左侧能大幅收窄扫描范围。

---

**Q3：流水表数据量越来越大怎么处理？**

两个思路，可以叠加用：

1. **按时间分区**：`PARTITION BY RANGE (YEAR(created_time) * 100 + MONTH(created_time))`，历史分区直接 `DROP PARTITION`，比 DELETE 快几个数量级
2. **冷热归档**：超过 6 个月的数据定期迁移到 `student_cert_log_archive` 归档表，主表只保留近期数据，查询性能稳定

```sql
-- 归档 SQL 示例
INSERT INTO student_cert_log_archive
  SELECT * FROM student_cert_log WHERE created_time < DATE_SUB(NOW(), INTERVAL 6 MONTH);
DELETE FROM student_cert_log WHERE created_time < DATE_SUB(NOW(), INTERVAL 6 MONTH);
```

### 二、Redis 相关追问

**Q4：biz_token 存 Redis，宕机了怎么办？**

biz_token 是短期会话态，TTL 120 分钟，本身就是**可丢失的**。宕机了用户重新走认证流程填一遍表单，不会有业务数据丢失，代价是当前正在认证的用户体验略降。如果用 MySQL 存反而引入事务和慢写开销，得不偿失。临时状态适合放 Redis，持久化业务数据才需要 MySQL。

---

**Q5：Redis 缓存和 MySQL 数据不一致怎么处理？**

这个项目里 Redis 存的都是**临时状态**（biz_token、助力集合），不是 MySQL 数据的缓存副本，本身不存在双写一致性问题——Redis 就是数据真源。

如果后续加了认证状态的 Redis 缓存层，用**"先更新 DB，再删 Cache"**的策略：

```
1. UPDATE student_identity SET status=2 WHERE uid=?   -- 先写 DB
2. DEL student_cert:status:{uid}                      -- 再删缓存
```

不用"先删缓存再更 DB"——并发下删完缓存后、DB 还没更新时，另一个请求读到旧值写回缓存，缓存永远是脏的。

---

**Q6：Redis key 设计为什么用冒号分隔？TTL 怎么定的？**

冒号是 Redis 命名空间惯例，RedisInsight 等可视化工具会按冒号展示树形结构，运维查问题时一目了然。

TTL 与业务生命周期对齐：
- `biz_token` 120 分钟：跟微信 code 有效期对齐，给用户足够时间完成人脸识别
- 活动相关 key（助力集合、红包记录）活动结束 + 10 天：活动结束后仍有历史分享链接的存量流量，保留 10 天缓冲，到期自动清理不留脏数据
- 告警频控 key 1 小时：同一告警 1 小时内只发一次，防告警轰炸

---

### 三、事务和并发追问

**Q7：认证成功后写 DB + 发红包，需要事务吗？**

不需要强事务。设计上明确了"写 DB 成功再发红包，发红包失败不回滚认证"——认证是主链路，红包是附属权益。

原因：
- 认证结果写中台和发红包是两个不同的微服务，分布式事务成本很高（2PC 或 Saga）
- 红包发失败可以通过补偿解决——用户下次进专区页时触发补偿逻辑重新发放，最终一致即可
- 如果因为红包服务抖动回滚认证，用户体验反而更差

> 核心思路：用**补偿机制**代替分布式事务，主链路和附属链路解耦。

---

**Q8：同人排重先查后写有并发漏洞，更优方案是什么？**

理论上更严格的做法是在 `student_identity` 表的 `id_card_hash` 字段上加唯一索引：

```sql
UNIQUE KEY uk_id_card_hash (id_card_hash)
-- 并发写入时 DB 层报 Duplicate key error
-- 业务层捕获异常，返回"该身份证已完成认证"
```

这样即使两个请求并发通过了业务层查询，写入时 DB 唯一索引会拦住第二个，彻底消除并发漏洞。

本项目里没加是因为中台接口不归我们管，改不了它的表结构，只能退而求其次用业务层排重。如果是我自己建表，会同时加 `uk_uid` 和 `uk_id_card_hash` 两个唯一索引，分别防"同一账号重复认证"和"同一身份证多账号认证"。

### 补充：Redis 宕机 / TTL 过期后红包会重复发吗？

题目： 你说红包领取记录用三态标记防重复发放，放在 Redis 里——那如果 Redis 宕机了，或者 TTL 到期被清掉了，用户再来领，后端怎么判断他之前领没领过？会不会重复发红包？

**直接结论：正常场景不会，但有一个已知盲区。**

#### 防重链路（两道，不是只有 Redis）

```
第一道：Redis 本地记录 receiveStatus=2 → 跳过发放（快）
         ↓ Redis 宕机 / TTL 过期时失效
第二道：调 zzactivity queryRedByPlanId 查远端状态 → 已领取跳过（兜底）
```

发放前的代码逻辑：先查本地 Redis 记录，没有再查远端 zzactivity，两道都没拦住才真正发放。

#### 已知盲区：跨活动换 planId

第二道防重有一个前提：**查的是当前配置的 planId**。

```
1. 用户在旧活动用 planId=A 领了红包 → Redis 记录 receiveStatus=2
2. Redis TTL 到期，记录被清掉
3. 运营开新活动，配了新 planId=B
4. 用户进来：Redis 无记录 → 查远端 planId=B → 没领过 → 重复发放 ❌
   （远端查的是 B，查不到 A 下的领取记录）
```

> 文档原话：「远端查询按当前配置计划 id，查不到旧计划的领取状态——跨计划防重依赖①的本地记录，这也是记录 TTL 须覆盖活动全程的原因」

#### 现有方案的应对

**TTL = 活动结束 + 10 天**，覆盖整个活动周期，活动内记录不会过期。只要不跨活动、planId 不变，第二道兜底就够用。

#### 更完善的改法（改进点）

把领取记录落 MySQL，Redis 降为缓存层：

```sql
CREATE TABLE student_cert_red_record (
  id              BIGINT   NOT NULL AUTO_INCREMENT,
  uid             BIGINT   NOT NULL,
  activity_id     BIGINT   NOT NULL,
  plan_id         BIGINT   NOT NULL,
  red_type        TINYINT  NOT NULL  COMMENT '1延保 2裂变原始 3裂变膨胀',
  status          TINYINT  NOT NULL  COMMENT '1未领取 2已领取 3库存耗尽',
  red_envelope_id BIGINT             COMMENT '领取到的红包 id',
  created_time    DATETIME NOT NULL  DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_uid_activity_type (uid, activity_id, red_type)
);
```

Redis 宕机或 TTL 过期时降级查 MySQL，跨活动换 planId 也能靠 `(uid, activity_id, red_type)` 唯一索引防重，彻底关掉这个漏洞。

#### 面试口述版本

> Redis 的领取记录 TTL 到期后，本地第一道防重失效了，但还有第二道：发放前调 zzactivity 查远端领取状态，已领的会跳过。这道防重覆盖了大多数场景，但有个盲区——跨活动、运营换了 planId 的情况，远端查新计划查不到旧计划的记录，会重复发。我们的处理是让 TTL 足够长（活动结束 + 10 天）来覆盖这个窗口，活动内不会过期。更完善的方案是把领取记录落 MySQL 做持久化，Redis 作为缓存层，这样即使 Redis 丢了也能从 DB 查，跨活动换计划的场景也能靠唯一索引兜底。这个是我回头看的改进点，当时活动周期有限、跨活动换计划概率低，用 TTL 覆盖够用。

## 非数据库追问：流程设计 / 并发幂等 / 安全合规 / 容错降级 / 扩展性（13 题）

### 一、认证流程设计

**Q1：biz_token 为什么用随机串而不是加密 uid？**

- 加密 uid 只解决"明文不暴露"，不解决"被复用"——同一 uid 可能每次加密出相同密文，攻击者收集到密文就能重放
- 要达到同等安全需要叠加签名 + 时间戳 + 一次性校验，代码量反而更大
- 随机串（UUID 底层 SecureRandom）天然不可推导，天然防重放（短 TTL + 用后即删），实现更简单

---

**Q2：App 跳小程序，怎么防止 A 账号提交表单、B 账号来做人脸？**

- biz_token 生成时把 App 侧 uid 存入 Redis
- 小程序做人脸前调 `verifyBeforeCert`，反查 biz_token 取出 App 侧 uid，与小程序当前登录 uid 比对
- 不一致直接拒绝，返回「转转 App 与转转小程序登录的账号需保持一致」
- 用户根本进不了人脸流程，不消耗微信配额

---

**Q3：为什么把两道防复用校验放在人脸认证之前？**

- 微信人脸接口有单用户日查询次数上限（errcode 83401），注定被拒的请求不应消耗配额，否则会吃掉真用户的重试机会
- 放前面不通过直接告知用户，不让用户白做人脸，重试意愿更高，转化率更好
- 两道校验本身只是 Redis 查询 + 中台接口调用，成本极低，前置没有额外开销

---

### 二、并发与幂等

**Q4：certCallback（认证回调）被重复调用怎么处理？**

三层幂等保障：
- **biz_token 一次性**：写入成功后立即 DEL，同一 token 第二次调用直接 TOKEN_EXPIRED
- **wx_studentcheck_code 作幂等键**：微信侧 code 一次性 + 2 小时过期，中台写入以此判重
- **先查 extendId 再写**：写入前查该 uid 是否已有学生扩展记录，有则 update、无则 add，防止产生多条记录

---

**Q5：同人排重是先查后写，极端并发下有漏洞，怎么解？**

- 当前方案是已知残留，文档明确记载产品知情接受
- 理论上更严格的做法：在 `student_identity` 表的 `id_card_hash` 字段加唯一索引，并发写入时 DB 层报 duplicate key，业务层捕获异常返回"该身份证已完成认证"
- 本项目无法实现：中台接口不归我们管，改不了它的表结构；自建表可以加

---

**Q6：Redis SADD 助力集合是原子的，但查满额+发红包不是原子的，并发助力会不会重复发膨胀红包？**

不会重复发，两道兜底：
- 发放前查 `student_cert:red` 里膨胀位 receiveStatus，终态（2 已领取 / 3 库存耗尽）直接跳过
- zzactivity receive 接口本身有同一 uid 同一计划领取上限约束，并发下第二次调用会被拒绝
- 两道叠加：最多多打一次 receive 请求，但不会多发一份红包

---

### 三、安全与合规

**Q7：身份证明文为什么不落库？传输过程怎么保护？**

- 未实名用户身份证只用于透传风控做二要素核验，不落库、不写日志、不入 Redis（biz_token 里只存学校信息）
- 这是合规要求：业务侧不持久化用户身份证明文，降低数据泄露风险
- 传输靠 HTTPS，服务间走内网 SCF 调用；代码里 `realNamePlain / idCardPlain` 标注 `transient` 作语义说明，context 为方法局部变量，链执行完即被 GC

---

**Q8：微信 openId 为什么不能直接作为认证唯一标识？**

- openId 是"微信账号 + 小程序"维度的唯一标识，不是"转转账号"维度的
- 同一个微信登录不同转转账号时，openId 相同（同一小程序同一微信用户 openId 固定不变）
- 用 openId 存认证状态，A 账号认证完，B 账号用同一微信登录，查 openId 就能复用认证结果
- 正确做法：以 uid（账号稳定主键）作为认证记录的归属，openId 只用于校验微信绑定归属

---

**Q9：助力链接里的 uid 为什么要加密？用的什么算法？**

- 分享链接发到微信群，明文 uid 可被枚举遍历，伪造"谁邀请了谁"的助力归属
- 用 `OrderIdEncryptUtils`：AES/GCM/NoPadding + Base64 URL-safe 编码，密钥走 Apollo
- GCM 模式每次加密用随机 IV，同一 uid 每次产出不同密文，防枚举攻击
- 加密串只由助力回流侧（场景八）后端解密，前端不感知明文

---

### 四、容错与降级

**Q10：微信核验接口日限额 100 万，接近上限怎么办？**

- 系统接了飞书业务告警：errcode 83401 触发 MQ 推飞书群，频控 1 小时只发一次
- 没有自动降级放行，因为降级意味着非学生也能通过认证拿到权益，这是资损风险，属于业务决策不是技术决策，需要产品介入处理

---

**Q11：认证回调写中台失败，会不会数据不一致？**

- 写失败直接返回认证失败，引导用户重新认证
- biz_token 保留原 TTL，用户可以重试，重走 certCallback 即可（中台接口自身幂等）
- 不用 MQ 兜底是刻意简化：写失败概率低，用户重试能解决，MQ 兜底引入额外复杂度不值得
- 唯一不一致场景：写中台成功但网络超时没返回 → 用户以为失败，实际已认证 → 下次进专区页 queryCertStatus 返回已认证状态，自然收敛

---

**Q12：Avenger 并发框架某个 Handler 超时了，整条链路怎么处理？**

- 单个 Handler 超时不终止整条 pipeline，框架跳过该 Handler 继续执行
- 后续依赖它的 Handler 通过 `@DependsOn` 声明依赖，感知到前置 Handler 的 context 字段为 null，自行决定降级（跳过）还是透传异常
- 整条链路有全局超时（线上 600ms），超时后 `getEventWater().isError()` 返回 true，统一抛系统异常「服务开小差了」
- 关键链路 Handler（如微信核验）依赖的前置 Handler 失败 → 整条链路直接报错，不静默放行

### 五、业务扩展性

**Q13：如果以后要支持专科（3 年）、硕士（3 年）不同学制，现在的设计扩展起来方便吗？**

- 学制年数已经抽成 Apollo 配置 `student.cert.study.years`，默认值 4，改配置不改代码
- 更完善的扩展方式：把配置改成按学历分档的 JSON：
  ```json
  {"大专": 3, "本科": 4, "硕士": 3, "博士": 4}
  ```
  `StudentValidUtil.calcGraduateTime(enrollYear, eduLevel)` 按学历取对应年限计算毕业时间，产品定案后改一行配置即可，代码零修改
