P0 重点准备（接口与鉴权）

Q1：讲讲你对 RESTful API 的理解？你们公司接口是怎么设计的？
参考答案：
我先说通用理解，再说转转实际怎么做的。
通用层面：RESTful 是一种 API 设计风格——用 URL 表示资源，用 HTTP 方法（GET/POST/PUT/DELETE）表示操作，用状态码表示结果。但实际企业里很少严格遵守，更多是"资源命名 + 统一返回格式"。
转转实际做法：

1. 接口不是走纯 HTTP REST，而是走自研 RPC 框架 ZZSCF。对外暴露统一在 facade 层，内部 Service 层不直接暴露，保证服务边界清晰。
2. 入参必须封装成 Java 对象，比如 GetUserRequest，禁止用 Map，单个入参也要定义对象——这样后续加字段不用改接口签名，扩展性好。
3. 入参必须继承 BaseRequest（分页用 PageRequest），里面内置了 kid（操作人标识），这是权限校验和操作留痕的前提。
4. 批量查询接口推荐返回 Map<Long, User>，key 是实体 id，方便调用方直接索引，不用自己再转 Map。
5. C 端 URL 格式：https://app.zhuanzhuan.com/zzopen/{工程名}/{接口路径}，网关层会要求请求体包一层 request；管理后台走 leaseerpapi.zhuanspirit.com。
   一句话总结：转转不追求形式上的 RESTful，核心是"入参对象化、返回统一包装、facade 统一对外、批量接口返回 Map"。

Q2：HTTP 状态码你了解哪些？你们接口的错误码怎么设计？
参考答案：
通用状态码：200 成功、301/302 重定向、400 参数错误、401 未认证、403 无权限、404 不存在、500 服务器内部错误、502/503 网关错误。
转转的实际做法（重点）：
转转不靠 HTTP 状态码表示业务错误，而是统一用 SCF 框架封装的 ApiResult 返回：

设计要点：

1. code=0 成功，业务失败用非 0 错误码，框架能统一监控。
2. 禁止通过抛异常表示业务错误，对外接口必须用错误码传递；但服务内部可以抛异常，方便事务回滚。
3. 异常信息统一封装成用户友好提示，不能把技术堆栈直接返回给前端用户。
4. 比如红包库存不足，会返回特定错误码 PLAN_META_STOCK_EMPTY，前端根据 code 判断展示什么文案。
   {
   "code": 0, // 0 表示成功，非 0 表示业务错误
   "message": "错误信息",
   "data": {}, // 业务数据
   "appName": "xxx", // 内置应用名
   "ip": "x.x.x.x" // 内置实例 IP，方便排查
   }

Q3：JWT 鉴权是什么？你们公司登录鉴权怎么做的？
参考答案：
JWT 通用原理：JWT（JSON Web Token）是一种无状态鉴权方案——服务端签发一个包含用户信息的 token，客户端每次请求带在 Header 里，服务端验签即可，不用存 session。优点是分布式友好，缺点是 token 签发后不好主动失效。
转转实际做法：

1. C 端请求通过统一网关 zzGateWay，鉴权、反爬、HTTP 转 RPC 都在网关层做。前端请求时带上 cookie，网关识别用户身份。
2. 登录走 SSO 统一单点登录（测试环境 tzzsso，线上 zzsso），不是每个服务自己发 token。
3. 入参 BaseRequest 内置 kid（操作人标识），后台接口靠 kid 做权限校验和操作留痕——这就是为什么规范要求所有后台接口入参必须继承 BaseRequest，否则新增/编辑接口连"谁操作的"都记不下来。
4. 跨服务调用走 ZZSCF RPC，调用方身份、权限由框架透传，业务代码不用自己处理 token。
   一句话：转转不是纯 JWT，而是"网关 + SSO + kid 操作人标识 + RPC 透传"的组合方案，业务层只认 BaseRequest 里的 kid。

Q4：入参校验怎么做？
参考答案：
转转规范：

1. 校验统一在控制层（facade/controller）完成，业务 Service 层不重复做非空校验，避免相同逻辑写两遍。
2. 优先用 JSR 注解校验（javax.validation），比如 @NotNull、@NotBlank、@Min，参数多时用注解，不手写一堆 if。
3. 业务异常用断言抛，比如金融服务用 FinanceBizAsserts，不要自己写 if (x == null) throw new RuntimeException()。
4. 几个硬规矩：
   ○ 入参必须定义对象，禁止 Map、禁止多个裸参数（如 update(Long id, Integer status) 必须改成 update(UpdateRequest request)）
   ○ 远程调用返回对象一律先做非空判断，防止 NPE
   ○ 警惕 a.getA().getB().getC() 这种级联调用
   ○ 包装类型自动拆箱可能 NPE

Q5：错误/异常怎么处理？
参考答案：
转转分两层处理：

1. 服务内部：直接抛异常
   ● 抛运行时异常（com.zhuanzhuan.scm.exceptions 包下的各类异常），方便事务回滚
   ● 不能吞异常——catch 里必须用 error 级别打印日志，不能打印完日志就 return，那样容易埋坑
   ● 调用第三方接口失败或返回不对，要抛异常，不能当成正常流程 return
2. 对外接口：用错误码，不把异常抛出去
   ● Facade 层有统一异常处理切面，自动捕获异常、打印日志、上报服务管理平台监控
   ● 业务代码里 RuntimeException 一般不用自己 catch，交给切面统一处理
   ● 最终返回给前端的是 ApiResult 的 code + 用户友好 message，不暴露技术细节

日志分级：流程信息用 info、业务中断用 warn、业务异常用 error。

P1 重点准备（数据库、缓存、并发）

Q6：数据库索引原理？怎么建索引？慢查询怎么排查？
参考答案：
索引原理：MySQL InnoDB 默认 B+ 树索引，叶子节点存数据或主键，范围查询友好。联合索引遵循最左匹配原则。
转转实际做法：

1. ORM 统一用 MyBatis-Plus，特殊情况才在 mapper 写注解 SQL。简单查询和 CAS 乐观锁更新直接用 Example，不用自己写 SQL，开发效率高。
2. 读写分离在数据源代理层用 shardingsphere 做，业务代码无感；需要强制读主库的场景用 MasterAccessor（比如刚写完马上要读，避免主从延迟）。
3. DDL 变更走 iDB 平台审核，而且有个坑——DDL 语句结尾必须加 inception_magic_commit;，否则 SQL 审核过不了。
4. 表设计硬规矩：
   ○ 金额字段统一用"分"（避免浮点误差）
   ○ 同一字段在不同表里必须同类型同长度
   ○ 表里禁止塞非直接相关字段（比如订单表里塞审核结果）
   ○ 枚举用英文字符串，禁止用数字
   ○ 实体属性用包装类型，不设默认值

慢查询排查：先看 ZZAPM 链路定位是哪条 SQL 慢，再到 iDB 平台看执行计划，确认是不是没走索引，最后加索引或改 SQL。

Q7：缓存怎么用？缓存穿透/击穿/雪崩怎么解决？
参考答案：
转转实际用 Redis（含 Tendis 冷热分离），而且所有 Redis 操作统一用团队封装的工具类，不自己写连接逻辑。
结合红包/助力场景讲（这是我最熟悉的）：

1. 数据结构选型：助力去重用 Redis Set——同一用户给同一邀请人助力，Set 自动去重；助力人数直接用 Set.size() 拿，不用单独维护计数字段，避免计数不一致。
2. Key 命名规范：统一 活动ID + 业务维度 + 用户ID，用占位符拼接，不硬编码。
3. 缓存写入时机：状态变更完成后立即写 Redis，后续请求直接读缓存，不重复调下游。
4. 过期时间：按活动周期设置，不设过短 TTL，避免缓存频繁失效压垮下游。
   三大问题对策：
   一致性原则：没有强一致要求的场景优先用缓存，降低下游压力；但要平衡一致性和性能。
   问题 对策
   穿透（查不存在的数据） 缓存空值 / 布隆过滤器
   击穿（热点 key 过期瞬间大量打 DB） 互斥锁 / 逻辑过期
   雪崩（大量 key 同时过期） TTL 加随机偏移、过期时间按活动周期错峰

Q8：并发问题怎么解决？接口幂等怎么做？
参考答案：
转转并发控制主要靠这几层：

1. 幂等性（最高优先级）
   ● 红包发放、权益发放这类核心接口必须做幂等，防止重复请求导致重复发放。
   ● 实际做法：发红包前先查 Redis 领取状态，已领取直接返回，不重复调下游；发放成功后立刻把状态写回 Redis。
   ● 助力场景用 Redis Set 天然去重。
2. 乐观锁
   ● 用 MyBatis-Plus 的 Example 做 CAS 更新（带版本号或条件），不加锁也能防并发覆盖。
3. 分布式锁
   ● 定时任务多实例跑、库存扣减等强一致场景用 zzlock（etcd 版强一致 / Redis 版高性能）。
4. 事务规范（很重要）
   ● 事务范围尽量小，能不用就不用（影响 DB QPS）
   ● 事务注解严禁打在接口和类上
   ● 事务里禁止做 RPC/HTTP 调用、禁止发 MQ——否则事务时长拉长、数据库连接被占住，还会有分布式一致性问题

5. 线程池和熔断：都用团队封装好的标准组件，不自己 new，避免参数配错。

P2 了解即可（MQ、微服务、分布式事务）

Q9：消息队列怎么用？
参考答案：
转转用 ZZMQ（底层 RocketMQ 封装）。

1. 生产端：业务里直接用事务消息模板 MQTransactionTemplate，保证业务和发消息的一致性。
2. 消费端：实现 GranularMessageListener 接口，配置 zzsc.mq 相关属性即可。
3. 状态机集成：基于状态机的业务，发消息逻辑自动集成，业务代码不用手动发。
4. 监控：MQ 消费者异常配置 zzsc.mq.consumer.exceptionZZMonitorKey 自动上报警。
5. 原则：MQ 不放在事务里发；消费端要做幂等。

Q10：微服务你们怎么拆的？服务之间怎么调用？
参考答案：

1. RPC 用 ZZSCF，服务之间不走 HTTP。接口定义在 contract 模块（发私有 Maven），实现放在 service 模块，下游依赖 contract jar 就能调。
2. 分层：Facade（对外）→ FSM 状态机 → Service（业务）→ Manager（复杂下游依赖封装）→ DAO（MyBatis）。
3. 服务边界：领域服务之间不横向调用，跨领域走编排层；对接下游只引入官方 contract 包，不关心下游内部实现。
4. 超时：生产环境接口默认超时 600ms，测试环境 10s，特殊场景再调。
5. 熔断：用团队封装的 Sentinel 组件，下游异常自动熔断，防止级联故障。

Q11：分布式事务怎么处理？
参考答案：
转转不强求强一致分布式事务，主要用最终一致性方案：

1. 本地事务 + 事务消息：用 MQTransactionTemplate 保证本地事务提交后消息一定发出去，消费端幂等消费，达到最终一致。
2. 状态机（FSM）：转转很多业务基于状态机做状态流转，状态机本身集成了消息通知和异步任务，天然解决分布式场景下的一致性问题。
3. 原则：事务里不做 RPC、不发 MQ，从源头避免分布式事务的复杂度。
   一句话：能不用强一致分布式事务就不用，靠"本地事务 + 事务消息 + 状态机 + 消费幂等"保证最终一致。
