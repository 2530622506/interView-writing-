后端面试题（AI全栈工程师方向）

一、接口设计基础
Q1：GET、POST、PUT、DELETE 分别用在什么场景？
参考答案：
方法 场景 举例
GET 查询数据 获取商品列表、获取用户详情
POST 新建资源 创建订单、提交表单
PUT 全量更新 修改用户全部信息
PATCH 部分更新 只改用户昵称
DELETE 删除 删除订单
追问点： GET 和 POST 的区别是什么？
GET 参数在 URL 里、有长度限制、会被缓存；POST 参数在 body 里、没有长度限制、不会被缓存。

Q2：常见的 HTTP 状态码有哪些？
参考答案：
状态码 含义 什么时候返回
200 成功 请求正常处理完
201 创建成功 POST 新建资源成功
301/302 重定向 页面跳转
400 参数错误 前端传的参数不对
401 未登录 token 没带或过期
403 没权限 登录了但没权限操作
404 找不到 接口路径错了、资源不存在
500 服务器错误 后端代码挂了

二、数据库基础
Q3：数据库索引是什么？为什么能加快查询？
参考答案：
索引就像书的目录——没有目录的话，找一个词要翻完整本书；有了目录，直接跳到那一页。
索引的底层一般是 B+ 树，把数据排好序，查询的时候不用全表扫描，直接顺着树找就行。
什么时候建索引： 经常作为查询条件的字段（比如 user_id、order_id）。
索引的代价： 占存储空间、写数据的时候要同时维护索引，所以不是越多越好。

Q4：SQL 里 WHERE、GROUP BY、ORDER BY 的执行顺序是什么？
参考答案：
执行顺序：FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
举个例子：查每个城市的用户数，按用户数倒序排列：
SELECT city, COUNT(\*) as user_count
FROM users
WHERE status = 1 -- 先过滤
GROUP BY city -- 再分组
HAVING user_count > 100 -- 分组后再过滤
ORDER BY user_count DESC -- 最后排序

三、后端开发实操
Q5：一个接口从请求到返回，中间经历了哪些环节？
参考答案（以 Node.js 为例）：

1. 接收请求：路由匹配到对应的 controller
2. 参数校验：校验前端传的参数对不对（有没有必填项、类型对不对）
3. 鉴权：检查 token、判断有没有权限
4. 业务处理：调用 service 层的方法，操作数据库
5. 返回数据：把结果格式化返回给前端
   追问： 为什么要分 controller、service、dao 三层？
   因为解耦——controller 只负责收请求返数据，service 负责业务逻辑，dao 负责数据库操作。这样改的时候互不影响。

Q6：接口报错了，你一般怎么排查？
参考答案：

1. 先看日志：后端服务的日志，看有没有报错堆栈
2. 看状态码：是 4xx（前端问题）还是 5xx（后端问题）
3. 复现一下：用 Postman 直接调接口，看能不能复现
4. 看数据库：是不是数据不对、是不是没查到
5. 看上下游：是不是依赖的其他服务挂了
   结合实际：我之前写红包接口的时候，就遇到过并发问题——多人同时抢红包，超发了。就是通过日志定位到的，后来加了数据库锁解决。

四、安全与鉴权
Q7：前端怎么知道用户有没有权限访问某个接口？
参考答案：
一般用 JWT（JSON Web Token） 的方式：

1. 用户登录的时候，后端生成一个 token 返给前端
2. 前端把 token 存起来，之后每次请求都带上（放在 header 里）
3. 后端收到请求，先验证 token 对不对、过没过期
4. 验证通过了，再判断这个用户有没有权限操作这个接口
   结合转转的实际： 我们内部用的是 @zz-common/zz-permission，支持多租户（tenantId），前端调接口的时候自动带权限信息。

Q8：SQL 注入是什么？怎么防止？
参考答案：
SQL 注入就是——前端传的参数里，藏了一段 SQL 代码，后端直接拼到 SQL 语句里执行了。
比如登录的时候，用户名输入 ' OR 1=1 --，如果直接拼 SQL，就变成了：
这样就不用密码也能登录了。
怎么防止： 用参数化查询（预编译语句），不要自己拼 SQL。现在的框架（Sequelize、TypeORM）默认就是参数化的，只要不用字符串拼 SQL 就行。
SELECT \* FROM users WHERE username = '' OR 1=1 --' AND password = 'xxx'

五、性能与并发
Q9：缓存是什么？什么时候用缓存？
参考答案：
缓存就是把经常查的数据，存在一个快的地方（比如 Redis），下次直接从缓存拿，不用再查数据库。
什么时候用：
● 经常查、不经常变的数据（比如商品分类、配置信息）
● 读多写少的场景
好处： 减轻数据库压力、接口响应更快
问题： 数据更新了，缓存怎么办？——一般是更新数据库的时候，同时更新缓存（或者删掉缓存，下次查的时候再重新加）。

Q10：高并发的时候，怎么防止超发？（比如红包、秒杀）
参考答案：
这是一个经典问题——比如红包有 100 个，1000 个人同时抢，怎么保证不会超发？
几种方案：

1. 数据库乐观锁：更新的时候判断余额够不够
   如果影响行数是 0，说明没抢到。
2. Redis 预扣：把红包数量预先放在 Redis 里，用 DECR 命令原子扣减，扣到负数就说明没了。
3. 消息队列：先把请求放进队列，慢慢消费，不要一下子都打到数据库。
   结合实际： 我之前写红包接口的时候，就是用数据库乐观锁的方式——简单够用，量不大的时候没必要上 Redis。
   UPDATE red_packet SET amount = amount - 1
   WHERE id = 1 AND amount > 0

六、AI 全栈相关
Q11：AI 全栈工程师和普通全栈工程师有什么区别？
参考答案：
我觉得核心区别是——不是"会用 AI 工具写代码"，而是"能把 AI 能力做到产品里"。
具体来说：

1. 开发效率层面：用 AI 工具（Cursor、Claude Code）提效，自己写代码更快
2. 产品能力层面：能把 AI 能力（比如问答、生成、推荐）集成到产品里——比如做一个内部知识库问答、AI 辅助的表单填写
3. 工程化层面：知道怎么把大模型接入到后端服务里——怎么调 API、怎么做 prompt、怎么处理返回结果
   结合实际： 我之前在转转做的 zzb2c-harness，就是把内部文档喂给 AI，做了一个研发工作台——这就是 AI 全栈的一个典型场景。
