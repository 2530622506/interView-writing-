## 一、行为型模式

### 观察者模式和发布订阅模式有什么区别？Vue 的响应式是哪种？

**参考答案：**

1. **核心区别：耦合程度不同**

| 维度 | 观察者模式 | 发布订阅模式 |
|------|-----------|------------|
| 耦合关系 | Subject 直接持有 Observer 引用，**直接耦合** | 通过事件总线（Event Bus）中介，**完全解耦** |
| 通知方式 | Subject 主动调用 Observer 的方法 | Publisher 向 EventBus 发布，Subscriber 订阅 EventBus |
| 组件关系 | 两个角色：Subject + Observer | 三个角色：Publisher + EventBus + Subscriber |
| 跨模块 | 不适合跨模块通信 | 适合跨模块、跨应用通信 |

2. **观察者模式示例**：
```js
// Subject 直接持有 Observer 列表
class Subject {
  constructor() { this.observers = [] }
  subscribe(observer) { this.observers.push(observer) }
  notify(data) { this.observers.forEach(o => o.update(data)) }
}
class Observer {
  update(data) { console.log('收到通知:', data) }
}
```

3. **发布订阅模式示例**：
```js
// 通过 EventBus 解耦
const EventBus = {
  events: {},
  on(event, fn) { (this.events[event] ||= []).push(fn) },
  emit(event, data) { (this.events[event] || []).forEach(fn => fn(data)) },
  off(event, fn) { this.events[event] = (this.events[event] || []).filter(f => f !== fn) }
}
// Publisher 和 Subscriber 互不知晓
EventBus.on('userLogin', handler)
EventBus.emit('userLogin', { name: 'Alice' })
```

4. **Vue 的响应式是哪种？**
   - **Vue2**：`Dep`（依赖收集器）持有 `Watcher` 列表，数据变化时 `Dep.notify()` 调用所有 Watcher，是**观察者模式**
   - **Vue 的 EventBus**（`$on`/`$emit`）：是**发布订阅模式**
   - **Vue3**：`effect` + `track`/`trigger` 本质仍是观察者模式，但结构更函数式

5. **记忆口诀**：观察者是"面对面"，发布订阅是"通过中间人"。

### 手写一个 EventEmitter，支持 on、off、emit、once

**参考答案：**

```js
class EventEmitter {
  constructor() {
    // 存储事件及其监听器：{ eventName: [fn1, fn2, ...] }
    this._events = Object.create(null)
  }

  /**
   * 注册事件监听器
   */
  on(event, fn) {
    if (!this._events[event]) {
      this._events[event] = []
    }
    this._events[event].push(fn)
    return this // 支持链式调用
  }

  /**
   * 注册只执行一次的监听器
   * 关键：包装函数执行后立即 off 自身
   */
  once(event, fn) {
    const wrapper = (...args) => {
      fn.apply(this, args)
      this.off(event, wrapper) // 执行后立即移除
    }
    wrapper._origin = fn // 保存原始函数引用，便于 off 时精准匹配
    return this.on(event, wrapper)
  }

  /**
   * 触发事件，传递参数给所有监听器
   */
  emit(event, ...args) {
    const listeners = this._events[event]
    if (!listeners || listeners.length === 0) return false
    // 浅拷贝防止在触发过程中 off 导致数组变化
    listeners.slice().forEach(fn => fn.apply(this, args))
    return true
  }

  /**
   * 移除指定事件的指定监听器
   * 需要同时处理 once 包装过的函数（通过 _origin 匹配）
   */
  off(event, fn) {
    if (!this._events[event]) return this
    this._events[event] = this._events[event].filter(
      f => f !== fn && f._origin !== fn
    )
    // 如果没有监听器了，删除该事件键
    if (this._events[event].length === 0) {
      delete this._events[event]
    }
    return this
  }

  /**
   * 移除某事件的所有监听器，或清空所有事件
   */
  removeAllListeners(event) {
    if (event) {
      delete this._events[event]
    } else {
      this._events = Object.create(null)
    }
    return this
  }
}

// 使用示例
const emitter = new EventEmitter()

const handler = (data) => console.log('收到:', data)
emitter.on('message', handler)
emitter.once('connect', () => console.log('只执行一次'))

emitter.emit('message', 'hello')  // 收到: hello
emitter.emit('connect')           // 只执行一次
emitter.emit('connect')           // 不再触发

emitter.off('message', handler)
emitter.emit('message', 'world')  // 无输出
```

### once 如何实现？如何防止内存泄漏？

**参考答案：**

1. **once 的实现原理**：
   - 创建一个包装函数 `wrapper`，在包装函数内调用原始函数，调用完毕后立即调用 `off` 移除自身
   - 在 wrapper 上挂载 `_origin = fn` 属性，使得外部通过原始函数 `off` 时也能正确匹配到 wrapper

2. **内存泄漏的常见场景**：
   - 组件销毁时没有 `off` 对应的事件监听器，导致回调中持有的组件引用无法被 GC
   - 大量 `once` 注册后没有触发（因为触发才自动 off），监听器堆积

3. **防止内存泄漏的实践**：
```js
// Vue 组件示例：在 onUnmounted 中清理
onMounted(() => {
  emitter.on('userUpdate', handleUpdate)
})
onUnmounted(() => {
  emitter.off('userUpdate', handleUpdate) // 必须！
})

// React 示例：在 useEffect 的 cleanup 中清理
useEffect(() => {
  emitter.on('userUpdate', handleUpdate)
  return () => emitter.off('userUpdate', handleUpdate)
}, [])
```

4. **Node.js EventEmitter 的保护机制**：默认超过 10 个监听器会警告，可通过 `setMaxListeners()` 调整

### 微前端场景下跨应用通信用什么模式？

**参考答案：**

1. **推荐方案：发布订阅模式（全局 EventBus）**
   - 在 `window` 挂载全局 EventBus，各子应用通过它通信，子应用之间完全解耦
   - qiankun 官方推荐的 `initGlobalState` 也是发布订阅的变体

2. **qiankun 的 `initGlobalState` 示例**：
```js
// 主应用
import { initGlobalState } from 'qiankun'
const actions = initGlobalState({ token: '', user: null })
actions.onGlobalStateChange((state, prev) => {
  console.log('主应用感知到变化', state)
})

// 子应用（通过 props 接收）
export function mount(props) {
  props.onGlobalStateChange((state) => {
    store.commit('setUser', state.user)
  })
  props.setGlobalState({ token: 'xxx' })
}
```

3. **其他方案对比**：
   - `CustomEvent` + `window`：原生方案，简单但无类型安全
   - `localStorage` + `storage` 事件：适合持久化数据同步
   - `SharedWorker`：适合高频数据共享（如实时协作）
   - props 传递：仅适合主应用向子应用单向传递

4. **注意事项**：子应用卸载时必须清理监听，防止僵尸监听器。

### 如何用策略模式重构多个 if-else 表单校验逻辑？

**参考答案：**

1. **问题场景**：传统写法用大量 if-else，扩展时需修改原函数，违反开放封闭原则：
```js
// ❌ 反例：if-else 地狱
function validate(type, value) {
  if (type === 'required') {
    return value !== '' || '必填'
  } else if (type === 'phone') {
    return /^1[3-9]\d{9}$/.test(value) || '手机号格式错误'
  } else if (type === 'minLen') {
    // ...
  }
  // 每次新增规则都要修改这个函数
}
```

2. **策略模式重构**：
```js
// ✅ 策略对象：每个 key 是一种校验策略
const strategies = {
  required: (value, message = '此项为必填') =>
    value !== '' && value !== null && value !== undefined ? true : message,

  minLen: (value, min, message) =>
    value.length >= min ? true : (message || `最少输入 ${min} 个字符`),

  maxLen: (value, max, message) =>
    value.length <= max ? true : (message || `最多输入 ${max} 个字符`),

  phone: (value, message = '手机号格式不正确') =>
    /^1[3-9]\d{9}$/.test(value) ? true : message,

  email: (value, message = '邮箱格式不正确') =>
    /^[\w.-]+@[\w.-]+\.\w+$/.test(value) ? true : message,

  pattern: (value, regex, message = '格式不正确') =>
    regex.test(value) ? true : message,
}

// 校验执行器
class Validator {
  constructor() { this.rules = [] }

  add(value, rules) {
    rules.forEach(({ strategy, args = [], message }) => {
      this.rules.push(() => {
        const strategyFn = strategies[strategy]
        if (!strategyFn) throw new Error(`未知校验策略: ${strategy}`)
        return strategyFn(value, ...(message ? [...args, message] : args))
      })
    })
    return this
  }

  start() {
    for (const rule of this.rules) {
      const result = rule()
      if (result !== true) return result // 返回第一个错误信息
    }
    return true
  }
}

// 使用示例
const validator = new Validator()
validator
  .add(form.phone, [
    { strategy: 'required', message: '手机号不能为空' },
    { strategy: 'phone' }
  ])
  .add(form.password, [
    { strategy: 'required', message: '密码不能为空' },
    { strategy: 'minLen', args: [8], message: '密码至少8位' }
  ])

const error = validator.start()
if (error !== true) {
  console.log('校验失败:', error)
}
```

3. **新增策略只需在 `strategies` 对象里加一个 key**，不需要修改 `Validator` 类，体现开放封闭原则。

### 策略模式和工厂模式的本质区别？

**参考答案：**

1. **关注点不同**：
   - **工厂模式**：关注**创建对象**，根据参数决定创建哪种实例，解决的是"如何创建"的问题
   - **策略模式**：关注**行为替换**，在运行时切换算法/行为，解决的是"如何执行"的问题

2. **使用时机不同**：
   - 工厂：需要根据条件创建不同类型的对象时使用
   - 策略：需要根据条件选择不同算法/逻辑执行时使用

3. **举例对比**：
```js
// 工厂模式：创建不同的 UI 组件实例
function createButton(type) {
  if (type === 'primary') return new PrimaryButton()
  if (type === 'danger') return new DangerButton()
}

// 策略模式：选择不同的排序算法执行
const sortStrategies = {
  bubble: arr => bubbleSort(arr),
  quick: arr => quickSort(arr),
  merge: arr => mergeSort(arr),
}
function sort(data, strategy = 'quick') {
  return sortStrategies[strategy](data)
}
```

### 策略模式和 switch/if-else 的区别？如何体现开放封闭原则？

**参考答案：**

1. **本质区别**：
   - `switch/if-else`：逻辑集中在一个函数/类中，每次新增分支都要修改原代码
   - 策略模式：每个策略独立封装，新增策略只需添加新的策略类/函数，不修改已有代码

2. **开放封闭原则（OCP）**：对扩展开放，对修改关闭
   - 用 if-else：新增一种支付方式，要修改 `handlePayment` 函数 → **违反 OCP**
   - 用策略模式：新增一种支付方式，只需在策略对象里增加一个 key → **符合 OCP**

3. **代码对比**：
```js
// ❌ if-else：每次新增都要改这里
function handlePayment(type, amount) {
  if (type === 'alipay') { /* 支付宝逻辑 */ }
  else if (type === 'wechat') { /* 微信逻辑 */ }
  // 新增银行卡支付，必须修改此函数
}

// ✅ 策略模式：新增只需在 paymentStrategies 加 key
const paymentStrategies = {
  alipay: (amount) => { /* 支付宝逻辑 */ },
  wechat: (amount) => { /* 微信逻辑 */ },
  bankcard: (amount) => { /* 银行卡逻辑（新增，不改旧代码）*/ },
}
function handlePayment(type, amount) {
  return paymentStrategies[type]?.(amount)
}
```

### Redux middleware 是什么设计模式？applyMiddleware 源码用了什么技巧？

**参考答案：**

1. **Redux middleware 是责任链模式 + 函数式编程的结合**
   - 每个 middleware 是链上的一个处理节点，action 依次经过每个 middleware
   - 每个 middleware 可以决定是否调用 `next(action)` 把 action 传给下一个

2. **Redux applyMiddleware 源码分析**：
```js
// Redux applyMiddleware 核心逻辑（简化版）
function applyMiddleware(...middlewares) {
  return (createStore) => (reducer, preloadedState) => {
    const store = createStore(reducer, preloadedState)
    let dispatch = store.dispatch

    // 给每个 middleware 传入阉割版 store（只有 getState 和 dispatch）
    const middlewareAPI = {
      getState: store.getState,
      dispatch: (action, ...args) => dispatch(action, ...args) // 注意闭包引用
    }

    // 第一层调用：传入 middlewareAPI，得到 (next) => (action) => {} 形式的函数
    const chain = middlewares.map(middleware => middleware(middlewareAPI))

    // compose 将中间件从右到左组合
    // compose(f, g, h) 等价于 (...args) => f(g(h(...args)))
    dispatch = compose(...chain)(store.dispatch)

    return { ...store, dispatch }
  }
}

// compose 实现：从右到左组合函数
function compose(...fns) {
  if (fns.length === 0) return (arg) => arg
  if (fns.length === 1) return fns[0]
  return fns.reduce((a, b) => (...args) => a(b(...args)))
}
```

3. **Redux middleware 的三层柯里化**：
```js
// 一个标准的 Redux middleware 结构
const loggerMiddleware = (store) => (next) => (action) => {
  console.log('dispatching:', action)
  const result = next(action) // 调用下一个 middleware
  console.log('next state:', store.getState())
  return result
}
// 第一层：接收 store（middlewareAPI）
// 第二层：接收 next（下一个 middleware 的 dispatch）
// 第三层：接收 action，处理后决定是否 next(action)
```

4. **关键技巧**：
   - **柯里化**：三层嵌套函数，依次注入依赖
   - **compose**：将多个中间件从右到左串联成一个 dispatch 函数
   - **闭包**：`dispatch` 变量在 `middlewareAPI` 中被所有 middleware 共享，后续赋值会更新所有引用

### Koa2 的洋葱模型是责任链还是装饰器？与 Express middleware 有什么区别？

**参考答案：**

1. **Koa 洋葱模型是责任链模式**（不是装饰器）：
   - 请求从外到内穿过每个中间件（执行 `await next()` 之前的代码）
   - 响应从内到外穿回每个中间件（执行 `await next()` 之后的代码）
   - 形似洋葱，每个中间件包裹内层

2. **Koa vs Express middleware 的本质区别**：

| 维度 | Koa（洋葱模型） | Express（线性模型） |
|------|--------------|------------------|
| 执行顺序 | 进入时从上到下，返回时从下到上（双向） | 从上到下单向执行 |
| 异步支持 | 天然支持 async/await，`await next()` | 依赖回调，异步处理较繁琐 |
| 错误处理 | 可在最外层 middleware 用 try/catch 统一捕获 | 需要专门的错误处理 middleware（4 个参数） |

3. **Koa 洋葱模型执行流程**：
```js
// 中间件执行顺序演示
app.use(async (ctx, next) => {
  console.log('1 进入')
  await next()
  console.log('1 返回')
})
app.use(async (ctx, next) => {
  console.log('2 进入')
  await next()
  console.log('2 返回')
})
app.use(async (ctx) => {
  console.log('3 处理')
})
// 输出：1进入 → 2进入 → 3处理 → 2返回 → 1返回
```

### 手写 koa-compose（compose 中间件函数）

**参考答案：**

```js
/**
 * koa-compose 核心实现
 * 将中间件数组组合成一个洋葱模型的执行函数
 */
function compose(middlewares) {
  // 参数校验
  if (!Array.isArray(middlewares)) throw new TypeError('middlewares 必须是数组')
  if (middlewares.some(fn => typeof fn !== 'function')) {
    throw new TypeError('每个 middleware 必须是函数')
  }

  return function (ctx, next) {
    let index = -1 // 防止同一个 middleware 中多次调用 next

    function dispatch(i) {
      // 如果同一个 middleware 调用了两次 next，抛出错误
      if (i <= index) return Promise.reject(new Error('next() 被调用多次'))
      index = i

      let fn = middlewares[i]
      // 处理到最后一个中间件后，调用外部传入的 next（如果有）
      if (i === middlewares.length) fn = next

      if (!fn) return Promise.resolve()

      try {
        // fn(ctx, next) 中的 next 是 dispatch(i+1)
        return Promise.resolve(fn(ctx, () => dispatch(i + 1)))
      } catch (err) {
        return Promise.reject(err)
      }
    }

    return dispatch(0) // 从第一个中间件开始执行
  }
}

// 使用示例
const middlewares = [
  async (ctx, next) => {
    ctx.result = []
    ctx.result.push('A start')
    await next()
    ctx.result.push('A end')
  },
  async (ctx, next) => {
    ctx.result.push('B start')
    await next()
    ctx.result.push('B end')
  },
  async (ctx) => {
    ctx.result.push('C')
  }
]

const fn = compose(middlewares)
const ctx = {}
fn(ctx).then(() => {
  console.log(ctx.result)
  // ['A start', 'B start', 'C', 'B end', 'A end']
})
```

### next() 不调用会怎样？compose 为什么用递归而不是 for 循环？

**参考答案：**

1. **next() 不调用的后果**：
   - 后续的中间件不会执行（链条在此断开）
   - `next()` 之后的代码（返回阶段）也不会执行
   - 对于 HTTP 请求，如果路由中间件没调 `next()`，后面的业务中间件不会触发
   - 常见用途：权限中间件验证失败时不调 `next()`，直接返回 403

2. **为什么用递归而不是 for 循环**：
   - 中间件是**异步的**（async/await），`for` 循环无法在 `await next()` 处"暂停"，等内层中间件执行完再继续
   - 递归配合 `Promise` 可以自然地处理：调用 `next()` 时进入下一层递归，等 Promise resolve 后返回当前层继续执行
   - 这正是洋葱模型的关键：每个 middleware "进入" 时执行 next 前的代码，"返回" 时执行 next 后的代码

### 编辑器的撤销/重做功能用什么设计模式？手写一个命令栈

**参考答案：**

1. **使用命令模式（Command Pattern）**：
   - 将操作封装成命令对象，每个命令包含 `execute`（执行）和 `undo`（撤销）方法
   - 历史栈保存已执行的命令，支持 undo/redo

2. **完整实现**：
```js
// 命令基类
class Command {
  execute() { throw new Error('子类必须实现 execute') }
  undo() { throw new Error('子类必须实现 undo') }
}

// 具体命令：插入文本
class InsertCommand extends Command {
  constructor(editor, position, text) {
    super()
    this.editor = editor
    this.position = position
    this.text = text
  }
  execute() {
    this.editor.insert(this.position, this.text)
  }
  undo() {
    this.editor.delete(this.position, this.text.length)
  }
}

// 具体命令：删除文本
class DeleteCommand extends Command {
  constructor(editor, position, length) {
    super()
    this.editor = editor
    this.position = position
    this.length = length
    this.deletedText = '' // 保存被删除的内容，undo 时恢复
  }
  execute() {
    this.deletedText = this.editor.getText(this.position, this.length)
    this.editor.delete(this.position, this.length)
  }
  undo() {
    this.editor.insert(this.position, this.deletedText)
  }
}

// 命令栈（历史管理器）
class CommandHistory {
  constructor() {
    this.undoStack = [] // 已执行的命令
    this.redoStack = [] // 已撤销的命令
  }

  execute(command) {
    command.execute()
    this.undoStack.push(command)
    this.redoStack = [] // 新操作清空 redo 栈
  }

  undo() {
    if (this.undoStack.length === 0) return
    const command = this.undoStack.pop()
    command.undo()
    this.redoStack.push(command)
  }

  redo() {
    if (this.redoStack.length === 0) return
    const command = this.redoStack.pop()
    command.execute()
    this.undoStack.push(command)
  }

  canUndo() { return this.undoStack.length > 0 }
  canRedo() { return this.redoStack.length > 0 }
}

// 使用示例

// 编辑器内容: "Hello World"

// 编辑器内容: "Hello"

// 编辑器内容: "Hello World"
```

### 简单工厂、工厂方法、抽象工厂的区别？React 的 createElement 是哪种？

**参考答案：**

1. **简单工厂**：一个工厂函数/类，根据参数创建不同类型的对象：
```js
// 简单工厂
function createShape(type) {
  if (type === 'circle') return new Circle()
  if (type === 'square') return new Square()
  throw new Error('未知类型')
}
// 缺点：新增类型必须修改工厂函数（违反开放封闭原则）
```

```js
// 工厂方法：每个子类工厂负责创建自己的产品
class ShapeFactory {
  createShape() { throw new Error('子类实现') }
}
class CircleFactory extends ShapeFactory {
  createShape() { return new Circle() }
}
class SquareFactory extends ShapeFactory {
  createShape() { return new Square() }
}
// 新增形状只需新增工厂子类，不修改原有代码
```

3. **抽象工厂**：创建**一系列相关对象**（产品族）的接口：
```js
// 抽象工厂：创建一套风格一致的 UI 组件
class LightThemeFactory {
  createButton() { return new LightButton() }
  createInput() { return new LightInput() }
  createModal() { return new LightModal() }
}
class DarkThemeFactory {
  createButton() { return new DarkButton() }
  createInput() { return new DarkInput() }
  createModal() { return new DarkModal() }
}
```

4. **React `createElement` 是简单工厂**：
```js
// React.createElement(type, props, ...children)
// 根据 type 参数（字符串/函数/class），创建不同的 VNode 对象
// 集中在一个函数中判断，是简单工厂的典型形式

React.createElement(MyComponent, { name: 'Alice' })
```

### Vue3 的 createApp 用了什么设计模式？和 Vue2 new Vue() 的本质区别？

**参考答案：**

1. **createApp 用了工厂模式**：

| 多实例 | 共享同一个 Vue 原型链 | 每个 app 有独立的组件/指令注册表 |

```js
app1.use(ElementPlus) // 只影响 app1

```

### JavaScript 的原型链本身就是原型模式的体现，说说你的理解

**参考答案：**

1. **原型模式的核心**：通过克隆（复制）现有对象来创建新对象，而不是通过类的实例化

## 三、结构型模式

### Vue3 的 reactive 为什么从 defineProperty 改成 Proxy？代理模式解决了什么问题？

**参考答案：**

1. **代理模式的定义**：为目标对象提供一个代理，通过代理控制对目标的访问，可以在不改变目标对象的前提下添加额外逻辑

2. **`defineProperty` 的局限性**（Vue2 的问题）：
   - 无法检测属性的**新增和删除**（需要 `Vue.set`/`Vue.delete`）
   - 无法检测数组的**下标赋值**（`arr[0] = 1`）和 **length 变更**
   - 初始化时需要**递归遍历**整个对象所有属性，大对象性能差

3. **Proxy 代理模式的优势**：
```js
// Proxy 可以拦截 13 种操作，天然支持：
const handler = {
  get(target, key) {           // 属性读取
    track(target, key)
    const res = Reflect.get(target, key)
    // 懒代理：访问到嵌套对象时才递归代理
    return isObject(res) ? reactive(res) : res
  },
  set(target, key, value) {    // 属性设置（包括新增）
    Reflect.set(target, key, value)
    trigger(target, key)
    return true
  },
  deleteProperty(target, key) { // 属性删除
    Reflect.deleteProperty(target, key)
    trigger(target, key)
    return true
  },
  has(target, key) {            // in 操作符
    track(target, key)
    return key in target
  }
}
```

4. **三种代理类型**：
   - **虚拟代理**：延迟创建开销大的对象（图片懒加载）
   - **缓存代理**：缓存计算结果（接口请求缓存）
   - **保护代理**：权限控制（Vue3 的 `readonly`）

5. **`Reflect` 配合 `Proxy` 的必要性**：确保 `this` 指向正确（Proxy 拦截后需要用 `Reflect` 调用目标对象的原始行为，否则 `this` 会指向 Proxy 而非目标对象）

### 实现一个图片懒加载的虚拟代理

**参考答案：**

```js
// 虚拟代理：延迟加载真实图片
class ImageProxy {
  constructor(src) {
    this.realImage = null
    this.src = src
    this.placeholder = 'loading.gif'
  }

  display(container) {
    if (!this.realImage) {
      // 先显示占位图
      container.src = this.placeholder

      // 后台加载真实图片
      this.realImage = new Image()
      this.realImage.onload = () => {
        container.src = this.src
      }
      this.realImage.src = this.src
    } else {
      container.src = this.src
    }
  }
}

// 使用 ES Proxy 实现懒加载代理
function createLazyImageProxy(imgElement) {
  return new Proxy(imgElement, {
    set(target, prop, value) {
      if (prop === 'src') {
        // 先设置占位图
        target.src = '/placeholder.gif'

        // 使用 IntersectionObserver 等视口才加载
        const observer = new IntersectionObserver((entries) => {
          entries.forEach(entry => {
            if (entry.isIntersecting) {
              target.src = value // 进入视口时加载真实图片
              observer.unobserve(target)
            }
          })
        })
        observer.observe(target)
        return true
      }
      return Reflect.set(target, prop, value)
    }
  })
}

// 使用
const img = document.querySelector('.lazy-image')
const lazyImg = createLazyImageProxy(img)
lazyImg.src = 'https://example.com/large-image.jpg'
```

### 实现一个 axios 请求缓存代理

**参考答案：**

```js
/**
 * 缓存代理：缓存 GET 请求结果，相同 URL 直接返回缓存
 */
function createCachedAxios(axiosInstance, options = {}) {
  const {
    maxAge = 5 * 60 * 1000, // 缓存有效期，默认 5 分钟
    maxSize = 100,           // 最大缓存条数
  } = options

  // 缓存存储：{ url: { data, timestamp } }
  const cache = new Map()

  return new Proxy(axiosInstance, {
    get(target, prop) {
      // 只代理 get 方法
      if (prop !== 'get') return Reflect.get(target, prop)

      return function (url, config = {}) {
        const { noCache = false, ...restConfig } = config

        // 不缓存或强制刷新
        if (noCache) return target.get(url, restConfig)

        const cacheKey = url + JSON.stringify(restConfig.params || {})
        const cached = cache.get(cacheKey)

        // 命中有效缓存
        if (cached && Date.now() - cached.timestamp < maxAge) {
          console.log(`[缓存命中] ${url}`)
          return Promise.resolve({ data: cached.data, fromCache: true })
        }

        // 发起真实请求
        return target.get(url, restConfig).then(response => {
          // 超出最大缓存数量时，删除最旧的
          if (cache.size >= maxSize) {
            const firstKey = cache.keys().next().value
            cache.delete(firstKey)
          }
          cache.set(cacheKey, { data: response.data, timestamp: Date.now() })
          return response
        })
      }
    }
  })
}

// 使用
import axios from 'axios'
const cachedAxios = createCachedAxios(axios, { maxAge: 60000 })

await cachedAxios.get('/api/users')       // 真实请求
await cachedAxios.get('/api/users')       // 命中缓存
await cachedAxios.get('/api/users', { noCache: true }) // 强制刷新
```

### Reflect 和 Proxy 配合使用时 this 指向问题如何处理？

**参考答案：**

1. **问题场景**：不使用 Reflect 时，目标对象内部方法中的 `this` 会指向 Proxy 而不是原始对象：
```js
const target = {
  name: 'target',
  getName() { return this.name }
}
const proxy = new Proxy(target, {
  get(t, key) {
    return t[key] // ❌ 直接访问，this 指向 proxy
  }
})
// proxy.getName() 中，this 指向 proxy，如果 proxy 没有 name 属性会出问题
```

2. **使用 Reflect 保证 this 正确**：
```js
const proxy = new Proxy(target, {
  get(t, key, receiver) {
    // receiver 是 Proxy 实例本身
    return Reflect.get(t, key, receiver)
    // 等价于 t[key].bind(receiver)
    // 确保目标对象方法执行时 this 指向 receiver（proxy）
  }
})
```

3. **实际应用**：Vue3 的 reactive 中所有 Proxy handler 都使用 `Reflect` 确保 this 指向正确，这对继承链上的属性访问尤为重要

### 装饰器和继承的区别（运行时扩展 vs 编译时固定）？

**参考答案：**

1. **继承**：在类定义时（编译时）固定功能扩展，是静态的：
   - 子类继承父类所有行为，包括不需要的
   - 多重继承复杂（JS 不支持），容易造成类爆炸

2. **装饰器**：在运行时动态给对象添加功能，是灵活的：
   - 按需叠加：一个对象可以动态组合多个装饰器
   - 不影响其他对象：不同对象可以有不同的装饰组合

3. **代码对比**：

```js
// 继承：静态固定，Coffee 必须继承一种固定的实现
class CoffeeWithMilk extends Coffee { /* 永远带牛奶 */ }
class CoffeeWithSugar extends Coffee { /* 永远带糖 */ }
class CoffeeWithMilkAndSugar extends Coffee { /* 组合爆炸 */ }

// 装饰器：运行时动态组合
const coffee = new Coffee()
const coffeeWithMilk = withMilk(coffee)            // 加牛奶
const coffeeWithSugar = withSugar(coffee)           // 加糖（不影响上面）
const deluxeCoffee = withSugar(withMilk(coffee))   // 自由组合
```

### React HOC 的透传 props 问题如何解决？为什么 Hooks 能部分取代 HOC？

**参考答案：**

1. **透传 props 问题**：HOC 包裹后，外部传入的 props 如果没有显式传递给被包裹组件，会丢失：
```jsx
// ❌ 没有透传 className、style 等 props
const withLoading = (Component) => ({ isLoading, ...rest }) => {
  if (isLoading) return <Spinner />
  return <Component /> // 丢失了 rest 里的所有 props
}

// ✅ 正确透传
const withLoading = (Component) => ({ isLoading, ...rest }) => {
  if (isLoading) return <Spinner />
  return <Component {...rest} /> // 透传所有其他 props
}
```

2. **displayName 问题**：HOC 返回的组件在 DevTools 中显示为匿名，需手动设置：
```jsx
const WithLoading = (Component) => {
  const Wrapped = ({ isLoading, ...rest }) => /* ... */
  Wrapped.displayName = `WithLoading(${Component.displayName || Component.name})`
  return Wrapped
}
```

3. **为什么 Hooks 能部分取代 HOC**：
   - Hooks 将**逻辑**从组件中抽离，不需要组件嵌套
   - 无 props 透传问题，无命名冲突，组件树更简洁
   - 但 HOC 仍有用武之地：需要修改组件渲染结果（如错误边界、权限控制条件渲染）

### axios 的 adapter 用了什么设计模式？在浏览器和 Node.js 环境里如何切换？

**参考答案：**

1. **适配器模式（Adapter Pattern）**：将不兼容的接口转换为统一的接口，使得原本不能一起工作的类可以协同工作

2. **axios adapter 的设计**：
   - 浏览器环境：基于 `XMLHttpRequest` 的 `xhrAdapter`
   - Node.js 环境：基于 `http.request` 的 `httpAdapter`
   - 两者对外提供完全相同的接口（接收 config，返回 Promise<response>）

3. **切换机制**：
```js
// axios 内部自动检测环境选择 adapter
function getDefaultAdapter() {
  if (typeof XMLHttpRequest !== 'undefined') {
    return xhrAdapter  // 浏览器
  } else if (typeof process !== 'undefined' && process.versions?.node) {
    return httpAdapter  // Node.js
  }
}

// 也可以自定义 adapter
axios.create({
  adapter: function customAdapter(config) {
    // 返回 Promise<{ data, status, headers, config, request }>
    return new Promise((resolve, reject) => {
      // 自定义请求逻辑（如 fetch、mock）
    })
  }
})
```

4. **前端开发中适配器模式的其他场景**：
   - 旧接口返回格式改变时，用适配器层转换，不修改业务代码
   - 替换 UI 库时，用适配器包装新旧组件 API 差异
   - 单元测试时，用 mock adapter 替换真实请求

### 外观模式的定义和前端场景？jQuery 为什么说本质是外观模式？

**参考答案：**

1. **外观模式（Facade Pattern）**：为复杂子系统提供一个简单统一的接口，隐藏内部复杂性

2. **jQuery 是外观模式的经典案例**：
```js
// 没有 jQuery（直接操作复杂的原生 API）
const xhr = new XMLHttpRequest()
xhr.open('GET', '/api/data')
xhr.onreadystatechange = function() {
  if (xhr.readyState === 4 && xhr.status === 200) {
    const data = JSON.parse(xhr.responseText)
    const el = document.getElementById('result')
    el.innerHTML = data.message
    el.style.color = 'red'
    el.classList.add('visible')
  }
}
xhr.send()

// 有 jQuery（外观模式简化接口）
$.get('/api/data', (data) => {
  $('#result').html(data.message).css('color', 'red').addClass('visible')
})
```

3. **前端其他外观模式场景**：
   - **BFF（Backend For Frontend）**：聚合多个微服务 API，对前端提供单一接口
   - **工具函数库封装**：将 `localStorage`/`sessionStorage`/`indexedDB` 封装成统一的 `storage.get/set`
   - **第三方 SDK 封装**：将复杂的微信 SDK API 封装成简单的 `wx.share(config)`

### Vue3 Composables 属于什么设计模式？和策略/装饰器的关系？

**参考答案：**

1. **Composables 主要体现以下设计模式**：
   - **策略模式**：不同的 Composable 是不同的"策略"，组件按需组合使用
   - **装饰器模式**：Composable 可以接收响应式数据并返回增强后的数据，类似装饰
   - **外观模式**：将复杂的响应式逻辑封装在 Composable 内部，对外暴露简单接口

2. **和策略模式的关系**：
```js
// 不同的数据获取策略，组件按需切换
const useFetchStrategy = {
  realtime: () => useWebSocket('/ws/data'),
  polling: (interval) => usePolling('/api/data', interval),
  onDemand: () => useFetch('/api/data'),
}

// 组件中选择策略
const { data, loading } = useFetchStrategy.polling(5000)
```

3. **和装饰器模式的关系**：
```js
// Composable 装饰：在 useRequest 基础上添加重试能力
function useRequestWithRetry(url, maxRetries = 3) {
  const { data, loading, error, execute } = useRequest(url) // 基础功能

  // 装饰：增加重试逻辑
  const executeWithRetry = async () => {
    for (let i = 0; i < maxRetries; i++) {
      await execute()
      if (!error.value) return
      await sleep(1000 * (i + 1))
    }
  }

  return { data, loading, error, execute: executeWithRetry }
}
```

### 微前端中的设计模式：沙箱隔离（代理）、应用通信（发布订阅）、加载策略（工厂）分别怎么体现？

**参考答案：**

1. **沙箱隔离 → 代理模式**：
```js
// qiankun 的 ProxySandbox：用 Proxy 拦截子应用对 window 的读写
class ProxySandbox {
  constructor() {
    this.modifiedMap = {}
    this.sandbox = new Proxy(window, {
      get(target, key) {
        // 优先读沙箱内的值
        return key in this.modifiedMap ? this.modifiedMap[key] : target[key]
      },
      set(target, key, value) {
        // 写操作只影响沙箱，不污染真实 window
        this.modifiedMap[key] = value
        return true
      }
    })
  }
  activate() { window.__currentSandbox = this }
  deactivate() { delete window.__currentSandbox }
}
```

2. **应用通信 → 发布订阅模式**：
```js
// 全局事件总线实现跨应用通信
const globalEventBus = (() => {
  const events = new Map()
  return {
    on: (event, fn) => events.set(event, [...(events.get(event) || []), fn]),
    emit: (event, data) => events.get(event)?.forEach(fn => fn(data)),
    off: (event, fn) => events.set(event, events.get(event)?.filter(f => f !== fn))
  }
})()
window.__microAppEventBus = globalEventBus
```

3. **加载策略 → 工厂 + 策略模式**：
```js
// 根据应用配置动态加载不同类型的子应用
class MicroAppFactory {
  static loaders = {
    'qiankun': (config) => new QiankunApp(config),
    'module-federation': (config) => new ModuleFederationApp(config),
    'iframe': (config) => new IframeApp(config),
  }

  static create(type, config) {
    const Loader = this.loaders[type]
    if (!Loader) throw new Error(`未知的子应用类型: ${type}`)
    return Loader(config)
  }
}
```

### Vue3 effect/track/trigger 源码与观察者模式的对应关系？

**参考答案：**

1. **对应关系**：

| 观察者模式概念 | Vue3 对应实现 |
|--------------|-------------|
| Subject（被观察者） | 响应式数据（reactive/ref 包裹的对象） |
| Observer（观察者） | `effect`（副作用函数，如渲染函数、computed、watch） |
| 注册订阅 | `track`（在 effect 执行时，读取数据触发 get trap，收集依赖） |
| 通知更新 | `trigger`（数据变更触发 set trap，通知所有依赖该数据的 effect 重新执行） |
| 依赖图 | `targetMap: WeakMap<target, Map<key, Set<effect>>>` |

2. **源码流程解析**：
```js
// 简化版 Vue3 响应式核心
let activeEffect = null
const targetMap = new WeakMap()

// 收集依赖（注册观察者）
function track(target, key) {
  if (!activeEffect) return // 非 effect 中的读取不收集
  let depsMap = targetMap.get(target)
  if (!depsMap) targetMap.set(target, (depsMap = new Map()))
  let dep = depsMap.get(key)
  if (!dep) depsMap.set(key, (dep = new Set()))
  dep.add(activeEffect) // 将当前 effect 加入依赖集合
}

// 派发更新（通知观察者）
function trigger(target, key) {
  const depsMap = targetMap.get(target)
  if (!depsMap) return
  const effects = depsMap.get(key)
  effects?.forEach(effect => effect()) // 执行所有依赖该数据的 effect
}

// 创建响应式 effect（观察者）
function effect(fn) {
  const effectFn = () => {
    activeEffect = effectFn
    fn() // 执行时会触发 track，建立依赖关系
    activeEffect = null
  }
  effectFn() // 立即执行一次，收集依赖
}

// 创建 Proxy（响应式代理）
function reactive(raw) {
  return new Proxy(raw, {
    get(target, key) {
      track(target, key) // 读时收集
      return Reflect.get(target, key)
    },
    set(target, key, value) {
      Reflect.set(target, key, value)
      trigger(target, key) // 写时通知
      return true
    }
  })
}

// 使用：典型的观察者模式
const state = reactive({ count: 0, name: 'Vue' })

effect(() => {
  // 这个函数就是"观察者"
  // 执行时读取 state.count，触发 track，将自身注册为观察者
  console.log('count 变了:', state.count)
})

state.count++ // 触发 trigger，通知观察者重新执行
// 输出: 'count 变了: 1'
```

3. **与传统观察者模式的区别**：
   - 传统：手动调用 `subscribe(observer)` 注册
   - Vue3：**自动依赖收集**，effect 执行时自动追踪读取了哪些数据，无需手动声明依赖
   - 这种"自动订阅"是 Vue3 响应式系统的核心创新
