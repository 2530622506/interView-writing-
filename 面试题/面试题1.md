后端面试题（进阶版）

一、数据库深入
Q1：什么是数据库事务？ACID 是什么意思？
参考答案：
事务就是——一组操作，要么全部成功，要么全部失败，不能只成功一半。
经典例子：转账——A 给 B 转 100 块，要做两件事：A 扣 100、B 加 100。如果 A 扣完了、B 还没加，系统挂了，钱就没了。事务就是保证这两件事要么都成、要么都不成。
ACID 四个特性：
特性 含义 通俗解释
Atomicity（原子性） 全部成功或全部失败 要么都干，要么都不干
Consistency（一致性） 事务前后，数据整体是对的 转账前后总钱数不变
Isolation（隔离性） 多个事务同时跑，互不干扰 两个人同时改同一条数据，不会乱
Durability（持久性） 事务提交了，就永久生效 重启了数据也不会丢

Q2：联合索引是什么？最左匹配原则是什么意思？
参考答案：
联合索引就是——把多个字段放在一个索引里，比如给 (user_id, age, city) 建索引。
最左匹配原则： 查询条件要从索引的最左边开始用。
举个例子，索引是 (user_id, age, city)：
一句话：索引是按顺序排好的，你得从第一个字段开始用，不然就找不到。
查询条件 能不能用到索引
WHERE user_id = 1 ✅ 能用
WHERE user_id = 1 AND age = 20 ✅ 能用
WHERE user_id = 1 AND age = 20 AND city = '北京' ✅ 能用
WHERE age = 20 ❌ 用不到（跳过了最左的 user_id）
WHERE user_id = 1 AND city = '北京' ⚠️ 只能用到 user_id 这一段

Q3：慢查询是什么？怎么优化一条慢 SQL？
参考答案：
慢查询就是——一条 SQL 跑了很久（比如超过 1 秒），影响接口性能。
怎么排查：

1. 用 EXPLAIN 看这条 SQL 的执行计划——有没有走索引、扫描了多少行
2. 看是不是没加索引
3. 看是不是扫描的行数太多
   常见优化手段：
   问题 优化方式
   没走索引 加索引、调整查询条件
   查了太多行 加 WHERE 条件、分页
   SELECT \* 只查需要的字段
   关联太多表 拆分查询、加冗余字段
   数据量太大 分库分表、归档历史数据

二、并发与锁
Q4：乐观锁和悲观锁有什么区别？分别用在什么场景？
参考答案：
悲观锁 乐观锁
思路 先锁住，再操作 先操作，提交的时候再检查
实现 SELECT ... FOR UPDATE 版本号 / 时间戳
适合场景 并发冲突严重、写多 并发冲突少、读多写少
性能 差（一直锁着） 好（不加锁）
举个例子——抢库存：
悲观锁：SELECT stock FROM goods WHERE id=1 FOR UPDATE——先锁住这行，别人等着，扣完再释放
乐观锁：更新的时候判断——
如果影响行数是 0，说明别人改过了，重试。
我之前写红包接口用的就是乐观锁——量不大，简单够用。
UPDATE goods SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = 刚才查出来的版本号

Q5：什么是分布式锁？为什么需要？
参考答案：
单机的时候，用进程内的锁（比如 Java 的 synchronized）就行。但如果是多台机器、多个实例，进程内的锁就不管用了——你锁住了这台机器的，另一台机器照样能操作。
分布式锁就是——跨机器的锁，大家都抢同一把锁，谁抢到谁执行。
常见实现：

1. Redis：用 SETNX（set if not exists）命令，谁设置成功谁拿到锁
2. 数据库：建一张锁表
3. ZooKeeper：临时节点
   典型场景： 定时任务——多个实例都在跑，如果不加分布式锁，同一个任务会被执行 N 遍。加了分布式锁，只有一个实例能执行。

三、缓存深入
Q6：缓存穿透、缓存击穿、缓存雪崩分别是什么？怎么解决？
参考答案：
这三个是 Redis 最经典的三个问题：
问题 是什么 怎么解决
缓存穿透 查一个数据库里也没有的数据，每次都打到数据库 1. 布隆过滤器 2. 查不到也缓存一个空值，设短过期时间
缓存击穿 一个热点 key 突然过期了，大量请求同时打到数据库 1. 热点数据永不过期 2. 加互斥锁，只让一个请求去查数据库
缓存雪崩 大量 key 同时过期，或者 Redis 挂了，全部打到数据库 1. 过期时间加随机值，不要同时过期 2. Redis 做集群、高可用 3. 数据库兜底限流
方案 说明
布隆过滤器 (Bloom Filter) 最推荐。在访问缓存前，先通过布隆过滤器判断数据是否存在。如果布隆过滤器说“不存在”，则直接返回，不再查库。优点是不占用额外内存存储 Key。
缓存空对象 即使数据库查不到，也将 Key-Null
存入缓存，设置较短的过期时间（如 5 分钟）。下次查询时直接返回 Null，保护数据库。缺点是需要维护额外的内存空间。
参数校验 在业务层对 ID 等参数进行严格校验，拦截非法或明显不存在的 ID。
一句话区分：
● 穿透：数据本来就没有，一直打 DB
● 击穿：一个热点 key 过期了，瞬间打 DB
● 雪崩：一大堆 key 同时过期，全部打 DB

四、接口设计
Q7：什么是接口幂等性？为什么需要？
参考答案：
幂等性就是——同一个接口，调一次和调多次，结果是一样的。
为什么需要：
比如用户点"提交订单"，网络卡了，用户以为没点上，又点了一次。如果接口不幂等，就会生成两个订单。
怎么实现幂等：

1. 前端加按钮防抖——点完就禁用
2. 用唯一请求 ID——每次请求带一个 request_id，后端判断这个 id 有没有处理过
3. 数据库唯一索引——比如订单号唯一，重复插入就报错
4. 状态机——订单已经是"已支付"了，就不能再支付一次

Q8：什么是接口限流？常见的限流算法有哪些？
参考答案：
限流就是——单位时间内，只允许多少个请求进来，超过的就拒绝。防止把服务打挂。
常见算法：
常见实现： 网关层限流（Nginx、Gateway）、代码层限流（Guava RateLimiter、Redis + Lua）
算法 原理 特点
固定窗口 每分钟最多 100 个请求 简单，但窗口边界可能突刺
滑动窗口 窗口慢慢滑，更平滑 比固定窗口精准
漏桶 请求像水一样进桶，桶按固定速度出水 出水速度恒定
令牌桶 以固定速度往桶里放令牌，拿到令牌才能执行 允许一定程度的突发流量

五、架构基础
Q9：什么是消息队列？用它解决什么问题？
参考答案：
消息队列就是——一个中间人，请求先扔给它，后面再慢慢处理。
解决什么问题：
缺点： 系统变复杂了、可能重复消费、消息可能丢、一致性变差。
问题 怎么解决
同步调用太慢 下单之后，要发短信、发邮件、加积分——不用一个个等，扔给消息队列异步处理
并发太高打挂服务 秒杀的时候，1 万个请求同时进来，先放进队列，消费者慢慢处理
系统解耦 下单服务不用知道短信服务、积分服务的存在——发个消息就行
数据最终一致性 分布式事务太复杂，用消息队列保证最终一致

Q10：CAP 定理是什么？分布式系统为什么难？
参考答案：
CAP 三个字母：
● C（Consistency）一致性：所有节点看到的数据是一样的
● A（Availability）可用性：每个请求都能得到响应
● P（Partition Tolerance）分区容忍性：网络断了，系统还能跑
CAP 定理：分布式系统，三个里最多同时满足两个。
因为网络分区（P）是一定会发生的——你不能保证网络永远不断。所以实际上你只能在 C 和 A 之间选：
● 选 CP：保证一致性，宁可不可用（比如 ZooKeeper）
● 选 AP：保证可用性，数据暂时不一致（比如 Eureka、大部分互联网业务）
互联网公司一般选 AP——可用性比强一致性更重要，数据最终一致就行。

六、结合 AI 全栈的追问
Q11：如果让你用 AI 做一个后端接口，你会怎么用？
参考答案：
我之前写红包接口的时候就是这么做的：

1. 先想清楚接口要做什么——入参是什么、出参是什么、业务逻辑是什么
2. 让 AI 生成骨架——路由、参数校验、数据库操作的基础代码
3. 自己写业务逻辑——红包怎么发、金额怎么算、并发怎么处理，这些核心的自己写
4. 让 AI 帮你找问题——把代码贴给 AI，问"这里有没有并发问题、有没有安全问题"
5. 找后端同事 review——AI 写的东西不能直接上，一定要有人把关
   核心思路：AI 帮你干重复的、模板化的活，核心的业务逻辑、并发、安全，自己把控。
