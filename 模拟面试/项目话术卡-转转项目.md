## 卡片 1：商详页性能优化

**一句话定位：** 千万级流量 C 端商详页首屏慢，综合多种手段将首屏时间从 878ms 降至 169ms。

### 背景
商详页是用户从浏览到购买的核心路径，PV 高。线上性能平台发现首屏时间、秒开率指标差。

### 定位瓶颈（三条链路）
1. **Network**：查资源加载时序，发现接口请求阻塞首屏、JS bundle 体积大
2. **Performance**：渲染阶段分析，定位 Layout/Paint 耗时
3. **容器冷启动**：Hybrid H5 的 WebView 冷启动时间约几百毫秒（Native 侧指标）

### 优化方案

| 方案 | 做了什么 | 解决什么 |
|------|---------|---------|
| 接口拆分 | 非首屏数据接口延迟加载 | 减少首屏阻塞请求 |
| 代码分包 | `defineAsyncComponent` + webpack 动态 import，非首屏组件拆到第二屏 | 首屏 bundle 体积降低 40% |
| WebView 预渲染 | 客户端进入 App 时按常驻列表预热容器，点击时判断命中直接复用 | 消除冷启动耗时 |
| 首图缓存 | 列表页缓存图片 URL，进入商详先展示，接口返回后覆盖 | 消除图片白屏 |
| 图片懒加载 | 非首屏图片延迟加载 | 减少首屏网络消耗 |
| 骨架屏 | 数据返回前展示骨架 | 改善感知加载速度 |

### 关键数据
- 首屏时间：878ms → **169ms**
- 秒开率：78% → **93.4%**
- 预渲染命中率：82% → **95%**

### 面试官常问追问
- **预渲染不是 SSR，是什么？** → WebView 容器预热，H5 in-app 场景特有方案，和 SSR/SSG 不同
- **命中率怎么统计？** → 命中时埋点上报，命中 PV / 采样总 PV，在线上性能平台查看
- **`defineAsyncComponent` vs `defineComponent`？** → `defineAsyncComponent` 是懒加载，`defineComponent` 是类型辅助，两者无关

## 卡片 2：秒杀高并发容灾（十亿补贴大促）

**一句话定位：** S 级大促前端核心开发，0 故障 0 线上事故，从三个维度做高并发保障。

### 一、流量整形

| 层级 | 手段 | 场景 |
|------|------|------|
| 基础层 | `debounce` 防抖（300-500ms） | 搜索框输入 |
| 基础层 | `throttle` 节流（leading 模式） | 按钮提交 |
| 进阶层 | `AbortController` 取消旧请求 | 搜索新请求覆盖旧请求、路由切换 |
| 大促专项 | 请求优先级队列 | HTTP/1.1 并发 6 连接上限，高优占用：下单/支付/加购，低优延迟：埋点/推荐 |

> ⚠️ 记住：debounce = 防抖；throttle = 节流，不要说反

### 二、幂等设计

1. **唯一 requestId**：前端生成 UUID，作为请求头 `X-Request-Id` 传后端
2. **按钮悲观锁**：点击后立即 disabled + loading，请求返回后才解锁
3. **超时先查状态**：超时不代表请求未到达，先轮询查订单状态，确认未创建再重试（携带新 requestId）
4. **本地防重表**：订单 id + requestId 写入 `sessionStorage`，刷新页面先查本地
5. **区分读写**：只对写操作（下单/支付/退款）做幂等，查询接口不做

### 三、容灾兜底

**分级降级（高峰期从低优先级开始降）：**

| 步骤 | 降级内容 |
|------|---------|
| 第一步 | 关闭筛选动效、图片懒加载改占位图、推荐模块隐藏 |
| 第二步 | 关闭评论、直播组件、"猜你喜欢" |
| 第三步 | 列表展示缓存数据 + 提示条"数据可能有延迟" |
| 始终保留 | 下单、加购、支付全程不降级 |

**动态开关：** 配置中心（Apollo）下发，无需发版秒级生效；前端通过 **SSE 长连接**（比 WebSocket 更轻量）订阅变更，服务端主动推送，不是轮询。

## 卡片 3：RAG 知识问答平台

**一句话定位：** 面向消费电子运营团队，主导 RAG 检索问答链路，查询效率提升约 80%。

### 检索链路全流程

```
文档解析（MinerU）
    ↓
父子分块（Markdown 结构）
    ↓
向量化（text-embedding-v4）存入 ES
    ↓
用户提问 → 意图识别 + 查询改写
    ↓
BM25 关键词召回 ‖ 向量 kNN 召回（并行）
    ↓
RRF 融合（丢分数用排名，1/(60+rank)）
    ↓
Reranker 精排（qwen3-rerank，交叉编码器）
    ↓
阈值过滤（0.4）→ 最终候选集
    ↓
答案生成（附来源引用）
```

### 父子分块

- **Parent**：按 Markdown 标题/章节切，超出范围递归按段落/列表/表格拆
- **Child**：Parent 内进一步切分，保留 **Overlap**（滑动窗口重叠）防语义截断
- **为什么**：检索精度（Child 小粒度）和上下文完整（回溯 Parent）分开处理

### 混合检索关键点

- **RRF 解决的问题**：BM25 和向量分数量纲不同，直接加权向量会被压制。RRF 丢原始分数只用排名，两路都命中则分数叠加
- **Reranker 解决的问题**：Embedding 双塔模型无 token 级交互，细粒度语义（否定、条件、数量对比）识别能力弱；Reranker 交叉编码器全 attention，但无法预存，只适合对 TopK 精排
- **一句话记忆：Embedding 管召回不漏，Reranker 管精排不噪**

### 分层记忆架构

| 层 | 存储 | 内容 | 作用域 |
|----|------|------|--------|
| Redis | 热缓存 | 最近 20 条对话 | 当前会话（session ID） |
| PostgreSQL | 事实源 | 全量历史消息 + 来源引用 | 永久 |
| Mem0 | 语义记忆 | 用户自陈述事实（偏好/背景） | user 层跨会话 / session 层当前会话 |

**记忆污染三道防线：**
1. **写入端**：LLM 分类器，制度/流程/金额等知识库内容一律不写进 Mem0
2. **注入端**：记忆注入时强制附加"以上仅作背景，规则以本轮检索资料为准"
3. **数据流**：只把用户原话喂给 Mem0，助手回答不作为记忆源

**跨会话流程：** 记忆检索和意图分类并行启动（不串行，节省延迟），Mem0 命中内容注入 System Message，记忆只提供背景和风格，不替代检索。

## 卡片 4：AI 全栈辅助研发工作台（增量同步）

**一句话定位：** 基于 Git 变更的知识库增量同步，用三层映射 + 水位机制 + ancestor 去重保障可靠性。

### Git 变更 → 知识文档映射（三层机制）

1. **入口组件锚点**：`page.md` 里每个模块登记入口组件路径，改动文件命中哪个模块目录就映射到该模块文档（任意层级可命中，不硬编码一级目录）
2. **共享代码反查**：改动落在 `components/utils` 等共享目录时，派只读子 Agent grep 引用关系，所有命中模块都要刷新
3. **新增/删除判定**：新目录走 init 流程，源码删除进清理队列

**ancestor 去重：** 模块文档的 `source_commit` 已包含本次变更则跳过，不重复生成。

### 同步水位机制（Watermark）

水位 = 存在 `page.md` frontmatter 里的字段，记录"知识库已处理到哪个代码版本"。

| 解决的问题 | 机制 |
|---------|------|
| 避免全量重建 | 下次扫描从水位往后扫 |
| 失败不丢变更 | 全部失败时不推进水位，下次从原起点覆盖 |
| 可追溯 | 每份知识对应的代码版本可查 |

### 三机制协作

- **三层映射** → 决定"哪些文档要更新"
- **水位** → 决定"扫哪个时间段的变更"
- **ancestor 去重** → 决定"已经最新的跳过"

## 面试表达技巧

### 数字先行
每个项目开口就给数字，面试官会立刻有印象：
- 商详优化：首屏 878ms→169ms，秒开率 78%→93.4%
- 大促：S 级活动 0 故障 0 事故
- RAG：查询效率提升约 80%，Recall@K 72%→86%
- AI 工作台：需求交付效率提升约 60%

### 被追问时不慌
- 不确定的说"这部分我没有直接参与，但我理解的是……"
- 说错了主动纠正，比硬撑更好

### 这个岗位的匹配点
- 海外电商 C 端 → 你有千万级流量电商 C 端经验
- React 优先 → 你在转转做过 React 后台，不只是 Vue
- 性能优化 → 直接对应商详优化项目
- 后端加分 → Spring Boot + NestJS 都有落地经验
