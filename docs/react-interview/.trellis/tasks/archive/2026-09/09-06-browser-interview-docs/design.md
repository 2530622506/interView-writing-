# 技术设计：浏览器篇面试文档重构

## 1. 交付结构

采用一份主文档承载完整学习路径，避免读者在多个文件之间跳转；图示作为 `assets/` 下的本地 SVG，流程图直接使用 Mermaid fenced code。推荐结构：

```text
browser-interview-guide.md
assets/
  browser-process-architecture.svg
  browser-rendering-pipeline.svg
```

主文档内部通过目录、章节锚点和“面试回答模板”维持导航；不引入构建工具，不改现有文档体系。

## 2. 章节架构

1. 先建立浏览器心智模型：浏览器进程、网络进程、渲染进程、GPU 进程与线程边界；
2. 用“输入 URL → 请求资源 → 解析 → 渲染 → 交互”贯穿全文；
3. 将缓存和本地存储分开：缓存解决资源复用，Storage 解决应用数据持久化；
4. 将网络协议按发生顺序组织：DNS → TCP → TLS → HTTP → 连接复用 / 关闭；
5. 将渲染流水线按数据产物组织：HTML → DOM、CSS → CSSOM → Render Tree → Layout → Paint → Composite；
6. 最后聚合性能、Worker、SSR / CSR 和高频问答，避免在正文中反复插入相同问题。

## 3. 图示设计

- Mermaid：适合 URL 主流程、缓存命中决策、TCP / TLS 时序、渲染阻塞关系、回流重绘决策。
- SVG：适合浏览器多进程架构和渲染流水线的横向分层图；SVG 需采用纯文本 XML，便于版本控制和离线查看。
- 每张图后设置“读图重点”小节，并在文字中明确图示的简化边界，例如 HTTP/2、HTTP/3 与传统 TCP 链路的差异不在主流程中展开。

## 4. 内容校准原则

- 以通用 Web 平台行为作为主线；对浏览器实现差异使用“通常 / 以具体浏览器实现为准”表述。
- 区分强缓存与协商缓存：前者通常无需网络请求，后者需要向服务器验证；明确 `Cache-Control` 优先于 `Expires`、`ETag` 通常优先于 `Last-Modified` 的语义。
- 区分页面刷新动作、开发者工具禁用缓存和 HTTP 缓存语义，避免将浏览器 UI 行为写成协议硬规则。
- 区分“阻塞 DOM 解析”和“阻塞首次绘制”：CSS、同步脚本、预解析、布局依赖需要分别解释。
- 将“GPU 加速”表述为浏览器可能将部分图层交给 GPU 合成，不承诺任意 CSS 属性都会创建独立合成层。
- Worker 章节明确同源、消息通信、DOM 访问限制和生命周期；Service Worker 强调其作为网络代理的能力与缓存更新策略。

## 5. 兼容性与风险

- Mermaid 在不同 Markdown 阅读器的渲染支持不同，因此图示旁必须有文字版流程和表格，不让 Mermaid 成为唯一信息载体。
- 远程原图可能失效或包含 OCR 噪声，默认不批量迁移；仅保留能明显增强理解的本地 SVG。
- 文档是面试学习资料而非浏览器规范全文；对规范细节使用准确但可读的简化表达，并通过“进阶追问”标记深入方向。
