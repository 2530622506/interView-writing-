## 1. 协议分层与一次请求的全景

### 1.1 一句话结论

HTTP 定义应用如何表达请求与响应，TCP / QUIC 负责端到端传输，TLS 提供认证与加密，IP 负责跨网络寻址；浏览器还会在这些协议之上执行缓存、同源策略、CSP 等规则。**不同层的保证不能互相替代。**

### 1.2 OSI 七层与 TCP/IP 模型

| OSI 层 | 核心职责 | 常见对应概念 |
| --- | --- | --- |
| 应用层 | 定义应用交互语义 | HTTP、DNS、SMTP、WebSocket |
| 表示层 | 数据表示、编码、加密等抽象职责 | 不能机械地把某个现代协议唯一塞入这一层 |
| 会话层 | 会话建立、管理等抽象职责 | 现代互联网应用常自行实现相关能力 |
| 传输层 | 端到端传输、端口、可靠性等 | TCP、UDP；QUIC 提供传输能力但承载于 UDP |
| 网络层 | 寻址、路由、跨网络转发 | IPv4、IPv6、ICMP |
| 数据链路层 | 同一链路上的帧传输 | Ethernet、Wi-Fi 的链路层、PPP |
| 物理层 | 传输比特的电、光、无线信号 | 网线、光纤、无线物理层 |

TCP/IP 常用四层模型：应用层、传输层、网际层、链路层。教学中的五层模型把链路层再拆成数据链路层与物理层。

**为什么是七层？** 它是一套为职责分离、标准化与互操作设计的参考模型，不是自然规律，也不意味着实际实现必须经过七个独立软件模块。前端面试中，解释边界比死记协议归属更重要。PPP 属于数据链路层；DNS、SMTP 不属于物理层。

### 1.3 一次 HTTPS 请求的典型路径

```text
解析 URL、应用 HSTS 等策略
        ↓
检查可用缓存 / Service Worker 的响应路径
        ↓ 未直接得到响应
解析域名，选择目标地址、代理和协议
        ↓
复用连接，或新建 TCP + TLS / QUIC 连接
        ↓
发送 HTTP 请求，经 CDN / 网关 / 反向代理到服务
        ↓
认证、授权、业务处理、数据库与下游调用
        ↓
返回响应，执行缓存与浏览器安全检查
        ↓
流式解析 HTML，发现子资源，并行加载与渲染
```

这是主干模型，不是每次请求必经的串行清单：

- DNS 可以命中缓存，连接可以复用，请求甚至不出浏览器。
- 页面解析、资源下载、脚本执行存在交叠，不是“全部下载完才开始渲染”。
- CORS 预检可能在实际请求前额外发出请求。
- 重定向可能开启新的请求链，甚至切换域名、连接和凭证处理规则。
- 返回响应不意味着必须断开连接，持久连接通常留在连接池里。

**追问：HTTP 安全了，业务就安全吗？**

不一定。TLS 保护链路，但不替服务器做对象级权限校验；TCP 保证字节有序交付，但不保证订单只创建一次；CORS 限制跨源读取，但不等于禁止跨站请求。

## 2. DNS、CDN 与连接建立前的工作

### 2.1 DNS 查询不是每次都从根服务器开始

浏览器、操作系统、递归解析器都可能有缓存。缓存未命中时，递归解析器通常通过根、顶级域、权威服务器逐步定位答案；具体查询步骤还可能因缓存而缩短。

常见记录：

- `A`：域名对应 IPv4 地址。
- `AAAA`：域名对应 IPv6 地址。
- `CNAME`：别名指向另一个域名。
- `HTTPS` / `SVCB`：可提供服务绑定、协议等信息，实际使用取决于客户端与部署。

TTL 约束记录可以缓存多久，不代表更新配置后全球客户端立刻切换。已有连接、应用缓存和递归解析器行为也会影响切流速度。

### 2.2 DNS 为什么既可能使用 UDP，也可能使用 TCP？

传统 DNS 普通查询常用 UDP，截断响应等情况需要 TCP；区域传送等场景也会用 TCP。现代环境还存在 DoT、DoH 等加密传输方式。因此“DNS 只走 UDP”是错误的。

**DoH 与 DNSSEC 不同：**

- DoH 保护客户端到所选解析服务之间的 DNS 通信，并不让所有参与者都看不到查询。
- DNSSEC 通过签名帮助验证 DNS 数据的来源与完整性，不提供查询内容加密。
- 二者都不能替代 HTTPS 对目标网站身份和应用数据的保护。

### 2.3 CDN 为什么能提速？

CDN 不只是“把文件放到更近的机器”：它还可以复用回源连接、缓存热点内容、吸收流量峰值，并优化运营商间路径。DNS 调度、Anycast、负载与健康状态都可能参与节点选择，“最近”不一定指物理距离最近。

但缓存命中率不足、跨区域回源、错误的缓存键与动态鉴权都可能让 CDN 收益下降，甚至制造数据泄漏。

**工程追问：DNS 时间为 0，是没有 DNS 了吗？**

通常不是。可能命中缓存、复用连接，或者该计时阶段对当前请求不适用。性能面板中的 0 不能直接理解成协议步骤不存在。

## 3. TCP 与 UDP：服务语义比速度标签更重要

### 3.1 30 秒回答

TCP 提供面向连接、可靠、有序的字节流，并实现流量控制与拥塞控制。UDP 提供保留报文边界的数据报服务，不内建重传、排序和拥塞控制。两者都不是加密协议，也不能简单比较谁永远更快；应用可以在 UDP 之上实现可靠传输，例如 QUIC。

| 维度 | TCP | UDP |
| --- | --- | --- |
| 交付单位 | 字节流，不保留应用消息边界 | 数据报，保留报文边界 |
| 连接状态 | 需要维护连接、序列号、窗口等状态 | 协议层无握手式连接建立 |
| 丢包 / 乱序 | 检测、重传、重排、去重 | 不内建恢复与排序 |
| 误码检测 | 有校验和 | 也有校验和；IPv4 可选、IPv6 通常要求，存在受限例外 |
| 流量 / 拥塞控制 | 内建相应机制 | 由应用或上层协议实现 |
| 首部大小 | 最小 20 字节，含选项可到 60 字节 | 固定 8 字节，不含 IP 等头部 |
| 通信形式 | 每条连接连接两个端点 | 可支持单播、组播；IPv4 也支持广播 |
| 数据安全 | 不自带身份认证和加密 | 同样不自带身份认证和加密 |

### 3.2 什么叫“面向字节流”？为什么会有粘包问题？

应用执行两次写入：`hello`、`world`，接收方可能一次读到 `helloworld`，也可能分几次读取。TCP 只保证字节序列，不承诺一次 `write` 对应一次 `read`。

因此应用层必须定义消息边界：

1. 固定长度消息。
2. 长度前缀，例如前 4 字节描述正文长度。
3. 分隔符，但必须处理转义和正文中的同名字符。
4. 自带帧格式的协议，如 HTTP/2、WebSocket。

所谓粘包不是 TCP 的 bug，而是应用错误地把字节流当成消息队列。类似地，一次 HTTP 请求也不等于一个 TCP 报文段。

### 3.3 UDP 为什么常用于实时音视频？

实时系统的核心取舍是：**超过播放截止时间的正确数据，可能不如按时到达的近似数据有价值。**

- 对延迟敏感的通话可以结合抖动缓冲、丢包隐藏、前向纠错和有限重传。
- 丢失关键帧或参考帧可能影响后续解码，不能说“视频丢几个包无所谓”。
- 重传是否有价值取决于剩余播放时间、RTT、丢包位置和码率策略。
- 浏览器网页不能任意使用原始 UDP socket；常见能力包括 WebRTC，以及基于 QUIC 的 WebTransport 等受控 API。
- 点播和大量直播采用 HLS / DASH，经 HTTP 可靠下载分片；“视频一定使用 UDP”不成立。

**追问：UDP 为什么不一定更快？**

如果应用需要补上握手、加密、确认、重传和拥塞控制，额外成本仍然存在。吞吐与时延还受网络路径、丢包、实现、CPU、缓存与连接复用影响。

## 4. TCP 三次握手、四次挥手与连接状态

### 4.1 三次握手确认的是什么？

核心是建立双方的连接状态，交换并确认初始序列号，确认双向通信路径可用，并协商 MSS、窗口扩大、SACK 等选项。**这不是 HTTP 握手，也不是 TLS 握手。**

```text
客户端                                      服务端
CLOSED                                      LISTEN
  | --- SYN, seq=x --------------------------> |
SYN-SENT                                     SYN-RECEIVED
  | <--- SYN+ACK, seq=y, ack=x+1 -------------- |
  | --- ACK, seq=x+1, ack=y+1 ----------------> |
ESTABLISHED                                  ESTABLISHED
```

SYN 消耗一个序列号。`seq` 表示本端发送序列空间的位置，`ack` 表示希望收到对方的下一个字节序号；不能把 ACK 标志位、确认号和本端序列号混为一谈。

### 4.2 为什么不是两次？为什么通常不需要四次？

只有两次时，服务端尚未收到客户端对自己初始序列号的确认。网络中延迟的旧 SYN 还可能让服务端错误地把历史请求当成新连接。第三次消息使服务端能验证客户端确实收到了这次握手的响应。

交换 SYN 与确认 SYN 是两个方向的工作，但服务端可以把自己的 SYN 和对客户端的 ACK 合并到一个报文，因此典型过程是三次而不是四次。

“互相确认收发能力”适合入门，但更深的答案应包括：**同步序列空间、防止旧连接报文混淆、建立双方状态**。它不是对网络永远可靠的证明。

### 4.3 第三次握手丢失会怎样？能带数据吗？

- 客户端通常已进入 `ESTABLISHED`，服务端可能还在 `SYN-RECEIVED`。
- 服务端超时重发 SYN+ACK，客户端可以再次确认。
- 客户端后续数据报文中的有效 ACK 也可能使握手完成。
- 第三个报文可以携带应用数据；“前三次握手一定不能带数据”过于绝对。
- TCP Fast Open 是允许在特定条件下更早携带数据的扩展，不应与普通握手混为一谈。

### 4.4 四次挥手为什么体现全双工？

关闭一个发送方向，不代表另一个方向已经没有数据要发送。以下以客户端主动关闭为例：

```text
客户端                                      服务端
ESTABLISHED                                  ESTABLISHED
  | --- FIN, seq=u --------------------------> |
FIN-WAIT-1                                   CLOSE-WAIT
  | <--- ACK, ack=u+1 ------------------------ |
FIN-WAIT-2                                   继续发送剩余数据
  | <--- FIN, seq=v -------------------------- |
  | --- ACK, ack=v+1 ------------------------> |
TIME-WAIT                                    CLOSED
  | 等待 2MSL
CLOSED
```

如果服务端接收 FIN 后恰好也准备关闭，可合并 ACK 与 FIN，因此不保证一定看到四个独立报文。FIN 表示有序关闭发送方向；RST 常用于复位连接，语义与正常挥手不同。

### 4.5 TIME_WAIT 为什么等待 2MSL？

MSL 是报文最大生存时间的抽象参数，具体实现与计时并非所有系统相同。等待主要为了：

1. 如果最后一个 ACK 丢失，对端重传 FIN 时，本端仍有状态可以重新确认。
2. 让旧连接中的延迟报文有机会消失，降低相同连接标识被复用后与新连接混淆的风险。

不是“等待 2MSL 就能证明对方收到了 ACK”。协议通过状态与重传处理不确定性，并不能消除一切网络故障。

### 4.6 如何分析大量 TIME_WAIT 与 CLOSE_WAIT？

- `TIME_WAIT` 较多：常见于主动关闭方的高连接周转，先检查是否没有复用连接、短连接过多、端口是否耗尽。它本身不一定是故障。
- `CLOSE_WAIT` 长期堆积：本端已经收到了对方 FIN，但应用迟迟未关闭自己的发送方向，优先检查 socket / 响应流释放、异常路径和资源泄漏。
- 不要直接把“缩短 TIME_WAIT”当成通用性能优化，先定位连接生命周期与资源瓶颈。

## 5. 可靠传输、滑动窗口与拥塞控制

### 5.1 TCP 的“可靠”不等于业务一定成功

TCP 使用校验和、字节序列号、确认、重传、去重与重排，向应用提供可靠有序的字节流，或者报告连接失败。

关键边界：

- TCP ACK 通常表示对端协议栈已收到相关字节，不代表对端应用已处理，更不代表数据库已经提交。
- 校验和检测偶然传输错误，不等同于密码学完整性保护。
- 发送调用成功可能只意味着写入本地缓冲区。
- 请求已在服务器执行，但响应丢失时，客户端无法仅凭超时判断“业务没有执行”。这正是幂等键和业务去重的价值。

### 5.2 累计确认、SACK 与重传

假设接收方已经连续收到字节 `0～999`，但 `1000～1499` 缺失，即使 `1500～1999` 已到，累计 ACK 仍可保持在 `1000`。

- **累计 ACK**：表示此前的连续字节已收到。
- **SACK**：额外报告哪些不连续区间已收到，减少无谓重传。
- **超时重传**：RTO 根据 RTT 及其波动估计，并非固定等待一个常数。
- **快速重传**：经典算法利用重复 ACK 推断缺口，避免一直等待 RTO。
- **现代丢包检测**：可能采用基于时间等更丰富的机制，不能把“三个重复 ACK”当成全部 TCP 实现的唯一算法。

丢包不保证一定出现三个重复 ACK，例如窗口很小、尾部丢包，或后续没有足够数据到达时，都可能无法满足条件。

### 5.3 流量控制：保护接收方

接收方通告接收窗口 `rwnd`，表示当前可接收的字节容量。发送方不能无限超前发送，否则接收缓冲区会被撑满。

接收窗口为 0 时，发送方暂停正常数据发送，并通过零窗口探测等机制发现窗口重新开放，避免窗口更新报文丢失造成永久等待。

### 5.4 拥塞控制：保护网络

拥塞窗口 `cwnd` 由发送方根据网络反馈控制，避免把过多数据注入网络。简化模型为：

```text
允许的在途数据上限 ≈ min(rwnd, cwnd)
本次还能发送的数据 ≈ max(0, min(rwnd, cwnd) - 当前未确认数据)
```

实际实现还涉及 pacing、发送缓冲区、算法状态等因素。

| 机制 | 保护对象 | 主要反馈 |
| --- | --- | --- |
| 流量控制 | 接收端 | 接收窗口、应用消费速度 |
| 拥塞控制 | 传输路径 | ACK、RTT、丢包、ECN 等 |

### 5.5 慢启动、拥塞避免、快恢复怎么讲才准确？

以经典 Reno 思路理解，而不是假设所有 TCP 都如此：

1. **慢启动**：初期探测可用容量，窗口通常呈近似指数增长；“慢”是从相对小的窗口起步，不是增长缓慢。
2. **拥塞避免**：达到门限后更谨慎增长，经典模型约每 RTT 增加一个 MSS。
3. **快速重传 / 快恢复**：某些丢包反馈出现时减小窗口并恢复，不必一律完全从头开始。
4. **超时**：通常触发更保守的退让；具体窗口调整依算法而定。

原文“初始窗口永远等于一个 MSS”“任何丢包都重置为 1”“快重传必然提高 20% 吞吐量”都不应背诵。现代实现可能采用 CUBIC、BBR 等算法，初始窗口也常不止一个 MSS。

### 5.6 带宽时延积为什么重要？

```text
BDP（带宽时延积） = 带宽 × RTT
```

例如带宽为 `100 Mbit/s`、RTT 为 `100 ms`，BDP 约为 `10 Mbit`，即 `1.25 MB`。要充分利用链路，需要足够的在途数据；窗口过小会限制吞吐。反过来，无限制排队会增加延迟，造成 bufferbloat。

**面试落点：** 用户说“带宽很大，但小文件加载慢”，不一定是下载速度问题，可能是 DNS、握手、多次串行请求和高 RTT 占了主要成本。

## 6. HTTP 无状态、方法语义与幂等重试

### 6.1 “无状态”里的状态是什么？

HTTP 无状态指：**协议不要求服务器为了理解当前请求，必须依赖此前某次请求所留下的会话上下文。** 它不是说服务器没有数据库、连接没有状态，或业务不能登录。

一个购物车系统可以同时具有：

- HTTP 协议层无状态。
- TCP 连接层有状态。
- Session 会话状态。
- 数据库里的购物车业务状态。

Cookie 让浏览器重复携带会话标识，服务端据此关联身份；这是在 HTTP 之上构建应用会话，并没有把 TCP 连接等同于用户。一个用户可使用多条连接，一条代理连接也可能承载不同用户的请求。

### 6.2 安全方法、幂等与可缓存不是同一个维度

- **安全（safe）**：请求语义是只读，不要求改变目标资源状态。访问日志等附带行为不使 GET 变成不安全方法。
- **幂等（idempotent）**：多次执行相同请求，对服务器的预期效果与一次相同，不要求每次响应状态码、响应正文都一样。
- **可缓存（cacheable）**：是否允许存储并复用响应，还取决于方法语义、状态码、缓存指令与实现。

| 方法 | 典型语义 | 安全 | 幂等 |
| --- | --- | --- | --- |
| GET | 获取目标资源的表示 | 是 | 是 |
| HEAD | 获取与 GET 对应的响应元数据，不返回正文 | 是 | 是 |
| POST | 由目标资源处理提交的内容 | 否 | 不保证 |
| PUT | 用提交的表示创建或替换目标资源状态 | 否 | 是 |
| PATCH | 对资源应用局部修改操作 | 否 | 不保证，取决于补丁语义 |
| DELETE | 删除目标资源的关联 | 否 | 是 |
| OPTIONS | 查询通信选项，也用于 CORS 预检 | 是 | 是 |
| CONNECT | 建立隧道 | 否 | 否 |
| TRACE | 诊断性回环，生产环境通常限制 | 是 | 是 |

**例子：** 第一次 DELETE 返回 `204`，第二次返回 `404`，仍可以是幂等的，因为资源的最终状态都是不存在。

### 6.3 GET 与 POST 的准确区别

最重要的区别是**语义**，不是参数放在哪里：

1. GET 通常用来读取资源，查询条件常放在 URL；POST 提交内容供服务器处理，内容常在 body。
2. GET 请求内容在通用 HTTP 语义中没有普遍定义，浏览器 Fetch 不允许 GET / HEAD 携带 body；不能把某个后端私有约定当成通用用法。
3. POST 也可以有 URL 查询参数，body 也不意味着无限大；网关、服务器、框架都有大小限制。
4. GET 响应通常更容易被缓存。POST 在满足明确条件时也有可缓存语义，但常规浏览器与 CDN 的支持和使用远少于 GET。
5. HTTPS 下，GET 的路径和查询串在链路上也被 TLS 加密；但 URL 更容易进入历史记录、访问日志、复制链接和某些 Referer 场景，仍不适合存放密码、长期令牌。
6. POST body 在 DevTools、服务端日志或受控终端仍可能被看到，因此“POST 天生加密”是错的。
7. GET / POST 都可能拆成多个 TCP 段，多个写入也可能合并；不存在“GET 一个包、POST 两个包”的协议规定。
8. `Expect: 100-continue` 是一种有条件的发送机制，不是每次 POST 必经流程。

浏览器回退是否请求、是否提示重复提交，还涉及导航类型、缓存与浏览器行为，不能简化为“GET 回退永远不请求”。

### 6.4 PUT 与 POST、PATCH 如何区分？

```http
PUT /users/42/profile HTTP/1.1
Content-Type: application/json

{"name":"Alice","city":"Shanghai"}
```

客户端明确目标 URI，并按接口约定提供替换表示。PUT 可以更新，也可以在目标不存在且服务允许时创建，并不是“只能修改不能新增”。

```http
POST /orders HTTP/1.1
Content-Type: application/json

{"productId":"p-1","quantity":1}
```

服务器处理创建订单，通常由服务器分配新资源 URI。重复调用可能创建多个订单。

PATCH 是否幂等要看操作：把昵称设为 `Alice` 可以幂等；把积分加 10 通常不幂等。不能只看方法名推断具体业务实现是否正确。

### 6.5 请求超时，什么时候可以重试？

**超时只说明客户端没有及时得到结果，不说明服务端没有执行。**

对可重试请求：使用总时限、指数退避、随机抖动、最大次数，并尊重 `Retry-After`。认证失败、参数错误、业务冲突通常不应盲目重试。

对创建订单等非幂等操作，需要业务幂等机制：

```text
客户端为一次“逻辑操作”生成 idempotencyKey
        ↓
重试沿用同一个 key，不生成新 key
        ↓
服务端以“用户 / 租户 + 操作类型 + key”建立唯一约束
        ↓
校验请求摘要一致，原子记录执行状态与结果
        ↓
重复请求返回原结果，或明确告知处理中
```

仅仅在请求头加一个 `Idempotency-Key` 不会自动实现幂等。还要处理并发、存储过期、请求参数冲突、事务提交与结果记录之间的崩溃窗口，以及下游支付等跨系统操作。

## 7. HTTP 报文、连接复用与关键首部

### 7.1 HTTP/1.1 报文由什么组成？

```http
GET /articles?page=1 HTTP/1.1
Host: api.example.com
Accept: application/json
If-None-Match: "articles-v3"

```

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Cache-Control: private, max-age=60
ETag: "articles-v4"
Content-Length: 2

[]
```

请求行 / 状态行、首部、空行与可选正文是 HTTP/1.1 的常见结构。真实 HTTP/2、HTTP/3 使用帧和伪首部，不能把它们理解为把同一段文本直接换条线路发送。

### 7.2 如何确定正文边界？

在 HTTP/1.1 中，正文长度的判定与方法、状态码和字段共同相关：

- `Content-Length` 以字节描述相应长度，不是 JavaScript 字符数。
- `Transfer-Encoding: chunked` 用分块编码传输未知总长度的内容，最后以结束块收尾。
- 某些响应可用连接关闭标记结束，但会妨碍连接复用。
- HEAD 响应、`204`、`304` 等没有消息正文，不能看到长度字段就机械读取正文。
- HTTP/2、HTTP/3 依靠帧与流的结束标记，不使用 HTTP/1.1 的 chunked 编码。

**深挖：为什么这也是安全问题？**

如果代理与后端对 `Content-Length`、`Transfer-Encoding` 或异常首部解析不同，就可能对请求边界产生分歧，形成 HTTP 请求走私风险。防御重点是严格拒绝歧义报文、统一解析规则、及时升级代理与服务器，并特别检查协议降级链路；不是让前端简单加一个请求头。

### 7.3 keep-alive 到底是什么？

HTTP 持久连接表示一条连接可以处理多个请求 / 响应，节省握手和重新增长拥塞窗口的成本。

- HTTP/1.0 默认不持久，但历史上有 keep-alive 扩展，不能说完全不能复用。
- HTTP/1.1 默认持久，不要求双方每次都显式发送 `Connection: keep-alive`。
- `Connection: close` 可表示该 HTTP/1.1 连接在当前交互后关闭。
- `Connection` 属于逐跳字段，不能不加处理地转发给所有下游。
- HTTP/2、HTTP/3 禁止使用 `Connection` 等连接专用字段，不用这些头开启多路复用。

**三个常见混淆：**

| 名称 | 解决的问题 |
| --- | --- |
| HTTP keep-alive | 复用底层连接 |
| TCP keepalive | 空闲时探测连接是否仍可达，不是可靠业务心跳 |
| Fetch `keepalive: true` | 允许某些请求在页面生命周期结束后继续，有大小等限制 |

它们都不等于 WebSocket，也不代表连接永久存在。代理、负载均衡器和服务器可以按空闲超时主动关闭连接。

### 7.4 首部按职责记忆，而不是背列表

| 职责 | 常用字段 | 理解重点 |
| --- | --- | --- |
| 目标与内容协商 | `Host`、`Accept`、`Accept-Language`、`Accept-Encoding` | 客户端接受什么，不是它已经发送了什么 |
| 表示元数据 | `Content-Type`、`Content-Encoding`、`Content-Language` | 实际正文的类型与编码 |
| 缓存 | `Cache-Control`、`Age`、`ETag`、`Last-Modified`、`Vary` | 新鲜度、验证器、变体区分 |
| 条件请求 | `If-None-Match`、`If-Modified-Since`、`If-Match` | 缓存验证或并发控制 |
| 身份凭证 | `Cookie`、`Set-Cookie`、`Authorization` | Cookie 属性由响应设置，不能在请求 Cookie 中体现 |
| 跨源 | `Origin`、`Access-Control-*` | 浏览器读取许可，不是业务授权 |
| 路由与重试 | `Location`、`Retry-After` | 重定向目的地、重试时间 |
| 部分内容 | `Range`、`Content-Range`、`If-Range` | 字节范围与版本一致性 |
| 安全策略 | `Content-Security-Policy`、`Strict-Transport-Security` | 浏览器可执行的约束 |

`Accept-Encoding: br, gzip` 表示支持的压缩编码；`Content-Encoding: br` 表示返回内容确实采用 Brotli。HPACK / QPACK 压缩的是 HTTP 首部，不等同于压缩响应正文。

## 8. 状态码、重定向与错误处理

### 8.1 高频状态码及其工程含义

| 状态码 | 核心语义 | 面试与工程边界 |
| --- | --- | --- |
| `100 Continue` | 可以继续发送请求正文 | 不等于业务已成功 |
| `101 Switching Protocols` | 协议升级 | 常见于 HTTP/1.1 WebSocket 握手 |
| `103 Early Hints` | 最终响应前提供提示 | 可提前提示资源加载，不是最终响应 |
| `200 OK` | 请求成功 | 是否有业务结果需看接口契约 |
| `201 Created` | 已创建资源 | 常配合 `Location` 指向新资源 |
| `202 Accepted` | 已接受，处理未完成 | 需要任务状态查询或通知机制 |
| `204 No Content` | 成功且没有正文 | 不要再无条件 `response.json()` |
| `206 Partial Content` | 返回请求范围内的部分表示 | 不是随意截短的普通响应 |
| `304 Not Modified` | 条件 GET / HEAD 可复用已有表示 | 无正文，不是普通 URL 重定向 |
| `400 Bad Request` | 请求格式或内容存在问题 | 应改请求，而非无限重试 |
| `401 Unauthorized` | 缺少有效认证凭证 | 应按认证方案发送 `WWW-Authenticate` |
| `403 Forbidden` | 服务端拒绝执行 | 可以是权限不足，不代表刷新 Token 必有用 |
| `404 Not Found` | 未找到或不愿披露存在性 | 可用于隐藏敏感资源存在与否 |
| `405 Method Not Allowed` | 资源不支持此方法 | 响应应带 `Allow` |
| `409 Conflict` | 与资源当前状态冲突 | 如状态机冲突、版本冲突 |
| `412 Precondition Failed` | 条件请求前置条件失败 | 如 `If-Match` 校验失败 |
| `413 Content Too Large` | 请求内容太大 | 检查上传上限、分片策略 |
| `415 Unsupported Media Type` | 内容格式不支持 | 检查 `Content-Type` 与实际正文 |
| `416 Range Not Satisfiable` | 范围不可满足 | 常需检查文件是否变化 |
| `422 Unprocessable Content` | 格式理解了，但无法处理指令 | 常用于语义校验失败 |
| `429 Too Many Requests` | 请求过多 | 可配合 `Retry-After` |
| `500 Internal Server Error` | 服务端内部异常 | 需要关联服务端日志 |
| `502 Bad Gateway` | 网关从上游收到无效响应 | 不能一概归因于前端断网 |
| `503 Service Unavailable` | 暂时不可用 | 维护、过载等，可配合 `Retry-After` |
| `504 Gateway Timeout` | 网关等待上游超时 | 要区分哪一跳超时 |

`fetch()` 遇到 `404` / `500` 通常仍会 fulfilled，需检查 `response.ok` 或 `response.status`；网络错误、CORS 失败、主动中止等才可能导致 Promise reject。业务错误码与 HTTP 状态码应有明确契约，不能指望“全部返回 200”仍保留完整的基础设施语义。

### 8.2 301、302、303、307、308 的关键区别

| 状态码 | 语义 | 方法与正文 |
| --- | --- | --- |
| `301` | 永久移动 | 历史兼容允许 POST 改 GET，不适合要求严格保留提交语义的场景 |
| `302` | 临时移动 | 历史兼容允许 POST 改 GET |
| `303` | 去另一个 URI 获取结果表示 | 通常使用 GET，HEAD 场景仍需保留其无正文语义 |
| `307` | 临时重定向 | 自动重定向时不得改变方法 |
| `308` | 永久重定向 | 自动重定向时不得改变方法 |

**Post/Redirect/Get：** 提交表单后返回 `303`，浏览器通过 GET 查看结果页，可以减少刷新结果页时重复提交的问题，但服务端仍应实现必要的幂等保护。

**边界与风险：**

- “永久”不等于必然永远缓存，仍受缓存语义与客户端行为影响。
- `307` / `308` 会保留提交方法，因此不要把敏感提交重定向到任意不可信地址。
- 跨源重定向可能改变凭证转发，不能假设 `Authorization` 原样保留。
- `Location` 来自用户输入时，需要防止开放重定向，例如使用相对站内路径或严格目的地白名单。
- 404 页面不应一律重定向到首页；这会掩盖错误，并可能形成 SEO 中的 soft 404。

## 9. Range、206 与断点续传

### 9.1 请求与响应如何配对？

```http
GET /video.mp4 HTTP/1.1
Host: media.example.com
Range: bytes=1000-1999
If-Range: "video-v7"
```

```http
HTTP/1.1 206 Partial Content
Content-Range: bytes 1000-1999/5000000
Content-Length: 1000
ETag: "video-v7"
Accept-Ranges: bytes

```

区间两端都包含在内，因此 `1000～1999` 共 1000 字节。上面的响应仅展示元数据，实际应跟随对应的二进制正文。

- `bytes=1000-`：从偏移 1000 到结尾。
- `bytes=-500`：最后 500 字节。
- 多范围响应可使用 `multipart/byteranges`。
- 服务器可以忽略 Range 并返回完整 `200`，客户端必须正确处理。
- 不可满足的范围可返回 `416`，并用 `Content-Range: bytes */当前总长度` 提供信息。

### 9.2 为什么需要 If-Range？

下载到一半后文件可能被更新。仅凭旧偏移续传，会把版本 A 的前半段与版本 B 的后半段拼在一起。

客户端保存强 ETag，续传时用 `If-Range` 验证：匹配则返回对应部分；不匹配则返回完整表示，客户端应重置下载。弱 ETag 不能用于这种要求字节级一致性的验证。

下载完整后还可以按业务需求校验摘要。ETag 是不透明验证器，不保证一定是文件内容的加密哈希。

### 9.3 哪些场景真正适合？

大文件恢复下载、媒体拖动定位、按需读取文件片段等。普通图片懒加载通常是推迟发出整张图片请求，而不是依靠 `206`。HTTP 分块传输、Range 下载、视频分片协议是不同概念，不应混用。

## 10. HTTP 缓存：从新鲜度到发布一致性

### 10.1 “强缓存 / 协商缓存”是教学术语

更准确的主线是：**能否存储 → 是否匹配当前请求 → 是否新鲜 → 是否允许复用 → 是否需要验证。**

```text
找到匹配的已存储响应？
  ├─ 否：正常请求
  └─ 是：当前请求和响应策略允许直接复用？
         ├─ 是，且响应新鲜：复用缓存
         └─ 否：有可用验证器？
                ├─ 有：发送条件请求
                │      ├─ 304：更新元数据并复用缓存正文
                │      └─ 200：接收新表示并按规则存储
                └─ 无：发送普通请求取得完整响应
```

缓存过期不代表一定协商：没有验证器就可能完整请求；缓存没过期也不保证直接复用，例如 `no-cache` 或请求侧要求重新验证。

### 10.2 Cache-Control 指令的准确语义

| 指令 | 含义 | 常见误读 |
| --- | --- | --- |
| `max-age=600` | 在新鲜度计算下允许使用 600 秒 | 不是从每个浏览器收到时重新无条件计时 |
| `s-maxage=600` | 针对共享缓存的新鲜度约束 | 不直接控制浏览器私有缓存 |
| `no-cache` | 可以存储，但复用前必须成功验证 | 不是“不存储” |
| `no-store` | 不存储该次请求 / 响应的相关内容 | 不会自动清除所有历史副本 |
| `private` | 不允许共享缓存存储 | 浏览器私有缓存仍可存储 |
| `public` | 明确允许共享缓存存储，仍需满足相关规则 | 不能随意用于含用户数据的接口 |
| `must-revalidate` | 一旦过期，不得未经成功验证就复用 | 不代表每次都验证 |
| `immutable` | 新鲜期间表示不会改变，可减少多余验证 | 适用于内容指纹 URL，不是永远新鲜 |
| `stale-while-revalidate=30` | 允许在规定窗口内先用陈旧响应，再后台更新 | 有意接受短暂旧数据 |
| `stale-if-error=86400` | 某些错误下允许按窗口复用旧响应 | 需结合实现与业务可接受性 |

`Expires` 是绝对过期时间，`max-age` 优先于它。即使没有显式缓存时间，一些响应也可能被启发式缓存，不能把“未设置 Cache-Control”理解为“保证不缓存”。

### 10.3 Age 为什么影响缓存寿命？

共享缓存转发响应时，`Age` 反映该响应的估算年龄。浏览器不应把一个已经在 CDN 放了 590 秒、`max-age=600` 的响应重新当成可缓存 600 秒的新响应。

新鲜度计算还涉及 `Date`、传输时间和驻留时间。面试可以用 `当前年龄 < 新鲜度寿命` 建立模型，但不要把实际算法简化成只比较本地当前时间和 `Expires`。

### 10.4 ETag 与 Last-Modified

```http
GET /config.json HTTP/1.1
If-None-Match: "config-v12"
```

如果当前表示匹配，GET / HEAD 可以返回 `304`；浏览器使用之前的正文并更新缓存元数据。网络链路仍发生了请求，所以它省正文带宽，但不一定省 RTT。

- `Last-Modified` 基于修改时间，HTTP 日期通常是秒级，不能可靠区分同一秒内的多次内容变化。
- `ETag` 由服务器生成，可以是哈希、版本号或其他不透明标识，不保证一定使用 MD5。
- 弱 ETag 如 `W/"v12"` 允许语义等价，不要求字节完全相同。
- 两组条件同时出现时，`If-None-Match` 优先，服务端不应再把 `If-Modified-Since` 当成主要判据。

**进阶：ETag 不只是缓存。** 修改时携带 `If-Match: "v12"`，服务器仅在版本匹配时更新，否则返回 `412`，可以防止用户 A 覆盖用户 B 已提交的新版本，这是一种乐观并发控制。

### 10.5 Vary 与缓存键

`Vary: Accept-Encoding` 表示同一个 URL 对应的不同编码响应要按请求头区分；`Vary: Origin` 常用于动态返回 CORS 许可的场景。

但 `Vary` 不是自动识别所有业务上下文：

- CDN 缓存键可能还受控制台配置、查询参数策略和自定义规则影响。
- `Vary: Cookie` 可能导致变体爆炸，不能当作个性化缓存的万能方案。
- 不应仅靠“响应有 Set-Cookie”保证所有中间层都不缓存。
- 携带 `Authorization` 的请求具有特殊共享缓存约束；不要在没审查的情况下通过 `public` 等配置放开用户数据缓存。

### 10.6 前端发布的推荐策略

**内容指纹静态资源：**

```http
Cache-Control: public, max-age=31536000, immutable
```

适用于 `/assets/app.a81f9c.js` 这类内容变化就换 URL 的资源。不要覆盖同名文件，否则“不可变”承诺被破坏。

**HTML 入口：**

```http
Cache-Control: no-cache
ETag: "html-build-42"
```

允许保存，但复用前验证，便于发现新版本。高流量站点也可采用短时共享缓存，但要显式接受传播延迟。

**敏感用户信息：**

```http
Cache-Control: no-store
```

如果业务确实允许浏览器存储某些个性化数据，可以设计 `private` 策略，但需要评估设备共享、登出清理与隐私风险。

**发布顺序：** 先上传新静态资源，再切 HTML，保留旧版本资源一段时间。否则旧页面的动态 import 仍可能访问旧 chunk，造成 `ChunkLoadError`。刷新 CDN 不能自动清除浏览器已持有的 HTML、Service Worker 缓存和打开页面中的运行时。

### 10.7 不要混淆不同缓存系统

- HTTP 缓存：按 HTTP 语义管理响应，内存 / 磁盘属于实现层面的存储位置。
- Service Worker Cache API：由代码控制，不会自动替你执行所有 HTTP 新鲜度与过期清理策略。
- bfcache：保存页面状态以恢复前进后退导航，不等于缓存一个 HTTP 响应。
- React Query 等客户端数据缓存：按应用 key 与失效策略管理业务数据，不会天然遵循服务端 `Cache-Control`。

排查“为什么还是旧数据”必须先问：**旧数据究竟来自哪一层？**

## 11. HTTP/1.1、HTTP/2、HTTP/3 的演进

### 11.1 30 秒回答

HTTP/1.1 默认持久连接，但单连接上的响应调度能力有限。HTTP/2 用二进制分帧和流实现多路复用，并通过 HPACK 压缩首部，解决 HTTP 层的串行响应限制，但仍受 TCP 有序字节流的队头阻塞影响。HTTP/3 把 HTTP 映射到基于 UDP 的 QUIC，以独立可靠流减少跨流的传输层队头阻塞，并整合 TLS 1.3，但并不消除所有等待，也不保证所有场景都更快。

| 维度 | HTTP/1.0 | HTTP/1.1 | HTTP/2 | HTTP/3 |
| --- | --- | --- | --- | --- |
| 常见传输 | TCP | TCP | TCP | QUIC，承载于 UDP |
| 连接复用 | 默认非持久，有历史扩展 | 默认持久 | 通常复用连接并多路复用 | 通常复用 QUIC 连接并多路复用 |
| 报文组织 | 文本起始行与首部 | 文本起始行与首部 | 二进制帧、流 | HTTP 帧映射到 QUIC 流 |
| 首部压缩 | 无 HPACK / QPACK | 无 HPACK / QPACK | HPACK | QPACK |
| 主要队头阻塞 | 串行请求处理常见 | 管线化响应有序 | TCP 丢包可阻塞多个 HTTP 流 | 缺口主要阻塞相关流，仍有其他依赖 |
| 安全 | 可经 TLS | 可经 TLS | 主流浏览器通常通过 TLS 使用 | QUIC 整合 TLS 1.3 |

HTTP/3 的核心规范 RFC 9114 发布于 2022 年，不能继续写成“2020 年、仍未标准化”。日常说 HTTP/2、HTTP/3 即可，不必人为加 `.0`。

### 11.2 HTTP/1.1 管线化不是“六个并发请求”

持久连接允许顺序复用。管线化则允许在前一个响应返回前发送后续请求，但响应仍要按请求顺序返回；前一个响应慢，后面的响应无法越过它。

浏览器对每个源常见的连接数量限制是实现策略，不是 HTTP/1.1 管线化规定的“最多六个请求”。主流浏览器也没有广泛依赖管线化来实现网页并发，通常使用多条连接。

### 11.3 HTTP/2 多路复用到底复用了什么？

一个 HTTP 交互关联一个流，流拥有 stream ID。HEADERS、DATA 等帧可以交错发送，接收方按流重新组织。

```text
一条 TCP 连接上的帧序列：
[流 1 HEADERS][流 3 HEADERS][流 3 DATA][流 1 DATA][流 5 HEADERS]...
```

因此慢接口 A 不再仅因为“响应必须排在前面”，就挡住已经准备好响应的接口 B。

但有边界：

- 并发流数量受双方设置与资源限制，不是无限。
- 服务端 CPU、数据库、调度和连接带宽仍然可能共享瓶颈。
- 不保证一个域名永远只建立一条连接；代理、网络分区、连接生命周期等都会影响。
- 在满足证书、地址与客户端策略等条件时，还可能出现跨源连接合并，也不是永远“一域名一连接”。

### 11.4 为什么 HTTP/2 仍存在队头阻塞？

TCP 向上层交付的是连续有序字节。如果某段字节丢失，后续字节即使已到，也可能暂时无法交付给 TLS / HTTP/2。由于多个流的帧都在这一条 TCP 字节流里，其他流可能一并等待。

区分三种“阻塞”：

1. **HTTP/1.1 管线化响应排序**：A 的响应必须在 B 前面。
2. **TCP 字节流缺口**：缺失字节挡住后续多个 HTTP 流的数据交付。
3. **业务依赖**：页面必须先拿到用户 ID 才能查询订单；换 HTTP/3 也不会自动消除。

“HTTP/2 解决了队头阻塞”必须补充“解决了哪一层”。

### 11.5 HPACK 与 QPACK 为什么不能简单说成差量发送？

HPACK 结合静态表、动态表、索引和 Huffman 编码压缩首部，并非只发送“相对上一个请求的差异”。双方必须维护一致的解码状态。

QUIC 的流可独立交付，如果直接沿用强顺序依赖的动态表机制，某条流可能等待另一条流的表更新。QPACK 通过专门的编码器 / 解码器流、引用约束与阻塞流限制来适应这个模型。

因此 HTTP/3 中仍可能发生**首部解码依赖引起的等待**。QPACK 降低并控制这种阻塞，不是宣布任何数据永远互不依赖。

### 11.6 QUIC 如何在 UDP 上做到可靠？

UDP 只负责传递数据报，QUIC 自己实现：

- 连接管理、包号、ACK、丢包检测和拥塞控制。
- 可靠流的字节偏移、重组、有序交付。
- 每流与连接级流量控制。
- 整合 TLS 1.3 的密钥协商、认证和加密保护。
- Connection ID、路径验证等连接迁移机制。

QUIC 通常重传丢失信息到新的包中，而不是用原包号原样重发整个包。HTTP/3 的 HTTP 消息使用可靠流，不能因为底层是 UDP 就把网页传输描述成“不保证完整”。

### 11.7 HTTP/3 消除了什么，又没有消除什么？

独立流使流 A 的缺失字节不必阻止流 B 已到齐的数据交付。但：

- 同一流内部仍要求有序交付，缺口仍会等待恢复。
- 多条流通常共享连接拥塞控制，丢包可能压低整条连接的发送能力。
- 首部压缩依赖、应用依赖与调度仍可能阻塞。
- 一个 UDP 数据报丢失可能同时影响其中承载的多个流的数据。
- UDP 被阻断、服务器实现开销、路径质量等可能影响收益，需要回退策略和实测。

### 11.8 0-RTT 与连接迁移的条件

**0-RTT：** 通常依赖曾经连接过并持有可恢复的会话信息，允许客户端提前发送早期数据，不代表首次访问无需握手，更不代表请求不需要传播时间。早期数据可能被拒绝，也有重放风险，详见下一章。

**连接迁移：** QUIC 使用 Connection ID 辅助识别连接，不只依赖传统四元组。Wi-Fi 切蜂窝网络等场景下可以尝试在新路径延续连接，但仍需要路径验证与拥塞状态处理，不是承诺任何断网都无缝恢复。

### 11.9 Server Push 还是推荐优化吗？

HTTP/2 在协议中定义过 Server Push，但它并没有成为稳定通用的浏览器性能优化路径，Chromium 已移除 HTTP/2 Server Push 支持。不要把“部署 HTTP/2 就自动把 CSS / JS 推给用户”当成现代默认行为。

更实际的优化是正确缓存、减少发现延迟，并按需使用 `preload`、`modulepreload` 或 `103 Early Hints`。它们与 Server Push 的机制不同，也可能因错误预加载浪费带宽。

## 12. HTTPS、TLS 握手与证书信任链

### 12.1 HTTPS 提供哪三项核心能力？

1. **机密性**：第三方不能直接读取传输中的应用数据。
2. **完整性**：篡改密文或认证数据会被检测，而不是悄悄变成另一份合法消息。
3. **身份认证**：通常客户端验证服务端身份；普通 HTTPS 不等于服务器已经认证了业务用户，也不默认使用双向证书认证。

HTTP/1.1、HTTP/2 的 HTTPS 通常通过 TCP 上的 TLS 实现；HTTP/3 通过 QUIC 整合 TLS 1.3。因此“HTTP / HTTPS 都一定基于 TCP”不准确。默认端口 80 / 443 是约定，不是安全性的来源。

SSL 是历史协议名称，现代部署应使用 TLS；不要把过时 SSL 当成推荐技术。

### 12.2 加密、密钥交换、签名、哈希分别做什么？

| 能力 | 解决问题 | TLS 中的角色 |
| --- | --- | --- |
| 对称加密 / AEAD | 高效保护大量数据，并验证完整性 | 例如 AES-GCM、ChaCha20-Poly1305 |
| 非对称密钥交换 | 双方在不直接发送最终密钥的情况下建立共享秘密 | 例如 ECDHE |
| 数字签名 | 证明持有私钥，认证握手或证书内容 | 例如 RSA-PSS、ECDSA |
| 哈希与密钥派生 | 摘要、绑定握手上下文、导出不同用途密钥 | TLS 1.3 使用 HKDF 等机制 |

不要把所有非对称操作都理解成“公钥加密、私钥解密”。现代 TLS 中，证书公钥经常用于验证签名，临时密钥交换负责导出共享秘密；二者职责不同。

### 12.3 TLS 1.3 完整握手主干

以下省略一些可选消息，描述常见的证书认证、无 HelloRetryRequest 的完整握手：

```text
客户端                                             服务端
  | -- ClientHello ---------------------------------> |
  |    支持版本、算法、key_share、SNI、ALPN 等             |
  | <--- ServerHello -------------------------------- |
  |      选择参数、key_share                            |
  | <--- {EncryptedExtensions, Certificate,           |
  |       CertificateVerify, Finished} --------------- |
  |                                                   |
  | 验证证书、签名、握手完整性，导出并验证密钥              |
  | -- {Finished} -----------------------------------> |
  | <========== 应用数据受对称 AEAD 保护 ==============> |
```

花括号表示相关消息已用握手阶段的密钥加密；实际记录组织并不要求每一行都是独立网络包。

核心过程：

1. 双方交换临时密钥份额，计算共享秘密，而不是把最终对称密钥明文发送给对方。
2. 服务端证书提供可被信任链验证的身份材料。
3. `CertificateVerify` 用签名证明服务端持有对应私钥，并绑定当前握手内容。
4. `Finished` 验证握手记录的完整性及密钥一致性。
5. 从共享秘密与握手上下文派生不同方向、不同阶段的密钥。

如果没有合适的密钥份额，服务端可能发送 HelloRetryRequest，增加往返。会话恢复也可能省略完整证书认证消息，所以不能把一张时序图当成所有连接都相同。

### 12.4 为什么原文的“三个随机数 + RSA 加密预主密钥”不应当作通用答案？

那是历史 TLS RSA 密钥交换的一种典型讲法，不代表现代 TLS：

- TLS 1.2 既存在历史 RSA 密钥交换，也广泛使用 ECDHE，需要明确密码套件与握手方式。
- TLS 1.3 移除了静态 RSA 密钥交换，不能继续用“客户端生成秘密，再用证书公钥加密发给服务器”解释所有连接。
- 使用 RSA 证书不意味着一定采用 RSA 密钥交换；RSA 也可以只是签名认证算法。

### 12.5 前向保密是什么？

使用临时 ECDHE，并妥善销毁临时秘密后，即使攻击者未来拿到服务器的长期证书私钥，也不应仅凭之前录下的流量解密历史会话。

这就是前向保密。它不是防止当前终端被入侵，也不是对所有 PSK 模式、0-RTT 早期数据作同样保证。TLS 1.3 中不同恢复模式的性质仍应区分。

### 12.6 浏览器如何验证证书？

常见验证要点包括：

1. 构建从叶子证书到受信任根的证书链；服务器通常发送叶子证书和必要中间证书，不必发送根证书。
2. 验证各级签名、CA 约束、用途与算法是否符合要求。
3. 检查访问主机名是否匹配证书 SAN，不是“证书存在就够了”。
4. 检查有效期、本地时间与浏览器策略。
5. 按平台与浏览器策略处理吊销、Certificate Transparency 等要求。

根证书受信任是因为操作系统 / 浏览器信任库或管理员配置，不是因为它自签名就自动可信。证书只说明相应身份绑定通过了验证，不代表网站经营者没有恶意。

**吊销不是每次请求都在线向 CA 问一遍。** CRL、OCSP、OCSP Stapling、浏览器本地机制与失败策略各不相同，不应保证所有客户端都实时获得所有吊销信息。

### 12.7 CA 证书能伪造吗？

任何人都能创建自签名证书，难点在于让受害者客户端接受它。攻击可能来自：

- CA 误签发或被入侵。
- 用户 / 管理员安装了不可信根证书。
- 域名控制权、签发流程或服务器私钥被攻破。
- 用户忽略证书警告。

所以答案不是“数学上绝对不可能”，而是正常情况下攻击者无法为目标域名获得受信任的有效身份链；信任体系、密钥和终端仍可能被破坏。

### 12.8 TLS 握手到底需要几个 RTT？

只比较典型条件下的握手开销，不含 DNS、服务器处理和最终响应传播：

| 情况 | 建立路径的大致模型 |
| --- | --- |
| TCP + 传统完整 TLS 1.2 | TCP 约 1 RTT，TLS 通常再约 2 RTT |
| TCP + 完整 TLS 1.3 | TCP 约 1 RTT，TLS 通常再约 1 RTT |
| 新 QUIC 连接 | 传输与 TLS 集成，典型约 1 RTT 完成主要握手 |
| 已有连接 | 可跳过新连接与完整握手成本 |
| 可恢复会话的早期数据 | 特定条件下可 0-RTT 发送，但可能被拒绝或重放 |

Retry、HelloRetryRequest、证书链、丢包、代理与恢复策略都可能改变实际时间，不能断言每次 HTTPS 必须固定消耗 3～4 个 RTT。

### 12.9 0-RTT 为什么存在重放风险？

服务器尚未完成新的完整握手时，就可能接收基于恢复信息加密的早期数据。攻击者可能重复递交捕获的早期数据，使其被多次处理。

因此：

- 不应默认让支付、下单、转账等操作接受早期数据。
- 仅看 GET 方法名也不够，如果 GET 被错误设计成改变状态，仍有风险。
- 部署端需要定义可接受早期数据的请求、反重放策略和拒绝后的重试机制。
- `425 Too Early` 可以用于拒绝有重放风险的早期请求，让客户端稍后重试。

### 12.10 HTTPS 保护不了什么？

- XSS、CSRF、越权、数据库注入、恶意依赖。
- 服务器、浏览器扩展或终端已经被控制。
- TLS 在 CDN 终止后，CDN 到源站仍使用不安全链路的部分。
- 网站自身通过日志、埋点或错误信息泄漏数据。
- 用户对错误证书主动放行。

HTTPS 加密 HTTP 的路径、查询串、首部和正文，但不保证隐藏目标 IP、流量时序和长度；域名是否可见还涉及 DNS、SNI 与 ECH 等部署条件。客户端 DevTools 显示明文是因为它是通信端点，不代表网络上在明文传输。

<a id="chapter-13"></a>
## 13. 正向代理、反向代理与信任边界

### 13.1 如何区分？

- **正向代理**代表客户端访问外部服务，例如企业出口代理。客户端知道并选择代理。
- **反向代理**代表服务器接收客户端请求，再转给内部服务，常承担 TLS 终止、路由、负载均衡、缓存和限流。

```text
客户端 → 正向代理 → 公网 → CDN / 反向代理 → 应用服务器
```

对 HTTPS，正向代理可以用 CONNECT 建立隧道，只转发加密字节；如果进行 TLS 解密检查，则必须在客户端信任体系中具备相应能力，信任边界已经改变。

### 13.2 开发代理为什么能解决跨域？

浏览器向自己的同源开发服务器请求 `/api`，开发服务器再向真正后端转发。后半段是服务器到服务器请求，不受浏览器 CORS 读取限制。

这不是后端“绕过安全”，而是把浏览器请求拓扑改成了同源。生产环境仍需部署对应网关 / BFF 或正确配置 CORS；开发代理配置不会自动进入生产环境。

### 13.3 哪些转发头不能直接信任？

`X-Forwarded-For`、`Forwarded`、`X-Forwarded-Proto` 等可能影响真实 IP、协议判断与安全 Cookie。客户端可以伪造同名字段，因此应用只能在明确可信代理链的前提下解释它们，边缘代理应清洗或重建字段。

同理，不能无条件信任客户端提交的 `Host` 来生成密码重置链接、绝对重定向或缓存键。代理解决流量入口问题，也引入新的信任边界。

<a id="chapter-14"></a>
## 14. 同源策略、CORS 与预检请求

### 14.1 同源与同站必须分开

**Origin（源）**通常由协议、主机、有效端口组成。`https://app.example.com` 与 `https://api.example.com` 不同源。

**Site（站点）**在现代 Cookie 语境中通常按 scheme 与可注册域判断，依赖公共后缀列表，不是简单取最后两段域名。上面两个 HTTPS 子域通常同站；HTTP 与 HTTPS 在 schemeful same-site 规则下可视为跨站。

- CORS 主要围绕跨源读取。
- SameSite Cookie 主要围绕跨站凭证发送。
- 同站不等于同源，兄弟子域被攻破仍可能影响整体安全设计。

### 14.2 同源策略限制的是哪些能力？

浏览器限制不同源页面之间读取 DOM、存储和某些响应数据，但并不一律禁止跨源资源加载、导航或请求发送。

例如跨站表单、图片加载在一定条件下可以发出请求；脚本不能因为请求成功，就自由读取跨源响应。由此可见：**“读不到响应”不等于“请求没到服务器”。**

CORS 是服务器通过响应字段授权浏览器向特定源公开响应的一套机制，不是服务器身份认证，也不约束普通脚本工具直接调用接口。

### 14.3 为什么有些 POST 会先 OPTIONS？

触发条件不是 POST 本身，而是请求是否超出 CORS safelist 等规则。常见会触发预检的跨源请求：

- PUT、PATCH、DELETE 等方法。
- `Content-Type: application/json`。
- `Authorization` 或 `X-CSRF-Token` 等非 safelisted 请求头。

GET / HEAD / POST 配合符合限制的首部与以下常见内容类型，可能不预检：

- `application/x-www-form-urlencoded`
- `multipart/form-data`
- `text/plain`

还存在首部值、长度以及特定 API 使用等细节，不应只检查 Content-Type 字符串。`credentials: 'include'` 本身不必然触发预检。

### 14.4 一次携带 Cookie 的跨源 JSON 请求

```javascript
const response = await fetch('https://api.example.com/orders', {
  method: 'POST',
  credentials: 'include',
  headers: {
    'Content-Type': 'application/json',
    'X-CSRF-Token': csrfToken,
  },
  body: JSON.stringify({ productId: 'p-1', quantity: 1 }),
});

if (!response.ok) {
  throw new Error(`HTTP ${response.status}`);
}
```

浏览器可能先发送：

```http
OPTIONS /orders HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type,x-csrf-token
```

服务器对允许的源返回：

```http
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: POST
Access-Control-Allow-Headers: Content-Type, X-CSRF-Token
Access-Control-Max-Age: 600
Vary: Origin
```

这里的预检许可不等于订单已通过身份与业务授权。标准预检本身通常不携带用户凭证，不能要求它先有业务登录 Cookie 才返回，否则容易把合法请求卡死。实际 POST 仍必须做认证、授权与 CSRF 校验。

实际响应也需要合适的 `Access-Control-Allow-Origin` 与 `Access-Control-Allow-Credentials`，不能只给 OPTIONS 配置。若动态预检响应会被中间缓存存储，还需正确区分相关请求字段或避免不恰当缓存。

### 14.5 带凭证请求的限制

- `Access-Control-Allow-Origin` 必须为明确允许的源，不能用 `*` 配合凭证模式。
- 不要无条件把请求 `Origin` 反射回响应；应与严格 allowlist 比较。
- Cookie 是否发送仍受 Domain、Path、Secure、SameSite 及浏览器第三方 Cookie 策略等限制。
- 跨站 Cookie 常需要 `SameSite=None; Secure`，但这不是绕过第三方 Cookie 限制的万能开关。
- JavaScript 要读取非默认公开响应头，如业务请求 ID，可能需要 `Access-Control-Expose-Headers`。
- `Set-Cookie` 是禁止向前端脚本暴露的响应头，不能靠 expose 配置让 JavaScript 读取它。

### 14.6 三个常见错误修复方式

**错误一：设置 `mode: 'no-cors'`。**

它不让你自由读取跨源数据，而是限制请求能力，并通常得到 opaque response，脚本无法读状态与正文。它不是通用跨域修复方法。

**错误二：让前端请求头携带 `Access-Control-Allow-Origin`。**

这是服务端响应许可，放到请求里不会让浏览器授权，反而可能增加预检。

**错误三：认为 OPTIONS 会在每次请求前出现。**

预检有专门缓存，并受浏览器上限、请求信息与缓存分区等条件影响。`Access-Control-Max-Age` 控制预检许可缓存，不等于业务响应缓存。

**历史补充：JSONP。** 它利用脚本跨源加载，在回调形式下执行服务端返回的 JavaScript，通常只能用 GET，等于把数据源当作可执行代码信任。现代接口优先使用 CORS 或受控的同源 BFF，而非用 JSONP 绕过问题。
